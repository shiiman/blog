## はじめに

個人開発の iOS / Android アプリ **Bucket List Commit** を、App Store と Google Play へ同時に提出しました。この記事はその Google Play 側（Play Console）で提出までにやったことの記録です。

[App Store Connect 編](/engineering/app/app-store-connect-review-submission-notes/)にも書きましたが、アプリのコードを書き終えてからが本番でした。 Play 側は Apple 側とは**罠の種類が違います**。

Apple は「成功レスポンスが嘘をつく」タイプの罠が多かったのに対し、Play はこうでした。

- 本人確認で一度落とされると、試行回数に上限がある
- 公式ヘルプに載っていない中間ステップがある（そこを埋めないと導線自体が出ない）
- Console のナビゲーションが頻繁に移動する
- 「アプリのセットアップ」に、チェックリストに現れない必須項目がある
- API が返す成功レスポンスと実際の状態が違う（これは Apple と同じ）

という構成です。特に**本人確認**と<strong>「アプリのセットアップ」の完了漏れ</strong>は、個人開発者が高確率で詰まる場所だと思います。

> アプリの実装やバグ修正の話は含みません。ストア審査のためだけに追加で実装が必要になった機能については、[全工程まとめの記事](/engineering/app/personal-app-cross-store-release-full-journey/)で扱います。

### この記事の表記について

固有の識別子は伏せています。

| 記事内の表記 | 実際は |
|---|---|
| `com.example.app` | パッケージ名 |
| `Example Works` / `EXAMPLE WORKS` | 屋号（D&B に登録した事業体名）|
| `1234567890123456789` | Play のデベロッパーアカウント ID |
| `1234-5678-9012` | お支払いプロファイル ID |
| `999999999` | D-U-N-S 番号 |
| `example-project` | Firebase / GCP プロジェクト ID |
| `review@example.com` | 審査用アカウント |

アプリ名 `Bucket List Commit` と公式サイト `blc.shiiman.dev` は実名です。

### 前提

- 個人事業主が**組織アカウント**で登録（本人確認あり）
- Kotlin / Jetpack Compose・Room・Firebase・Play Billing・Glance
- 配信地域は**日本 + 米国**
- iOS と同日に提出する方針

## 提出までの全体像

```
Step 0  屋号を決める → 開業届に屋号を記載して出し直す（控えが本人確認の材料になる）
Step 1  D-U-N-S 番号を取得                        ← 外部待ち
Step 2  D&B グローバルデータへの反映を待つ         ← 外部待ち（数日〜2週間）
Step 3  Play Console で組織アカウントを作成
Step 4  組織のウェブサイト確認（Search Console 経由）
Step 5  本人確認（組織の登録書類）              ← ここが最大の関門
Step 6  電話番号の確認 / 15% サービス手数料への登録 / デベロッパー名の変更
Step 7  税務情報（W-8BEN）+ 銀行口座 → デポジット認証
Step 8  アップロード鍵の生成 → release 署名 → AAB → アプリ作成 → 内部テスト
Step 9  課金商品の登録（新 API）
Step 10 「アプリのセットアップ」11項目 + 広告ID の申告
Step 11 ストア掲載情報（画像・掲載文）
Step 12 課金テスト（ライセンステスター）→ 提出
```

Step 5 の本人確認が完了しないと、Step 6 の 3 つが解禁されません。これは公式ヘルプに書かれていない依存関係です（後述）。

## 先に確認すべき「期限のある公式要件」

Play には**期限つきの技術要件**があります。満たしていないと「公開」でブロックされます（既存バイナリは動き続けるので、気づくのが遅れます）。

| 要件 | 性質 |
|---|---|
| targetSdk の年次要件（毎年 8 月末に最低 API レベルが上がる）| 公開ゲート。延長申請の窓もあるが期限つき |
| Play Billing ライブラリの最低バージョン（毎年 8 月末に上がる）| 公開ゲート。既存バイナリは動き続けるので気づきにくい |
| 16 KB ページサイズ対応（施行は先だが猶予は有限）| ネイティブコードを持つアプリのみ |
| データ削除の公開 URL | アカウントを作れるアプリは必須 |

私は提出直前の総ざらいで確認して**たまたま全部満たしていました**が、これは運が良かっただけです。

16 KB ページサイズは、自前のネイティブコードが無くても依存ライブラリの `.so` が対象になります。 AAB 内の `.so` を 2 本見つけて、両方とも `p_align` が `0x4000`（16KB）であることを確認しました。「NDK を使っていないから対象外」とは限りません。

> **教訓**: 「公開ゲート」の要件は、着手時に自分の値を実測して表にしておく。提出直前に気づくと、間に合わなければそこで数週間止まります。

## 組織アカウントか個人アカウントか

最初の分岐です。Play では組織 → 個人の変更ができません（Apple は Individual → Organization が可能）。

| | 個人アカウント | 組織アカウント |
|---|---|---|
| D-U-N-S | 不要 | 必須 |
| クローズドテスト要件 | 12人×14日連続 | 免除 |
| 公開される情報 | 住所（IAP ありの場合）| 住所 + 電話番号 |
| 種別変更 | 組織へ変更可 | 個人へは戻せない |

私は**組織アカウント**を選びました。判断の根拠はこれです。

- Play のデベロッパー名は種別に関係なく自由設定できるので、「組織化すれば本名を隠せる」というメリットは実質ない（Apple 側は Individual だと本名固定なので、そもそも両 OS で揃わない）
- 組織化の実利は「12人×14日のクローズドテスト要件が免除される」ことだけ
- ただしその免除は大きい。12人集めて 14 日連続で使ってもらうのは、個人開発では 3〜4 週間の外部待ちになる

この要件が適用されるのは「ある時期以降に作成した個人アカウント」だけです。公式ヘルプのタイトル自体が「**新しい個人用デベロッパー アカウント向け**のアプリテスト要件」で、本文も「〜以降に**個人アカウント**を作成したデベロッパーは…」と限定しており、組織アカウントへの言及がありません。

つまり「アカウント種別の選択がクリティカルパスそのものを消せる」ということです。最初の比較でこの依存関係を見落としていて、「12人×14日は避けられない最長経路」として扱っていました。

組織化のコスト見積もりは、D-U-N-S の取得ルートで大きく変わります。D-U-N-S は Apple の専用ページから無料・数日で取得でき（書類提出なし）、事業体に 1 つの識別番号で用途に紐づかないので、Apple 経由で取っても Play で使えます。これを知らないと日本の窓口の有料コース（16,500円）や無料コース（30営業日）を前提に考えることになり、**組織化の期間コストを大きく見誤ります**（私はそれで一度 A → B → C と判断をやり直しました）。

> 屋号の決定 / 屋号入り開業届の取り直し（税務署）/ D-U-N-S の 3 ルート比較と TSR フォームの中身 / 名義の可逆性 / 2FA と復旧手段は両ストア共通の前段なので、[事務手続き編](/engineering/app/indie-app-store-registration-paperwork/)にまとめました。

要件はアプリ単位なので、今後もアプリを出すなら組織アカウントが繰り返し効きます。

### 組織アカウント作成で通った入力値

D&B に照合が通ると、組織名と住所が**自動補完**されます。

| 項目 | 値 |
|---|---|
| 組織名 | `EXAMPLE WORKS`（D&B の全大文字表記がそのまま入る）|
| 種別 | 組織アカウント |
| アカウント ID | `1234567890123456789` |
| お支払いプロファイル ID | `1234-5678-9012` |
| D-U-N-S | `999999999`（照合済み）|

そのほか実際に通った値です。

- 組織の種類 `企業またはビジネス` / 規模 `1〜10 人`
- 電話番号は区切り無しの `+81xxxxxxxxxxx`（`+81 80-xxxx-xxxx` は**エラーで弾かれた**）
- アプリ `1〜5個` / 収益化「はい」= アプリ内購入 + 定期購入 / カテゴリは「上記以外」のみ（**子ども向けは選ばない**）
- Google からの連絡先メール: Google アカウントとは別で、かつサイトのドメインと一致する必要がある（私は `admin@<自ドメイン>` を使った）

### 電話番号の確認は 2 つある（SMS が 2 通来る）

これは軽くハマりました。確認が必要な電話番号は **2 種類**あります。

| 欄 | 公開されるか |
|---|---|
| 連絡先電話番号 | Google 専用。Play には出ない |
| デベロッパーの電話番号 | 公開されるデベロッパープロフィールに表示される |

同じ番号を入れると SMS が 2 通来ます。1 つずつ完了させてください（片方だけ終わらせて「済んだ」と思うと、いつまでも設定完了になりません）。

### アカウント設定が完了したことの確実な判定

個々の欄のチェックマークより、これが確実な指標でした。

> Play Console ホームの「**デベロッパー アカウントの設定を完了する**」カードと、上部の青いバーが**両方とも消える**

個々の項目を見ていくと「これは済んだが、あれはまだ？」と分からなくなります。このカードの消滅で判定するのが一番速いです。

### お支払いプロファイルで「個人 / ビジネス」を選ばされない

事前に「個人事業主が組織を選ぶと法人登記簿を求められて詰む」（Google Ads 由来の話）というリスクを警戒していましたが、Play では選択肢自体がありませんでした。組織アカウント登録時に組織プロファイルが自動生成されます。

ただし**別の危険があります**。

同じ画面に既存の個人プロファイル（AdSense / 広告 / Cloud 用）が並ぶので、絶対に選んではいけません。選ぶと次のことが起きます。

1. 領収書に本名が出て D-U-N-S を取った意味が消える
2. Play の売上と Google Cloud（Firebase の従量課金）の請求が同一プロファイルに混ざる

画面に「お支払いプロファイルは Google のすべてのサービスで共有、使用されます」と明記されています。

## 本人確認 — ここが最大の関門

個人事業主が組織アカウントを取るとき、最も詰まるのがここです。一度却下されました。

### 却下の経緯

最初、**開業届の控えを単体で提出**しました。マイナンバーは黒塗りにして。

画面は「本人確認中」に変わりました。これを「アップロードされた = 進行中」だと理解しましたが、数時間後に却下メールが来ました。

> 組織を証明する書類: ご提出いただいた書類には必要なページが含まれていません。必要なページがすべて見えるようにして書類をご提出ください。

画面が「本人確認中」に変わるのは「アップロードされた」だけで「承認された」ではありません。

これは `altool` の `UPLOAD SUCCEEDED` ≠ 受理と同型の罠です。同じ日に自分でその話を説明しながら踏みました。ステータス表示ではなく Google からのメールで判定します。

もう 1 つ大事な点があります。

本人確認の試行回数には上限があります。

> 不正防止のため、本人確認手続きを行える回数は限られています

推測で再提出してはいけません。

### 却下理由の 2 仮説（対処が正反対）

却下メールの文面だけでは原因が絞れませんでした。

| | 仮説 | 根拠 |
|---|---|---|
| A | マイナンバーの黒塗りが「編集・操作」と判定された | Play Console のホームに「書類を編集したり操作したりしないでください」と常時表示されている。却下メールにも「書類の一部が隠れたりしている場合…受け付けられません」|
| B | 提出の証明（受付印 / 受信通知）が足りない | 却下理由の文面「必要なページが含まれていません」|

- A なら → **黒塗りを外した原本**を出す（マイナンバーが Google に渡る）
- B なら → **税務署発行の裏付け**を追加する

対処が正反対なので、両方やることにしました。

### 構造的な理由: 開業届は「自分が作った書類」

Web 調査で複数の先行事例が一致しました。

> 開業届（受付印あり）+ 納税証明書を、1 つの画像ファイルにまとめて提出

開業届の単体提出では通りません。理由は Google の公式要件にあります。

> 書類は政府 / 税務当局など信頼できる発行元が発行したものでなければならない

開業届は自分が作って提出した書類で、税務署が発行したものではありません。だから当局発行の裏付けが要ります。

> そもそも**屋号入りの開業届をどう取り直すか**（屋号専用の変更届は存在しない / 開業日は当初の日付のまま書く / Mac から e-Tax を直接叩く経路が無い）は、[事務手続き編](/engineering/app/indie-app-store-registration-paperwork/)に書きました。

### 正解は納税証明書ではなく「税務署のリーフレット」だった

ここで私は「納税証明書を取ってきてください」と案内しました。**これは誤りでした**（まだ納税していないので実質空になるうえ、そもそも不要）。

2025 年 1 月に税務署の収受日付印（受付印）が全国一律で廃止されました。その代替措置として、国税庁が窓口で<strong>リーフレット『申告書等の提出について』</strong>を交付しています。

- 「（本日）、書面で提出された申告書等を受け付けました。」と大きく表記されている
- **日付・税務署名の記載欄がある**（窓口で記入して交付される）
- 郵送提出でも、返信用封筒を同封すれば返送される

これは「税務当局が発行した提出事実の証明」なので、Google の「信頼できる発行元が発行した書類」要件を満たし、「受付印付き開業届」と実質同等です。

> **教訓**: 制度が廃止されたときは「代替措置が何か」まで調べる。
> 私は「収受日付印が廃止された」までは把握していたのに、代替がリーフレットで交付されることを知らなかったので、納税証明書という遠回りを提案してしまいました。

### 通った提出物

**1 枚の JPEG に原寸で縦連結**しました（2000×8156 / 2.86MB）。

```
① 開業届の控え（黒塗りなし）        → 屋号の証明
② リーフレット『申告書等の提出について』 → 提出事実 = 税務当局発行の裏付け
③ 英訳ページ（保険）
```

写真は撮り直しました。却下条件に「光の反射や光沢」「暗い・ぼやけている」が明記されているので、前回の写真（左上に影があった）は使いません。試行回数に上限があるので、画質のリスクは消しておくべきです。

**連結するときに画素を加工しない**

「1 枚にまとめる」ときに縮小や再圧縮で判読性を落とすと、それ自体が却下条件（暗い・ぼやけている）に当たります。

私は画像処理ツールが入っていない環境だったので、PDF に埋め込まれた画像を直接取り出して、拡大縮小せず原寸のまま白いキャンバスに縦に並べる方式にしました。そして、判読性は「帯ごとの輝度統計」＋「原寸で切り出した部分の目視」で検証しました。全体を縮小表示して「読めるっぽい」で判断すると、提出後に却下されて試行回数を 1 つ失います。撮影は明るい場所で真上から、フラッシュなしで、四隅を入れて撮ります。

### 承認は即時だった

```
「組織の登録書類が必要です」（会社設立証書 / 税務署からの書類の抜粋 / 納税証明書 の 3 択を提示）
  → 【書類アップロード】
  → 「組織の情報をご提供ください」（組織名 + 住所を表示して一致確認）
  → 「EXAMPLE WORKS の確認が完了しました」/ 組織 = 確認済み
```

フロー内で完了表示が出て、同時刻にメールも来ました。初回は「本人確認中」で数時間置かれてから却下メールでしたが、今回はその場で終わりました。「審査に数日かかる」前提で待たなくていいということです。

裏取りもしました（画面表示だけで判定しないルール）。

```
From: Google Play Console <noreply-play-console@google.com>
件名: 本人確認が完了しました
```

### この画面の注意点 2 つ

- 画面の書類リストに「開業届」は載っていません（会社設立証書 / 税務署からの書類の抜粋 / 納税証明書 の 3 つだけ）。**それでも通ります** ——公式の日本向けヘルプに「個人事業主は**個人事業の開業・廃業等届出書**を送信することで組織として適格性確認を受けられる」と明記があり、実体は 2 番目の「税務署からの書類の抜粋」に当たります。UI の選択肢に無いことは、不適格の根拠になりません。
- 「組織の情報をご提供ください」画面の「編集」は絶対に触らないでください。D&B 照合済みの組織情報が崩れます。書類は日本語 / Google 側の登録はローマ字表記でズレて見えますが、それで正しいです。

**提出したファイルは残しておくこと**（再提出や別サービスの本人確認で再利用できる）。

## 15% サービス手数料 — バナーが出ない真因

Play の 1 回限りの購入（買い切り商品）は、プログラム未登録だと 30% です。

| BLC の商品 | 未登録 | 登録後 |
|---|---|---|
| サブスク ¥280/月・¥2,800/年 | 15%（登録不要・自動・年間収益に無関係）| 15% |
| 買い切り ¥250 × 6 種 | 30% | ○15% |

定期購入は最初から 15% ですが、1 回限りの購入はプログラム未登録だと 30% です。買い切り 1 本 ¥250 なら手取り ¥175 → ¥212.5 で、**1 本あたり ¥37.5 の差**になります。年間収益 100 万ドル以下が条件なので、個人開発なら確実に条件内です。

### バナーが出ない真因は「ヘルプに載っていない 2 問」

公式ヘルプの手順はこうなっています。

> アカウントグループを作成 → バナー「確認して登録する」が出る → 規約に同意

アカウントグループを作っても、バナーが出ませんでした。探すのに数往復かかりました。

正解はここです。

```
関連付けられているデベロッパー アカウント → 右上「管理 ▼」→ 「アカウント グループを管理」
  → モーダルに未回答のラジオが 2 問
      ・お客様の法人は Google Play Console デベロッパー アカウントを他にも所有していますか?  → いいえ
      ・お客様のデベロッパー アカウントのアプリと類似するブランドのアプリを公開している
        他のデベロッパー アカウントはありますか?                                        → いいえ
  → 「保存」
  → ページ本体に「アカウント グループの設定を完了すると、15% のサービス手数料に登録できます」
     + 「確認して登録する」バナーが出る
```

この 2 問を明示的に回答して保存するまで、ページのどこにも登録導線も登録状況も表示されません。公式ヘルプ記事はこの中間ステップに触れていません（記事が 2021 年のもので、現行 UI と一致していない）。

> ヘルプに載っていない中間ステップがある前提で UI を疑う。

### さらに前提: 本人確認が完了していないと登録できない

もう 1 つ、**公式に記載がない依存関係**がありました。

本人確認が審査中で、画面最上部に「アプリを公開するには、デベロッパー アカウントの設定を完了してください」が出ている状態では、画面はこう見えます。

- お支払いプロファイルのバナーは**変化しない**（元々ここに同意導線はない）
- 「関連付けられているデベロッパー アカウント」ページを再読み込みしても**バナーが出ない**
- 右上「管理 ▾」の中身は「アカウントグループを管理 / 名前を変更 / 削除」の 3 つだけで登録導線なし

本人確認完了後に再訪すると出ます。売上はリリース後にしか発生しないので数日遅れても実害はゼロですが、ここで「自分の操作が悪いのか」と時間を使わないように。

### 登録完了の判定方法

これが唯一の確実な指標です。

「関連付けられているデベロッパー アカウント」ページ**下部**の `登録しているプログラムやサービス` に

```
- サービス手数料 15%   +  「規約を表示する」
```

が並びます。**登録前はこのセクション自体が存在しない**ので、「無い = 未登録」と判定してよいです。

### 回り道した調べ方（次はやらない）

参考までに、無駄だった調査経路を残します。

- 通知の「アカウントグループを管理」リンク → 同じページに戻るだけ
- 「リクエスト」タブ → リクエストなし
- アクティビティログ → 「アカウントグループを作成しました」だけで規約同意の行は無い
- Gmail → 関連メール 0 件

アクティビティログは全操作を記録していません（同日の電話番号確認が載っていなかった）。「行が無い = やっていない」の証明には使えません。

「アプリが 1 本も無いからバナーが出ない」という私の仮説も外れました。前提条件は「保留中のリクエストが無いこと」だけです。

### 2026-09-30 に日本の料率が変わる

これはリリース時期に直接効く話なので書いておきます。日本の Play サービス手数料体系は **2026-09-30** に変わります（EEA / 英国 / 米国は 2026-06-30 に適用済み、韓国は 2026-12-31）。

**1 回限りの購入の新料率:**

| | 標準 | 新プログラム登録時 | 年間収益 100 万ドルまで |
|---|---|---|---|
| 新規インストール | 20% | 15% | 10% |
| 既存インストール | 25% | 20% | 10% |

自動適用ではありません。公式に「新しいアプリ エクスペリエンス プログラムへの登録が必要」「プログラムの要件が増える見込み」と記載されています。**該当時期が近づいたら要件を再確認する**必要があります。

**EEA / 英国 / 米国は別料率**です（新規インストール = 10% + 請求手数料 5% / 既存 = 20〜25% + 5%）。米国配信があるならこの体系になります。15% 登録とは別の話です。

### 事前に直しておくこと: プロファイルの「氏名」

お支払いプロファイルの `氏名` が自動で組織名（`EXAMPLE WORKS`）になっています。

人名欄に屋号が入った状態で税務フォームを出すと、「正式な氏名がアカウント名と一致していない」で弾かれます（先行事例あり。個人申請者はお支払いプロファイルの氏名と一致が必要）。

→ 先に `氏名` を本名に直します。`組織名` は別欄で `EXAMPLE WORKS`（確認済みバッジ付き）のまま維持され、D&B 照合は壊れません。

### フォームは 1 時間で入力が消える・中断できない

材料を全部揃えてから始めてください。間違えると 15〜20 分やり直しです。

### 個人事業主の正解手順

| 質問 | 正解 | 理由 |

| 口座の種類 | 個人 | プロファイルが「組織」でも、米国税法上、個人事業主は独立した法的主体ではない。事業体を選ぶと Chapter 3 の事業体区分に該当なし + 法人番号を求められて詰む |
| 米国民 / 米国居住 | いいえ | |

| DBA または事業体 | `EXAMPLE WORKS` | Line 7（Reference number）に載り、プロファイル名との一致問題の橋渡しになる |

| 米国内で Google 向けの活動 | いいえ + 保証チェック | 「はい」にすると米国源泉の役務所得になり第7条の免税が崩れる |
| 税金に関するレポート | ペーパーレス | 4 年間取得可。Form 1042-S は 0% でも発行される |

### 承認結果と有効期限

即時承認されました。

| 項目 | 値 |
|---|---|
| ステータス | 承認済み |
| 有効期限 | 署名年の末日から 3 暦年 |
| 源泉徴収率 | 全所得タイプ 0% |

```
映画とテレビ番組        0%  申請済み   ← チェックしていないのに自動適用された
その他の著作権作品      0%  申請済み
サービス               0%  申請済み
```

有効期限を過ぎると 30% 源泉徴収に戻ります。カレンダーに入れておくべき項目です。

映画 / TV を意図的にチェックしなかったのに Google が自動で 0% にしました。日米租税条約第12条は映画フィルムのロイヤリティも含む使用料全般を免税にするため、条約テーブルから自動適用されたようです。根拠なくチェックを増やさない判断はコストゼロでした。

生成される PDF の Line 8（Date of birth）が空欄ですが問題ありません（Google はそもそも生年月日を聞いてこない）。Apple 側は `MM-DD-YYYY` で入力を求められるので、**両ストアで挙動が違います**。

**配信対象外の国の税務情報は提出しないこと**（私は台湾の税務情報を空欄のままにした）。

### 銀行口座 — 既定が「貯蓄」の罠

お支払いプロファイルが組織でも、受取口座は個人名義で登録できます。名義欄は半角カタカナの自由入力で、「プロファイル名と一致させろ」という制約は画面に一切ありません。

→ 屋号名義口座の開設（数日〜2週間の外部待ち）は発生しませんでした。事前に懸念したが不要でした。

最大の罠。

「アカウントの種類（受取人口座種目）」の既定が `貯蓄` になっています。

Google が英語の `Savings / Checking` から機械訳しているためです。日本の一般的な個人口座は「普通預金」で、「貯蓄預金」は別商品なので、直さないと振込が失敗します。

Apple 側は既定が「普通」でした。ストアごとに違うので、両方で確認してください。

### デポジット認証を忘れない

入力後、状態は `確認待ち` になります。

3 営業日以内に Google から少額デポジットが入金され、その金額を Play Console に入力して認証する手順が残ります。これが終わるまで売上受取は有効になりません。当日には完了しないので、忘れやすい項目です。

## デベロッパー名とウェブサイト確認

### 組織のウェブサイト確認は Search Console 経由

Play が TXT レコードを直接要求する方式ではありません。

```
1. Google Search Console でドメインの所有権を登録   ← これが前提
2. Play Console → デベロッパー アカウント → アカウントの詳細 → 「確認リクエストを送信」
3. Search Console の登録済み所有者に承認リクエストが飛ぶ → 承認
```

私のドメインは既に Search Console の「ドメイン プロパティ」（プロパティ名が `https://` 無し + 地球アイコン = 全サブドメインをカバーする一番強い形式）で登録済みだったので、TXT の追加も承認操作も不要で即座に「ウェブサイトを確認しました」に変わりました（所有者が Play の所有者と同一だったため自動承認）。

### デベロッパー名は「保存 ≠ 反映」

アカウントの詳細 → **「あなたの情報」タブ** → デベロッパー名が、**ストアでユーザーに表示される唯一の名前**です（アプリ名の下に出る）。

D&B の正規化で全大文字（`EXAMPLE WORKS`）になっていたので、正規表記（`Example Works`）に変更しました。保存すると Google 自身がこう出します。

> **新しいデベロッパー名は審査中です** — 新しい名前（Example Works）が承認されるまで、ユーザーには「EXAMPLE WORKS」と表示されます。

後日、承認されて表示が切り替わったかを確認する必要があります。私の場合は同日中に承認されました。

承認の判定は「このバナーが消えたかどうか」だけです。

アクティビティログや他のページの表示名は判定に使えません。それらは「送信した値」や内部表示なので、**保存した直後から新しい名前で表示されます**（承認されていなくても）。「もう変わっている」と誤読しやすい場所です。

同じページの「組織の詳細」（組織名 / D-U-N-S / 住所）も絶対に触らないでください。D-U-N-S 照合の対象です。デベロッパー名だけは別物で、変更しても照合は壊れません（画面に「組織の正式名とは異なる名前を指定できます」と明記あり）。

### 販売者の公開プロファイル

この画面の送信 = **販売 / 配布契約への同意**です。**この画面に銀行口座欄はありません**（税務情報 → 銀行口座は後続ステップ）。だから屋号口座がなくても先に進めます。

| 欄 | 入れた値 | 理由 |
|---|---|---|
| ○正式な事業名、連絡先、住所を使用する | チェック維持 | 自宅住所が Play 上で公開されるのは D-U-N-S を取った時点で受け入れた前提 |
| ウェブサイト | 事業者サイト（apex ドメイン）| アプリ個別のサブドメインではない。販売者単位のプロファイルで将来の全アプリが共有する |
| 販売する商品やサービス | コンピュータ ソフトウェア | 決済のマーチャントカテゴリ。ゲームではないので「おもちゃ、ゲーム、趣味」は不適 |
| カスタマー サポートのメール | `support@<自ドメイン>` | ユーザーに公開される |
| クレジットカード明細書の名前 | `EXAMPLE WORKS` | アプリ名ではなく屋号（販売者単位なので将来の全アプリの明細に出る）|

## アプリの作成と API 化

### 確定した不可逆な値

| | |
|---|---|
| パッケージ名 | `com.example.app`（AAB の中身を実測してから確定させた）|
| 無料 / 有料 | 無料（公開後は有料に変更不可。公開前は変更可）|
| アプリ署名鍵 | Google 生成（`CN=Android, O=Google Inc.`）|

### 「アプリ作成」と「内部テスターの指定」以外は全部 API でやれる

Play Console の操作はサービスアカウントで API 化できます。

```
サービスアカウント: play-publisher@example-project.iam.gserviceaccount.com
Cloud プロジェクト: example-project（Firebase と同一）
androidpublisher.googleapis.com を有効化
```

Play Console の「API アクセス」ページはもう存在しません。サービスアカウントは「ユーザーと権限」から人間と同じように招待します（2026 年時点）。Cloud プロジェクトのリンクは不要でした。

### Play Console のナビは移動しまくる → 画面を探すな、API で取れ

アプリ署名鍵の SHA を探して 3 回ナビを外しました。「テストとリリース → 設定 → アプリの署名」から「アプリの完全性」へ、さらに「Google Play による保護」へと 2 段階で移設されていました。

確実な取り方（UI 非依存）はこれです。

```python
api.generatedapks().list(packageName=PKG, versionCode=N)   # certificateSha256Hash が入っている
api.generatedapks().download_media(...)                    # アプリ署名鍵で署名された APK が落ちる
```

→ `apksigner verify --print-certs <apk>` で SHA-1 も SHA-256 も取れます。

`apksigner` は `JAVA_HOME` / `PATH` を通さないと "Unable to locate a Java Runtime" になります。

### 課金商品の登録 — 旧 API は新規アプリで使えない

旧 `inappproducts` API は新規アプリで 403 になります。

```
403 "Please migrate to the new publishing API"
```

新 API はこうです。

| 種別 | メソッド |
|---|---|
| 買い切り | `monetization.onetimeproducts` |
| 定期購入 | `monetization.subscriptions` |

- 買い切りは **`create` メソッドが無い**ので、`onetimeproducts.patch(..., allowMissing=True, updateMask="listings,purchaseOptions", regionsVersion_version="2022/02")` で create 相当を行う
- 定期購入は `subscriptions.create` + `basePlans`（`autoRenewingBasePlanType.billingPeriodDuration` = `P1M` / `P1Y`）

### 成功応答が嘘をつく — state は専用メソッドでしか変わらない

これは同じ日に 3 回踏んだパターンです。

```
patch で state: "ACTIVE" を送る
→ HTTP 200 が返る
→ 実際は DRAFT のまま
```

state の変更は**専用メソッド**でしかできません。

| 種別 | メソッド |
|---|---|
| 買い切り | `onetimeproducts.purchaseOptions.batchUpdateStates` フィールド名は `activatePurchaseOptionRequest`（`activatePurchaseOption` だと 400）|
| 定期購入 | `subscriptions.basePlans.activate` |

> 必ず list で再取得して `state=ACTIVE` を目視すること。

### API で作った定期購入の Grace Period は `P0D` だった

`gracePeriodDuration` が <strong>`P0D`（0 日）</strong>になっていました。Play の既定である 3 日ですらありません。

修正するには `basePlans` を丸ごと patch するしかないので、**read-modify-write** で行い、地域別価格の件数と `state=ACTIVE` が保持されていることを再取得で確認します（作り直すと価格が消えます）。

Play の grace period は離散選択ではなく **`P0D`〜`P30D` の範囲**でした（`P999D` を投げて `Grace period must be between P0D and P30D, inclusive` を得た）。Apple 側は 3 / 16 / 28 日の離散選択なので、**Play を Apple に寄せる**方向でしか揃えられません。

そもそも猶予期間が両 OS で非対称になるのは構造的な理由があります。

| | 猶予の実体 |
|---|---|
| iOS | アプリ側で実装できる（購入情報を読んで自前で猶予を持たせられる）|
| Android | 購入照会 API が期限切れ・返金済みを除外して返すので、アプリ側で猶予を持てない。猶予は Play Console の設定そのもの |

要するにPlay Console の設定を放置すると、同じ有料プランなのに OS によって猶予日数が違うという状態になります。既定値が入っていること自体を確認しないと気づけません（私の場合は API で作った商品が `P0D` = 0 日でした）。

### API でできないこと

- 内部テスターの個別メールアドレス指定。`Testers` スキーマは `googleGroups` のみ。→ 内部テスト → 「テスター」タブ → メーリングリストの作成 で作れる（アプリ単位の画面で完結）。**作るだけでは紐付かない**（チェック ON + 保存が必要）
- `edits.testers(internal)` は保存後も `{}` を返す。Console が「1 人」と表示していても API からは見えません（`Testers` は `googleGroups` しか持たないため Console のメーリングリストが載らない）。→ 「テスターが設定済みか」は Console の画面だけが正。`{}` を「未保存」と読むと誤診します。判定に使えるのは トラックの概要が「非アクティブ」→「有効」に変わること
- **コンテンツレーティング**（IARC 質問票）は完全に手作業。discovery を全走査して rating / questionnaire 系メソッドが 0 件であることを実際に試しました（「API が無い」を推測ではなく自分で見て言えるようにした）
- 一方 `applications.dataSafety`（POST）は存在します。データセーフティは CSV 文字列を渡せば API で登録できます（後述）

`androidpublisher` v3 の全 143 メソッドを走査した結果、「アプリのセットアップ」11 項目で API から扱えるのは 3 つだけでした: `applications.dataSafety` / `edits.details`（連絡先）/ `edits.listings`（掲載文）+ `edits.images`（掲載画像）。**残りは手作業確定**です。

## 署名鍵 — 3 種類を混同しない

ここは Apple と最も性質が違う部分です。

| 鍵 | 用途 |
|---|---|
| debug キーストア | エミュレータ / ローカル検証 |
| アップロード鍵 | 手元サイドロードの release APK / Play へのアップロード |
| アプリ署名鍵（Google 生成）| 本番配信に実際に署名する鍵 |

`assetlinks.json` / Firebase に登録する SHA は「アプリ署名鍵」が本番用です。アップロード鍵を入れても本番の App Links や Play Integrity は通りません。

さらにこれは Play Console 登録が前提なので、**D-U-N-S 待ちに依存します**（アプリ署名鍵は Play にアップロードするまで存在しない）。順序に注意してください。

### アップロード鍵の生成

| 項目 | 値 |
|---|---|
| 場所 | リポジトリ外（`~/.blc-release/` 配下・600）|
| alias / 方式 | RSA 4096 / SHA384withRSA |
| 有効期限 | Play 要件（2033-10-22 以降）を超える長さにする（validity 10000 日 = 2053 年）|

パスフレーズは `openssl rand -hex 24` で生成し、`keytool` へは argv でなく stdin で渡します（`-storepass` はプロセス一覧に残る）。`keytool` は `-storepass:file` / `:env` に**非対応**なので stdin が唯一の手です。

```sh
printf '%s\n%s\n\n' "$PASS" "$PASS" | keytool -genkeypair ...
#                             ^^^^ 3行目の空行 = keypass を storepass と同じにする
```

パスフレーズはキーストアと鍵で同一にしました。分けられる仕様ですが、「鍵ファイル + 1 つのパスフレーズ」が 1 つのアクセス単位なので、分けても実質的な強度は上がらず、取り違え事故のリスクだけ増えるという判断です。

保管はパスワードマネージャに鍵ファイル + パスフレーズの両方を入れました。クラウドストレージ単独では、鍵とパスフレーズが同じアカウント配下に揃ってしまうので不可としています（分けるなら「ストレージに鍵 / パスワードマネージャにパスフレーズ」）。

鍵の有効期限は Play の要件（一定の年月以降まで有効であること）を大きく超える長さにします。約 27 年にしました。短いと将来アップデートを出せなくなります。

Apple の配布証明書とは性質がまったく違います。Apple は Cloud Managed で秘密鍵がローカルに無く「紛失」の概念がありませんが、Android のアップロード鍵は紛失すると Play サポートにリセット依頼が必要です。

### release ビルドの実際の値と誤っていた前提

- **署名確認**: APK は `apksigner verify --print-certs`、AAB は `jarsigner -verify`（AAB は APK ではないので `apksigner` が使えない）
- `enableV1Signing = true` は効かない —— AGP は minSdk 26 では v1 を付けません（`v1 scheme: false` / `v2: true`）。minSdk 26 は v2 で足りるので実害はないが、「保険が効いていない」ことは知っておくべき
- 「デバッグメニューは R8 が完全除去する」は再検証で否定された —— ナビゲーションに無条件登録していると R8 は到達可能と判断し、画面のコードと日本語リテラルは release の dex に残ります。判定は dex 内の文字列ではなく「設定画面に入口が出るか」で行う（入口側が `BuildConfig.DEBUG` ガードなら実害なし）
- logcat の `Not starting debugger since process cannot load the jdwp agent` が「release が debuggable でない」証拠になる
- R8 による破壊は実行時にしか出ません。エミュレータに入れて起動するまでが検証です。debug 版とは署名が違うので `adb uninstall` が必須

### クラッシュレポートは「最初の 1 件が届くまで有効化されない」

Console を探しても解決しない類の罠でした。

クラッシュレポート機能に「有効にする」ボタンはありません。SDK から最初のレポートが届いた時点で自動的に有効化される仕様なので、Console 側の操作では永久にオンボーディング画面のままです。

 リリース前に意図的にクラッシュを 1 件送る手段が要ります。 Debug メニューにテストクラッシュの項目を作っていなかったので、本物の未捕捉例外でしか検証できませんでした（強制終了系のコマンドでは拾われない）。

しかももう 1 つ、**シンボル化の配線**です。

| | シンボル化 |
|---|---|
| iOS | dSYM のアップロードをビルドフェーズに配線しないと届かない。dSYM は生成されているのに送っていない状態になり、スタックトレースがアドレスのままになる |
| Android | 難読化するならマッピングファイルのアップロードを有効にする（レポートにマッピング ID が紐づいているかで確認できる）|

「SDK を入れた」と「クラッシュがシンボル化されて読める」は別です。TestFlight / 本番で一番必要な場面で機能しないので、リリース前に実クラッシュ 1 件で通しておくべきでした。

### release ビルドに Debug 用の検証ライブラリが同梱される

クライアント認証（App Check）のライブラリで踏んだ非対称です。

| | Debug プロバイダの扱い |
|---|---|
| iOS | `#if DEBUG` でコンパイル時に排除できる = release バイナリに存在しない |
| Android | 依存の宣言方法によっては release にも入る（実行時の分岐で使われないだけ）|

**セキュリティ実害はありません**（release では起動できない）が、出荷バイナリに未使用の検証コードが残るのはレビュー上の常套フラグです。依存を debug 限定に降格するには初期化処理のソースセット分割も必要でした（宣言を移すだけだと release のコンパイルが通らない）。

### 「ログが本番ビルドに残らない」は前提が誤りだった

私のログ実装は意図的に release でも logcat へ本文を出す設計でした（クラッシュレポート側へは分類とレベルだけ送り、本文は送らない = PII 混入を避ける）。

「release ではログが出ない」という思い込みで検証手順を組むと、実機調査ができなくなります。正しい検証は「ログ出力が自前のラッパー経由に統一されているか」でした（`println` / `System.out` / 素の `android.util.Log` 直呼びが 0 件であること）。

## AAB とリリースビルド

### APK 直入れでは検証できない設定がある

`assembleRelease` の APK をエミュレータに入れるだけでは不十分でした。

```kotlin
bundle { language { enableSplit = false } }   // AAB 配信時のみ効く
```

このようなバンドル設定は AAB 経由でしか検証できません。なので AAB → `bundletool` → 分割 APK という、Play と同じ経路で確認しました。

試した結果確認した項目です。

- アップロード鍵で署名済み（`jarsigner -verify` = `jar が検証されました`）
- 言語分割が無効（`BundleConfig` が `LANGUAGE` + `negate: true`・ja / en 両方同梱）
- AAB の `minSdkVersion` は 26。`dumpsys package` が返す `minSdk=32` は bundletool が端末向け分割に付ける値なので、こちらを見て「minSdk が上がっている」と誤読しないこと
- `DEBUGGABLE` 無し・設定画面に Debug 入口が無い
- App Links がオンデバイスで `verified`（`pm get-app-links`）。assetlinks.json が HTTP 200 で SHA-256 が 3 本（debug / アップロード鍵 / **アプリ署名鍵**）入っていること

この検証で「release ビルドだけ初回起動が落ちる」バグを見つけました。debug では出ません。release ビルドを実際に起動するまでは何も確かめられていないということです。

### AAB の native シンボル警告は構造的に消せないことがある

アップロード時に「native デバッグシンボルがありません」という警告が出ました。調べると、対象の `.so` は**すべてライブラリのプリビルド**で、自分のプロジェクトは NDK コードを一切持っていませんでした。

`debugSymbolLevel` を足しても出せるシンボルが無いので消えません。そして、直すためにビルドし直すとビルド番号が動いて iOS と揃わなくなるので、私は触りませんでした。**警告と実害を切り分けて判断する**場面です。

## 「アプリのセットアップ」11 項目 + 隠れた 10 個目

### ダッシュボードが `1/11 完了` と言っていた

これは完全な追跡漏れでした。私のトラッキング Issue は 11 項目のうち「コンテンツのレーティング」1 件しか追えていませんでした。ダッシュボードが `1/11 完了` と表示していることを指摘されて発覚しました。

11 項目すべてが公開の前提条件です。

| # | 項目 | 私の回答 |
|---|---|---|
| 1 | プライバシー ポリシーを設定する | URL を設定 |
| 2 | ログインの詳細 | 審査用アカウントの認証情報が必須（後述）|
| 3 | 広告 | 広告なし |
| 4 | コンテンツのレーティング | IARC 質問票（後述）|
| 5 | ターゲット ユーザー | 13〜15 / 16〜17 / 18歳以上 の 3 つ（= 13+）|
| 6 | データ セーフティ | CSV 経由で登録（後述）|
| 7 | 行政アプリ | 該当なし |
| 8 | 金融取引機能 | 該当なし |
| 9 | 健康 | 該当なし |
| 10 | アプリのカテゴリと連絡先 | ライフスタイル / アプリ |
| 11 | ストアの掲載情報 | 画像 + 掲載文（後述）|

**依存は `2 → 5 → 6` の一本道**です。ターゲットユーザーが未設定だと、データセーフティが赤エラーで送信できません。これを「独立に進められるだろう」と推測して外しました。画面に書かれている依存関係を、推測で上書きしてはいけません。

### 判断が要った 3 項目

- **ターゲットユーザー**: 12 歳以下を 1 つでも選ぶと Families ポリシーが適用され、要件が激増します（Families 向け広告 SDK 制限 / Teacher Approved 審査 / 追加のプライバシー要件）。13+ で足りるなら 13+ にする
- **金融取引機能**: アプリ内課金は金融取引機能に当たりません。設問は銀行・ローン・送金・暗号資産・株取引・保険・信用調査・金融アドバイスを提供するかを聞いています。紛らわしい「特典、ポイント、マイレージ」も、ポイント制度がなければ該当なし
- **健康**: 「健康」というカテゴリのデータをユーザーが入力できても、**計測 / 管理機能がなければ該当なし**。健康系権限 0 件 / Health Connect・`BODY_SENSORS`・`ACTIVITY_RECOGNITION` の参照 0 件を試して裏付けました

### 「アプリのカテゴリと連絡先」の外部マーケティング

「外部マーケティング」は ON のままが正解です。これは Google が Play 以外でアプリを宣伝してよいかの設定で、「アプリ内に広告なし」の申告とは**無関係**です。切るとインストール機会を捨てるだけで、変更の反映に 60 日かかります。

### 隠れた 10 個目の必須申告: 「広告 ID」

これは PLAY-1〜11 のチェックリストに現れません。「アプリのコンテンツ → 要注意」に残り続け、画面にこう書かれています。

> この申告を完了するまで、Android 13 をターゲットとするアーティファクトを含むリリースは公開できません

= **リリースの必須要件**です。

そして、この設問の答え方に罠があります。

「自分は宣言していないから いいえ」は根拠になりません。設問は「広告 ID を使用している SDK をアプリがインポートする場合も含む」で、画面自身が SDK のライブラリマニフェストから `AD_ID` 権限が自動マージされると警告しています。

判定は必ずマージ後のマニフェストで行います。

```
app/build/intermediates/merged_manifest/release/.../AndroidManifest.xml
  → AD_ID / ACCESS_ADSERVICES_* が 0 件か
AAB の base/manifest/AndroidManifest.xml も確認
```

さらに逆方向の罠。

> 「はい」と宣言したのに、マニフェストに `AD_ID` を含まないリリースはブロックされます。

言い換えると権限を意図的に外しているなら「いいえ」が唯一整合する答えです。「安全側に倒して はい にしておく」は逆効果で、公開が止まります。

「収集をオフにする設定」では権限宣言は消えません。

アナリティクス SDK には「広告 ID の収集を無効にする」設定値がありますが、これは収集を止めるだけで、マニフェストにマージされる権限宣言は残ります。その状態で「収集しない」と申告すると、申告とマニフェストが食い違い、審査指摘の要因になります。

→ 権限そのものを `tools:node="remove"` で除去して、release / debug の両方でマージ後マニフェストに 0 件であることを自分で試す必要がありました。

### dex にライブラリが残るのは欠陥ではない

余談ですが、この調査中に「アナリティクス SDK が広告 ID 取得クラスを依存に持っている」ことを見つけ、除外しようとしました。これは失敗しました。

```
> Task :app:minifyReleaseWithR8 FAILED
ERROR: R8: Missing class com.google.android.gms.ads.identifier.AdvertisingIdClient
  (referenced from: ...measurement.internal...)
```

- **リフレクションではなく直接参照**されている
- **`-dontwarn` も採れない**: 実行時に `NoClassDefFoundError` になり得る。これは `Error` なので SDK 側の `catch (Exception)` では拾われない
- iOS 側にある「アナリティクスのコア分離ライブラリ」に**Android の対応物は存在しない**

Android の opt-out の機構はそもそも違って、`AD_ID` 権限の除去そのものです（マニフェストで `tools:node="remove"`）。dex にクラスが残ることは想定内で、欠陥ではありません。iOS と機構が違うことを「非対称だから直すべき」と誤読しかけました。

## コンテンツレーティング（IARC）

### ナビが分かりにくい

**アプリ単位**のメニュー → モニタリングと改善 → ポリシーとプログラム → アプリのコンテンツ → コンテンツのレーティング

`ポリシーとプログラム` はトップレベルではなく `モニタリングと改善` の配下です。**アカウント単位のメニューには存在しません**（`設定 → ライセンス テスト` などとは階層が違う）。

### カテゴリ選択は「主な目的」で決まる

選択肢は 3 つだけです。

| 選択肢 | 判定 |
|---|---|
| ゲーム | 非該当 |
| ソーシャルまたはコミュニケーション | 非該当。説明が「このアプリの主な目的は、人と出会ったり、コミュニケーションを取ったりすること」（例: SNS / メッセージングアプリ）|
| その他のすべてのアプリの種類 | ○これ。説明に「ライフスタイル アプリ」「ユーティリティ、ツール」が明記 |

「社交機能があるか」ではなく「主な目的か」で選びます。当初「UGC を聞かれるカテゴリを選ぶべき」と考えましたが基準を誤読していました。UGC は選んだ後の設問で正直に答えれば足ります。

メールアドレスはアプリ固有の連絡先を入れます（販売者プロファイルの `support@` は全アプリ共通のもので、ここではない）。

### アルコールの懸念は「設問の文言」で解決した

このアプリには「やりたいこと」の定番データが約 490 件同梱されており、そのうち約 10 件が酒に言及します（ワインテイスティング / 蒸溜所見学 / クラフトビール / 居酒屋、うち 1 件は禁酒）。iOS 側は「アルコール該当なし」で申告していたので矛盾を心配しました。

質問票は「言及」を聞いていませんでした。

> アプリでは、一般的に年齢制限が適用される商品や行為（タバコ、アルコール、銃器、ギャンブルなど）の**宣伝または販売に焦点を当てて**いますか?

→ **いいえ** が正当です。**iOS の再申告も不要**でした（もし「言及」基準だったら Apple 側は "Infrequent/Mild Alcohol References" で 4+ → 13+ に上がっていた）。

**設問の文言を精読するだけで判断が決まる**ことがあります。

### 全設問と答えの根拠

| 設問 | 答え | 根拠 |
|---|---|---|
| ①同梱アセットにレーティング関連コンテンツ（性・暴力・言葉）| いいえ | 該当なし |
| ②音声/SMS/画像・オーディオを共有して他ユーザーと交流 | はい | 公開・フレンド公開のカバー画像が他ユーザーに見える + 共有リストの共同編集 |
| ②-1 UGC が主要コンテンツソースか | いいえ | 主は自分のリスト + 同梱の定番データ |
| ②-2 ヌード / ②-3 露骨な暴力の公開を許可 | いいえ | 利用規約で明示禁止 |
| ②-4 ブロック機能 | はい | 審査要件として後から実装した（[全工程まとめ](/engineering/app/personal-app-cross-store-release-full-journey/)参照）|
| ②-5 報告機能 | はい | 同上 |
| ②-6 チャットモデレート | いいえ | チャット自体が無い |
| ②-7 対話を招待された友人のみに制限できる | はい | これが唯一効いた緩和要素 |
| ③オンラインコンテンツを呼び物 / 宣伝 | いいえ | 例示は動画配信 / 音楽配信 / 生成 AI などの third-party カタログ |
| ④年齢制限製品の宣伝・販売に焦点 | いいえ | 上記 |
| ⑤現在地を他ユーザーと共有 | いいえ | 位置情報 API 不使用・画像は EXIF / GPS 除去済 |
| ⑤デジタル商品購入 | はい | サブスク + 買い切り |
| ⑤ルートボックス / 運任せの購入（購入 = はいで出る追加設問）| いいえ | 確率要素ゼロ |

結果はこうなりました。

| 地域 / 機関 | 評価 |
|---|---|
| 北米 ESRB | E（全ユーザー対象）|
| その他の地域 IARC Generic（= 日本）| 3 歳以上 |
| PEGI / USK / ロシア / 韓国 | 3 / 0 / 3+ / 3+ |
| ブラジル ClassInd | 14 歳以上 |

**ブラジルの 14 は無視して正しい**です（交流機能があると機械的に 14 を付ける機関。配信は日本 + 米国のみ）。

**日本に CERO が出ないのは正常**です（CERO は IARC 非加盟 = 家庭用ゲーム専門。日本は IARC Generic が適用される）。

概要画面に出る**韓国の警告**（「19 歳未満に適さない**ゲーム**は GRAC のレーティングが必要」）はゲーム向けの定型文なので、非ゲームなら無視してよいです。

保存時の「審査のため送信できるようになります」は送信可能になるだけで、審査には出ません。

### 再回答はアンケート全体をやり直す形になる

報告 / ブロック機能を後から実装したので、②-4 / ②-5 を「いいえ」→「はい」に変えるために再回答しました。

カテゴリ選択 → アンケート → 概要の 3 ステップを最初からやり直しで、前回の回答は一切引き継がれません。

実際に「デジタル商品を購入できますか」を いいえ にしかけました（前回は はい）。課金アイテムを 8 種登録済みなので実態と矛盾します。

> 再回答するときは、前回の回答表と 1 問ずつ突き合わせること。全問入れ直しになるので、記録がないと必ずどこかがズレます。

結果は**全機関で前回と同一**でした（ブロック・報告は緩和要素なので上がらない）。**ブラジルの 14+ も下がりませんでした**（「ブロック・報告を入れれば下がるかも」という私の予想は外れ）。

### 送信済みかどうかの判定

「要注意」/「対応済み」タブで判定できます。未送信なら「要注意」側に残ります。Play API にコンテンツレーティングの読み書き口はないので、確認は画面でしかできません。

## ログインの詳細 = 審査用アカウントは必須

これは一度誤った答えを入れて、後から気づきました。

最初の答案は「サインインは任意の Google アカウントで行えます。専用のテストアカウントは不要です」でした。Play では通りません。

「ログイン情報を追加」ダイアログに明記されています。

> 審査担当者は、アプリにアクセスするため、アカウントを作成したり、**担当者固有の既存アカウントを使用したり**、無料試用を利用したりすることはできません。

→ 審査専用アカウントの認証情報を渡す必要があります。設問は「一部または全部の機能が制限されている」を選ぶのが正しいです。

### 最下部のチェックボックスが律速になる

> この申告に含まれるログイン情報を使用すると、このアプリ内のすべての機能とコンテンツ（プレミアム コンテンツや有料コンテンツを含む）を制限なくご利用いただけます。

- 有料プランを持たないアカウントで ON にすると虚偽申告
- OFF にすると「有料コンテンツを審査できない」申告（画面に「審査できないとアプリが削除される可能性」と警告が出る）

私のアプリは課金の権利判定を**サーバー権威**にしていたので、DB を直接書き換えて Pro にする逃げ道もありませんでした。

→ 審査アカウントで実際にテスト購入してから ON にするのが唯一の正解です。

ライセンステスターに審査アカウントが入っていないと、テスト購入自体ができません。私のライセンステスターのメーリングリストは開発者本人 1 名だけだったので、先に追加が必要でした。

後日この前提が崩れました。テスト購読は寿命が短いので（後述）、約 2.5 時間で失効してチェックボックスの申告が偽に戻りました。最終的に「審査アカウントにはサーバー側で恒久的に権利を付与する」実装を追加して解決しています。

### その他の罠

- **「その他の情報」は 500 文字上限**。最初の文面は 595 字で弾かれました
- ダイアログの「追加」だけでは保存されず、画面下部の「保存」も必要
- 項目名は「ログインの詳細」。Play Console に「アプリへのアクセス権」という項目はありません（私が誤った名前で手順を案内しました）。ナビは モニタリングと改善 → ポリシーとプログラム → アプリのコンテンツ → ログインの詳細

審査アカウントのパスワードは会話 / Issue / PR に絶対に書きません。Play Console へは人間が直接入力します。

審査アカウントの表示名も確認してください。検証用に付けていた名前（`KeepThisName`）がそのまま残っていて、**レビュアーが見る名前だった**ことに後から気づいて `Reviewer` に直しました。

## データ セーフティ

11 項目のうち**一番重いのがこれ**です。Apple の App Privacy と一致させる必要があります。

### CSV エクスポート → 埋める → CSV インポートが正解

画面で 1 項目ずつ入れると膨大なので、`CSV にエクスポート` → 埋める → `CSV からインポート` が最短です（私の場合 782 行のうち有効 59 行）。

### 踏んだ罠

- `PSL_DATA_USAGE_EPHEMERAL` は空欄不可で `false` の明示が必要。最初のインポートはこれで弾かれました
- 依存は `ログインの詳細` → `ターゲットユーザー` → `データセーフティ` の一本道（対象年齢層が無いと赤エラーで送信できない）
- `applications.dataSafety` は POST のみで GET が無いので、照合手段は **Console のプレビューだけ**です。プレビューと CSV を 1:1 で照合しました（9 種すべて表示 / 全部「オプション」/ 第三者共有なし）

### 申告内容を実装から起こす

Apple 側と同様、マニフェストの宣言を信じずに実装から起こしました。報告・ブロック機能を追加した後は、次の 2 項目が追加になりました。

- アプリのアクティビティ → **その他のユーザー生成コンテンツ**（報告の自由記述）
- 個人情報 → **ユーザー ID・名前**（報告・ブロック対象）
- 用途に 不正行為の防止・セキュリティ・コンプライアンス を追加

を足す必要がありました。機能を追加したらデータセーフティも更新する——この連動を忘れると申告が古くなります。

## ストア掲載画像（PLAY-11）

### iOS のスクリーンショットは Play に流用できない

Play は「長辺 ≤ 短辺 × 2」という比率制約があります。

| 端末 | 解像度 | 比率 | 可否 |
|---|---|---|---|
| iPhone の大画面 | 1320×2868 | 2.17 | 不可 |
| 手持ちの AVD | 1080×2424 | 2.24 | 不可 |
| 新規作成した AVD | 1080×2160 | 2.00 | ○|

AVD を作り直しました。

| AVD | 解像度 | 用途 |
|---|---|---|
| スマホ用 | 1080×2160（ちょうど 2.00 / density 440）| `phoneScreenshots` |
| 7 インチ用 | 1200×1920（density 240）| `sevenInchScreenshots` |
| 10 インチ用 | 2560×1600 | `tenInchScreenshots` |

`avdmanager` は `JAVA_HOME` を export しないと "Unable to locate a Java Runtime" になります。作成後は `config.ini` の `hw.lcd.width/height/density` を直接書き換えます。

投入結果は最終的にこうなりました。

| 種別 | 枚数(ja/en) | サイズ |
|---|---|---|
| `icon` | 1 / 1 | 512×512 透過なし |
| `featureGraphic` | 1 / 1 | 1024×500 透過なし |
| `phoneScreenshots` | 6 / 6 | 1080×2160 |
| `sevenInchScreenshots` | 5 / 5 | 1200×1920 |
| `tenInchScreenshots` | 5 / 5 | 2560×1600 |

### ステータスバーは SystemUI demo mode で整える

素で撮ると時刻がバラバラ + エミュレータのデバッグアイコンが写ります。

```sh
adb shell settings put global sysui_demo_allowed 1
adb shell am broadcast -a com.android.systemui.demo -e command enter
adb shell am broadcast -a com.android.systemui.demo -e command clock -e hhmm 0930
adb shell am broadcast -a com.android.systemui.demo -e command notifications -e visible false
```

アプリの表示言語切り替えは `adb shell cmd locale set-app-locales <pkg> --locales en-US` が便利です（端末再起動不要・`localeConfig` が無くても効く）。

### 掲載用データの投入で踏んだ罠

デモデータを投入して撮影する仕組みを作ったのですが、そこで踏んだものです。

1. 認証状態のリフレッシュより後にデータ投入を呼ぶ。先に呼ぶとモックのサインイン状態が戻され、ソーシャル系のタブが鍵アイコンになる
2. ローカル DB に入れただけでは起動時の同期処理に掃引される。権威側のスナップショットに積む必要がある
3. **撮影を邪魔するゲートを全部畳む**（オンボーディング完了 / 規約同意 / 通知許可の要求済みフラグ / 各種初回カード）
4. タブレットは 2 ペインなので素で撮ると右ペインが「◯◯を選択」の空状態になる。ディープリンクや 1 件タップで埋める。一覧と詳細が同じ絵になるスクショは入れない
5. 英語撮影でモックデータだけ日本語のままになる（言語固定のモックがある）。撮影用に英語分岐を入れる

### 投入 API

```python
edits().images().upload(packageName, editId, language, imageType, media_body)
```

- 先に `deleteall` しないと追加になり、古い絵が混ざります
- `imageType` は `icon` / `featureGraphic` / `phoneScreenshots` / `sevenInchScreenshots` / `tenInchScreenshots`
- 確認は必ず新しい edit を作って `images().list()`。commit しただけでは証拠になりません

撮影用の資材（写真素材とライセンス台帳）を一時ディレクトリに置くのは危険です。消える寸前でリポジトリ管理に移しました。CC0 / PD 写真とライセンス台帳は失うと出所を再証明できません。

ただし その素材が release ビルドに同梱されないようにする必要があります（私は iOS 側は「バンドル外に置いてインストール後にコピー」、Android 側は「debug ソースセットから参照」で実現し、release の成果物に掲載写真 0 件・撮影用文言 0 件を自分で確認しました）。

## 課金テストとライセンステスター

### 実課金ゼロの担保は購入シート自身が言い切る

Console を見に行く必要はありません。タップ前にこれを読むのが唯一必要な安全確認です。

- Play 定期購入: 「Test card, always approves」/「This is a test subscription… You will not be charged.」/ 価格が **`¥280/5 min`** のように表示される
- Play 買い切り: 「This is a **test order**, you will not be charged.」

表示が `¥2,800/30 min` のようになるのは、テスト定期購入の周期が短縮されているためです。バグではありません。

### テスト購読の寿命が検証の順序を決める

| | 周期 | 打ち切り |
|---|---|---|
| Play テスト定期購入 | 5 分 | 最大 6 回で自動キャンセル ≈ 30 分 |
| iOS Sandbox 月額 | 5 分 | 12 回 |
| iOS Sandbox 年額 | 1 時間 | 12 回 |

→ 長く Pro 状態を保ちたい検証は先に年額へ上げてから回します。逆に「Pro を消したい」ときは **Play 側を解約**すると次の 5 分境界で切れます。

### 「購入ゼロの状態」を Android では作れなかった

「権利を 1 つも持たないときの表示」を検証しようとして詰まりました。

Play Billing はストアのプロフィール切り替えに追従しません。アカウントを切り替えても、アプリをインストールしたアカウント（= ライセンステスター）の購入を返し続けます。

切り替え自体は成立していて（Play の初回オンボーディングが出て購入履歴も空になる）、それでも購入照会の結果は元のアカウントのままでした。購入ゼロの状態が作れないので、その分岐を実機で見られません。

実機で見たい場合は、Play Console でテスト購入を払い戻して購入ゼロにする必要があります。代わりに **iOS 側で同じ条件を作って検証**しました（[App Store Connect 編](/engineering/app/app-store-connect-review-submission-notes/)の Sandbox 購入履歴クリアを使う）。分岐そのものはユニットテストで固定しています。

### ライセンステストは Play Integrity をサポートしない

Console の画面に明記されています。

> ライセンス テストは Play Integrity API または自動保護をサポートしていません

 sideload した版では Play Integrity が成立しません（App Check を使っているなら、トークンが出ません）。Play Integrity 系の検証は、内部テストトラック経由でインストールした版で行う必要があります。

ライセンステスターは、公開に使うアカウント（Console オーナー）は常にテスター扱いですが、明示チェックは無害なので入れておきます。

### クライアント認証を「強制」にする順序を間違えると課金が全滅する

課金のサーバー検証を実装したあと、ログにこう出ていました。

```
Callable request verification failed: AppCheck token was rejected.   WARNING
課金権利を検証しました                                                INFO
```

トークンは拒否されているのに、処理はそのまま成功していました。強制モードが未設定なので**警告止まり**だったのです。

→ つまり強制モードにした瞬間に、課金検証が全呼び出し失敗します。

逃げ道がありませんでした。エミュレータで通すためのデバッグ用トークンは debug ビルド専用で、release ビルドは debug プロバイダを持たないので、Play 配信の release 版を載せたエミュレータでは使えません。

→ 順序は「課金の実機 E2E が全部通ってから、強制モードに切り替える」にしました。逆順だと「購入検証が失敗しているのは課金の実装のせいか、認証のせいか」を切り分けられません。

### 「Play 配信で検証した」を名乗る前に installerPackageName を見る

これは検証の前提が崩れていた実例です。

エミュレータに入っていたビルドは、`installerPackageName=null` = `adb install` で入れたサイドロード版でした。Play 配信版は**Play アプリ署名鍵**で署名されるため、ローカル鍵で入った APK への上書き更新は**構造的に不可能**です。

```
PackageInstallerSession: Marking session ... as failed:
  INSTALL_FAILED_UPDATE_INCOMPATIBLE: Existing package signatures
  do not match newer version; ignoring!
```

Play ストアの UI 上はただの `Can't install` としか出ないので、`adb logcat | grep INSTALL_FAILED` を見ないと原因に辿り着けません。

判定は必ずこれです。

```sh
adb -s <serial> shell dumpsys package com.example.app | grep -E 'versionCode|installerPackageName'
#  installerPackageName=com.android.vending  ← これが無ければ Play 配信ではない
```

エミュレータのスナップショットが巻き戻ったあとは特に疑ってください。巻き戻り先がサイドロード時代なら、以後の「Play 配信で検証した」記録は全部前提が崩れています。

### debug ビルドと Play 配信 release で挙動が変わる 3 点

私の構成では以下が違いました。似た構成なら参考になると思います。

1. 画像ストレージが InMemory でクラウドに上がらない（= 画像がからむ検証は Play 配信でしか成立しない）
2. Play 接続が解決せず、課金権利のサーバー検証が 1 度も呼ばれない
3. **外部 API 連携がモックに差し替わる**

逆に、内部状態を読む必要がある検証は Play 配信版では不可能です（Play ストア入りイメージは `adbd cannot run as root in production builds`・release は `run-as` 不可）。debug ビルド + 本番バックエンドに繋ぐトグルに切り替えて直読みしました。

### RTDN（サーバー通知）— アプリを開かずに反映されるか

サブスクの更新 / 失効をサーバーで受けるには Pub/Sub 経由の RTDN を設定します。ここで踏んだものです。

- Play Console に登録するトピック名はフルパス必須
- 「通知の内容」のラジオは、買い切り商品があるなら「定期購入、取り消し済みの購入、すべての 1 回限りのアイテム」側を選ぶ（旧 UI の「無効な購入に関する通知」チェックはこのラジオに統合されていた）
- テスト通知が Cloud Run 手前の 401 で弾かれた。カスタムのサービスアカウントを使うと、デプロイツールが Cloud Run サービスへの `roles/run.invoker` を自動付与しません。付与したら再配達が IAM 伝播後に自動で通りました（テスト通知の再送は不要）
- テスト通知は「Play Console → Pub/Sub」の経路しか検証しません。実購入通知が届くことの確認は別に必要です

自分で動かして分かった重要な挙動です。

購入直後の通知は `unknown-user` にしかなりません（まだ購入とユーザーの紐付けがサーバーに無いため。設計どおり）。「サーバーが解決できた」状態を観測するには 2 回目以降の通知を待つ必要があります。

アプリを完全終了したまま自動更新を待ったところ、サーバー側で権利が更新されました。= **「アプリを開かないと反映されない」は誤り**で、RTDN を入れた意味そのものが実証できました。逆に Play の定期購入を解約すると、期限の数秒後にサーバー側の権利が失効します（両 OS のアプリを開いていない状態で）。

## 提出 — Console 操作が必須なものが 3 つある

Play の提出は API だけでは完結しませんでした。

### API 不可だった 3 つ

1. **国 / 地域の選択** — `edits.countryavailability` は**読み取り専用**。`releases[].countryTargeting` は `Country targeting is only supported for staged releases.` で拒否される
2. **サードパーティのアプリストア設定**（デベロッパーアカウント単位）— 米国の裁判所命令対応で 2026-07-22 に開始された設定。掲載情報（名前 / アイコン / 説明 / スクショ / 動画）を米国のサードパーティ Android ストアにも載せるかを選ぶ。**放置すると自動公開されます**（私の場合、一度発動していた）
   - 裁定は 「いずれのサードパーティのアプリストアでも公開しない」。理由は 2 つで、①ダウンロードは Play 経由で手数料も同じなので金銭的メリットが無い ②Play のポリシーが適用されないストアに、UGC を扱うアプリの掲載情報を出すリスクだけが残る
   - 「メリットが無いから放置」ではなく「明示的に選ぶ」必要があります（放置＝自動公開なので）
3. **リリース作成 → 審査送信** — `edits.commit` が `Changes are sent for review automatically. changesNotSentForReview must not be set.` を返す = このアプリでは「審査に出さずに commit」ができない

### Play の初回リリースは「承認 = 自動公開」ではない

これは当初、私が誤って断定していた点です。

ダッシュボードのチェックリストに 「リリースを審査のために Google に送信する」と「Google Play にアプリを公開する」が別ステップとして並びます = **承認後に公開操作が必要**です。

私が根拠にした「管理対象の公開: オフ」のツールチップは

> **アップデート**は承認されるとすぐに自動的に公開されます

でした。**初回には当てはまりません**（そう書いてあるのに読み飛ばしました）。

「管理対象の公開」は最初「現在、オンにすることはできません」と表示されていましたが、リリースと国 / 地域が揃った後は ON にできました。設定できない項目を「非対応」と決めつけないようにしましょう。

### 「ストアへの事前通知」の窓口ができていた

法令対応で「利用規約やプライバシーポリシーの重要な変更を、事前にストアへ通知する」義務があります（詳しくは[全工程まとめ](/engineering/app/personal-app-cross-store-release-full-journey/)に書きました）。

私は当初「ストアに『通知する』API も画面も存在しない」と判断して、代わりに**変更の側を凍結する**方式を採りました。

ただし調べ直したら、Play Console に「Age Signals」のセクションができていて、アプリの更新なしに重要な変更をストアへ通知できるようになっていました。前提が変わっていたので、方針の記録も更新しました。

> 「窓口が無い」と判断したものは、時間が経つとできていることがあります。半年〜1年で再確認する価値があります。

### 「一時的なアプリ名 `com.example.app (unreviewed)`」は仕様

ダッシュボードに「一時的なアプリ名は `com.example.app (unreviewed)` です」と出ます。

これは セットアップ完了 + 審査通過までの間、内部テスターのダウンロード時に Play が自動生成した名前を出すもので、`android:label` の表示名不具合とは無関係です。**審査が通れば正しい名前になる**ので追わなくてよいです。

```
□ 掲載用の写真素材と台帳をリポジトリ管理にする（release には入れない）

【課金】
□ 旧 inappproducts は使えない（新 monetization API）
□ state は専用メソッドでしか変わらない（HTTP 200 を信じない）
□ API で作った定期購入の grace period が P0D になっていないか確認する
□ ライセンステスターに審査アカウントを追加する
□ テスト購読の寿命（5分×6回）を前提に検証順序を決める
□ installerPackageName=com.android.vending を毎回確認する

【提出】
□ 国 / 地域の選択は Console 手動
□ サードパーティのアプリストア設定を明示的に選ぶ（放置で自動公開）
□ 初回リリースは「承認 = 自動公開」ではない。公開操作が別にある
```

Play 側で一番の学びは、「公式ヘルプに書かれていない前提と中間ステップがある」ことでした。15% 手数料のバナーも、本人確認の必要書類も、依存関係の一本道も、ヘルプ記事だけでは辿り着けません。画面に出ていない = 自分の操作が悪い、とは限らない——ここで消耗しないだけでかなり楽になります。

## はじめに

個人開発の iOS / Android アプリ **Bucket List Commit** を App Store と Google Play へ同時提出しました。この記事はその**アプリ本体以外に用意が必要だったもの**——公式サイト・ドメイン・メール・OAuth・バックエンド——の記録です。

ストアに出すには、アプリ本体のほかに「事業者としての面」が必要になります。ここも実装とは関係ないのに、アプリが直接開く URL があるので後から変えられないという厄介さがあります。

さらに厄介なのが、この領域はほぼ全部「推測で外した」ことです。リダイレクトの書き方、メールの制約、設定を API でやってよいかどうか——**実測しないと分からないものばかり**でした。

> ストア側の手順は別記事です。[App Store Connect 編](/engineering/app/app-store-connect-review-submission-notes/) / [Google Play Console 編](/engineering/app/google-play-console-review-submission-notes/) / [事務手続き編](/engineering/app/indie-app-store-registration-paperwork/) / [全工程まとめ](/engineering/app/personal-app-cross-store-release-full-journey/)

### この記事の表記について

ドメインは `example.com` に置き換えています。アプリ名 `Bucket List Commit` と公式サイト `blc.shiiman.dev` は実名です。

### 前提

- サイトは Astro の静的サイト + Cloudflare Pages（無料枠）
- バックエンドは **Firebase**（Firestore / Storage / Auth / App Check / Cloud Functions）
- 外部連携として Google Calendar / Sheets（**機密スコープなので審査あり**）と **GitHub**
- 日英 2 言語（配信地域が日本 + 米国）

## 用意したもの一覧

| もの | 何のために |
|---|---|
| 事業者サイト（apex ドメイン） | Play の販売者プロファイル / D-U-N-S の「組織のウェブサイト」/ 組織のウェブサイト確認 |
| アプリ用サブドメイン | 法務 4 ページ / 着地ページ / 要望フォーム / ダウンロード導線 |
| サポート用メールアドレス | 両ストアで公開される連絡先 |
| Google グループ | OAuth 同意画面のサポートメールに独自ドメインが使えないため |
| DMARC / SPF / DKIM | 転送・送信の到達性 |
| Firebase プロジェクト + 従量課金 | バックエンド |
| Google Cloud の OAuth 同意画面 | Calendar / Sheets 連携（機密スコープなので審査あり） |
| GitHub OAuth App | GitHub 連携 |

サイトを 2 つに分けたのが結果的に正解でした。Play の**販売者プロファイル**は「販売者単位」でアプリを跨ぐので、ここにアプリ固有のサブドメインを入れると 2 本目のアプリで矛盾します。

### 事業者サイトは「申請より前」に公開する

順序の話として、これは効きました。

事業者サイト（apex）は、D-U-N-S 申請と各種審査で「事業体が実在すること」を示す参照先になります。屋号 / 事業内容 / プロダクト / 事業者情報（所在地は「日本」のみ・詳細住所は非掲載）と英語の About を載せたページを、**申請より先に公開**しました。

Google の OAuth 検証でも「ホームページ」と「プライバシーポリシー」が所有権確認済みドメイン上にあることが前提になります。サイトは一番最初に片付けておくと、後続の審査が全部楽になります。

### apex のカスタムドメインは DNS を自動で作らない

静的ホスティングにカスタムドメインを割り当てるとき、apex（`example.com`）は自動で DNS レコードが作られませんでした。`CNAME example.com → <project>.pages.dev`（proxied）を**手動で作成**する必要があります。

しかもここでメールを壊しかけました。

apex に CNAME を置くと、本来は同じ名前の MX / SPF / DMARC と共存できません（DNS の仕様上、CNAME は他のレコードと同居できない）。使っているサービスが **CNAME flattening** を実装している場合は共存できますが、それを「たぶん大丈夫」で済ませると受信が全部死にます。

→ 権威 DNS サーバーへ直接問い合わせて、MX / SPF / DMARC が引けることを実際に確認してから進めました。メールの疎通は「送って届くか」で確認するより、レコードが引けるかを先に見るほうが速いです。

## アプリが直接開く URL は後から変えられない

ストアが要求する URL は 4 つです。

| パス | 誰が要求するか |
|---|---|
| `/terms` | UGC ポリシー（規約で不適切コンテンツを禁止する必要がある） |
| `/privacy` | 両ストア（プライバシーポリシー URL は必須） |
| `/support` | App Store の Support URL / Play の連絡先 |
| `/account-deletion` | Play のデータ削除要件（アプリ内の削除機能とは別に「公開 URL での案内」が要る） |

`/terms` と `/privacy` はアプリが直接開きます。つまり**あとからパスを変えられません**（`/ja` 接頭辞を付けることさえできない）。ストア側にも登録するので、URL を変えると両ストアの申告を更新する話になります。最初に決めてください。

### 法務ページの本文は「仕様書」ではなく「実装」から書く

これは意識的にやって効きました。仕様書を元に書くと、実装とズレた約束をユーザーにしてしまいます。

実装を読んで書いた結果、こういう粒度になりました。

- プライバシーポリシー: **メールアドレスは DB に保存しない** / 生年月日は 10 年区切りの年代のみ送信する / プッシュ通知のトークン / 診断データ（オプトアウト可）
- アカウント削除の説明: **「いいね」の参照は匿名で残る** / 削除してもサブスクリプションは自動解約されない / 外部サービス側（連携先）のデータは残る
- 利用規約: 返金は各ストアの標準ポリシーに準ずる / サービス提供終了時の扱い

「削除してもサブスクは自動解約されない」のような不都合な事実こそ書く必要があります（書かないと、ストアの申告とも実装とも食い違う）。

### 公開できたことの検証

「デプロイした」ではなく「実 URL で読める」で判定しました。

```sh
curl -sL -o /dev/null -w '%{http_code} %{size_download}\n' https://example.com/terms/
```

4 ページとも **HTTP 200 + 本文長が数千字**あることを確認し、さらに 「準備中」「TODO」「Coming soon」等の未完成マーカーが 0 件であることを確認しました（プレースホルダのまま公開していないことの証明）。

さらに、アプリの機能として着地ファイルが 2 つ必要でした。

| パス | 役割 |
|---|---|
| `/.well-known/apple-app-site-association` | iOS の Universal Links。未配信だと招待 URL / QR がアプリで開かずブラウザに飛ぶ |
| `/.well-known/assetlinks.json` | Android の App Links |

## 着地ファイルの罠

### ① AASA は拡張子が無いので Content-Type を誤判定される

`apple-app-site-association` はファイル名に拡張子がありません。そのため静的ホスティングが正しい MIME タイプを付けず、**iOS が読めません**。

→ `_headers`（ホスティングのヘッダ設定）で `application/json` を明示しました。HTTP 200 が返っていても、Content-Type が違うと機能しません。「配信されているか」だけ見ると通ったつもりになります。

### ② assetlinks.json に入れるのは「アプリ署名鍵」の指紋

アップロード鍵の SHA-256 を入れても本番の App Links は通りません。Play App Signing を使うと、実際に配信される APK は **Google が持つアプリ署名鍵**で署名されるためです。

アプリ署名鍵は Play にアップロードするまで存在しません。`assetlinks.json` の完成は Play Console 登録（= D-U-N-S 待ち）に依存します。debug 鍵 / アップロード鍵 / アプリ署名鍵の **3 本**を並べて解決しました。

検証は**オンデバイスで見る**のが確実です。

```sh
adb shell pm get-app-links <package>
#  → 対象ドメインが verified になっているか
```

### ③ 対象パスの一覧は「アプリ側の定義」と突合する

AASA と `assetlinks.json` には「アプリで開くパス」を列挙します。ここを手で書くと、アプリ側のルーティングとズレます。

→ 私は iOS のルーター（URL を捌く `switch` の分岐）と Android の `intent-filter` を両方読んで、9 パスが一致することを試してから書きました。片方にしか無いパスがあれば、そのリンクはその OS で開きません。

### ④ 着地ページ自体を用意しないと「開けるが何も無い」になる

App Links の対象パスは、アプリが入っていない人がブラウザで開いたときの着地ページも必要です。9 パス全部に静的ページを用意し、**実 URL で 200 を確認**しました（ここを省くと「リンクを踏んだら 404」になる）。

## ホスティングで踏んだ落とし穴 7 つ

静的ホスティング（Cloudflare Pages）で自分で動かして分かったものです。推測ではほぼ全部外しました。

### ① リダイレクト設定の 200 プロキシは、宛先の末尾スラッシュが必須

招待リンクを別パスへ内部プロキシしていたのですが、宛先の書き方で結果が変わりました。

| 宛先の書き方 | 結果 |
|---|---|
| `/invite/` | ○成立 |
| `/invite` | 308 に化けてトークンが消える |
| `/invite/index.html` | ×404 |

招待トークンをクエリで運んでいたので、308 でリダイレクトされた時点でトークンが失われました。「リンクを開くとアプリに入れない」という症状の真因がこれでした。

### ② クエリ位置のプレースホルダは展開されない

`?token=:splat` と書いても `?token=%3Asplat` になります。**展開されるのはパス位置だけ**です。

### ③ Functions の探索位置はデプロイの実行ディレクトリ基準

モノレポでサイトを複数持っていると、`functions/` が拾われません。デプロイの作業ディレクトリをサイトのルートに変える必要がありました。

### ④ プレビュー用ドメインの二重公開は、リポジトリの外で解決されている

`*.pages.dev` が本番と同じ内容を配信すると SEO 上の重複になります。これはアカウント側の Bulk Redirect リストで 301 にしていました。

リポジトリ内に `_redirects` も middleware も無いので、コードを読んでも絶対に気づけません。新しいサイトを追加したとき、**そのリストへの登録漏れ**が起きます（実際に 1 サイト漏れていました）。

### ⑤ エッジキャッシュで直後の確認が嘘をつく

デプロイ直後は 404 / 200 が伝播途中で揺れます。`?cb=$RANDOM` を付けて確認し、安定するまで複数回見る必要がありました。

### ⑥ デプロイ直後の 1 回目は旧版が HTTP 200 で返る

`assetlinks.json` の更新で実際に確認した例です。

```
[試行 1] HTTP 200 / 430 bytes  ← 旧版（指紋 2 件）
[試行 2] HTTP 200 / 537 bytes  ← 新版（指紋 3 件）
```

ワークフローが success でも、直後の 1 回目は旧版。しかも HTTP 200 なのでエラーとして気づけません。→ **「期待する内容が来るまでリトライ」で判定**します（`size_download` の変化も手掛かりになる）。1 回で「未反映」と判断すると誤報になります。

### ⑦ `curl` に `-L` を付けないと「表示されていない」と誤読する

末尾スラッシュへの 308 が挟まるので、`-L` が無いとリダイレクト応答の空ボディを読んでしまいます。これで「反映されていない」と誤認しました。

## 日英対応の URL 設計

配信が日本 + 米国なので、サイトも日英対応にしました。設計はこうです。

- `/` = 日本語（**接頭辞なし固定**）/ `/en/...` = 英語
- 自動リダイレクトを付けない。URL が内容を決めるので、ストアの各ロケールに固定 URL を登録できる（`ja` の申告に `/privacy`、`en-US` の申告に `/en/privacy`）
- `hreflang` + `x-default`
- 英語の法務ページには「日本語版が正文」の注記を入れた（**個人開発で翻訳の完全性を保証できないため**）
- そもそも英訳するかどうかも判断が要ります。米国配信があるので「審査担当者が読める英語版が必要」と判断し、法務ページだけでなく**サイトの全ページを英語化**しました

着地ページだけは `/en` を持てません。アプリが発行する招待 URL に言語情報が無いためです。→ **1 ページ内で日英併記**にしました。

フォームは 1 つのコンポーネントに共通化しました（言語別に複製すると送信処理が 2 本になり、片方だけ直す事故が起きる）。選択肢の value は共通で、ラベルだけ言語別にします（サーバー側のマッピングとの対応が崩れないため）。

## メールは「受信できる」だけでは足りない

**⓪ アドレスを役割で分ける**

先に整理しておくと後が楽です。独自ドメインで **4 本**作りました。

| アドレス | 役割 | どこに出るか |
|---|---|---|
| `admin@` | 事業者としての連絡先 | D-U-N-S 申請 / Play の「Google からの連絡先」 |
| `support@` | 事業体レベルのサポート窓口 | Play の販売者プロファイル（アプリを跨いで共有される） |
| `blc@` | アプリ固有の連絡先 | ストアのアプリ掲載情報 / レーティング質問票 |
| `dmarc@` | DMARC レポートの受け先 | 非公開 |

「事業体レベル」と「アプリ固有」を分けておかないと、2 本目のアプリを出すときに困ります。この 2 つは**実際に別の画面で聞かれる**ので、混同すると片方に間違ったアドレスが載ります。

**決定的なのは「変更しやすさ」が違うこと**でした。

|  | 変更のしやすさ |
|---|---|
| 販売者プロファイルのサポートメール | アカウント全体で 1 つしか持てず、全アプリ共通 = 変えにくい |
| ストア掲載情報のメール | アプリごとに指定できる = 差し替えやすい |

→ アプリ固有アドレスが荒れたら差し替えられるように、最初から分けておくのが正解でした（アカウント側は世界に公開済みなので変えにくい）。

Play の「Google からの連絡先」は、Google アカウントとは別で、かつサイトのドメインと一致している必要がありました。

**① 転送サービスは受信専用**

独自ドメインのメールを無料の転送サービス（Email Routing）で受けていました。これは受信専用で、そのアドレスから送信できません。

ストアのサポートアドレスとして公開する以上、返信は必ず発生します。個人の Gmail から返信することになり、アドレスを分けた意味が消えます。対応は「Gmail の『他のアドレスからメールを送信』+ SMTP リレー + SPF / DKIM」で、**ストア公開前に必須**の項目です。

**② DMARC を足す**

SPF / DKIM だけでなく DMARC レコードも追加しました。転送を挟むと到達性が落ちやすいので、ストアに載せるアドレスは受信できることを実際に確認しておきます。

### ③ OAuth 同意画面のサポートメールに独自ドメインが使えない

ここは詰まりました。OAuth 同意画面のユーザーサポートメールは「自分の Google アカウントのアドレス」か「自分が所有する Google グループ」のみ（ドロップダウン制約）。独自ドメインの転送アドレスは Google の identity ではないので選択肢に出てきません。

→ **Google グループを新設して指定**しました。設定のポイント:

- **メッセージの管理 = 管理しない**（Google の審査連絡が承認待ちで埋もれる事故を防ぐ）
- 購読 = メッセージごとにメール

一方で **「デベロッパーの連絡先情報」欄は自由入力**なので、独自ドメインのアドレスを入れられます。**画面によって制約が違う**ので、1 か所の制約を全体に一般化しないよう気をつけます。

### ④ 転送メールは「必ず」迷惑メールに入る（試した 2 通ともそうでした）

仕組みを理解しておかないと、いくら自分のドメイン設定を直しても解決しません。

**なぜ入るか**:

1. 転送すると `From:` は元の送信者のドメインのままで、配送元の IP だけが転送サービスに変わる
2. → **元ドメインの SPF が整合しない**（そのドメインは転送サービスの IP を許可していない）
3. → さらに、その転送経路に受信側は**信用の履歴を持っていない**

重要なのは「自分のドメインの MX / SPF / DKIM を正しく設定しても効かない」ことです。DMARC の評価は `From:` ドメインに対して行われるので、自分のドメイン側に何を足しても、他人のドメインから届いたメールの判定は変わりません。

→ 対処は受信側でフィルタを作り「迷惑メールにしない」を明示することだけです。

これはストア公開の問い合わせ窓口なので、設定しないと実ユーザーからの問い合わせに気づけません。外部申請用のアドレスだけフィルタを作り忘れていて、外部待ちの確認メールを見落とすリスクを抱えていました。

### ⑤ DMARC は「入れた」だけでは何も守らない

`_dmarc.<ドメイン>` に `v=DMARC1; p=none; rua=mailto:...` を設定しましたが、ここで 2 つ勘違いをしていました。

- `p=none` はなりすましをブロックしません。「観測して報告させるだけ」の監視段階です
- `rua` の宛先が受け取れないとレコードは無意味です（レポート受信用の転送ルールも作る）
- **昇格の判断材料**: そのドメインから正規に送信しているものが無ければ、レポートを数週間観測して想定外の送信が無いことを確認できれば `p=quarantine` → `p=reject` に上げられます
- ただし将来そのアドレスから送信する（SMTP を足す）ときは、送信元の SPF / DKIM を先に設定してから `p` を上げること。順序を逆にすると**自分の送信が拒否されます**

### ⑥ 設定系 API の権限は「メール」の権限ではなかった

転送サービスの**有効化・設定系の API** は、「メールのルール」や「メールのアドレス」の権限では通らず、**ゾーンの設定権限**を要求しました（権限が足りないと `Authentication error` になるだけで、何が足りないかは教えてくれません）。

受信の設定自体は MX 3 件 + SPF + DKIM が自動で追加されました。catch-all は「破棄」かつ無効のままにしています（有効にするとスパムの受け皿になる）。

### ⑤ 本番 HTML に素のメールアドレスが存在しない

これは検証が空振りした例です。サイトにサポートアドレスを載せたあと、こう確認しました。

```sh
curl -s https://example.com/support | grep '@'
→ 0 件
```

この結果を見て「未反映」と判断しかけました。**実際は反映済み**で、原因が 2 段ありました。

1. `/support` は 308 で `/support/` へリダイレクトする（`-L` が無いと空ボディを読む）
2. ホスティングの Email Obfuscation 機能が有効なので、本番 HTML に素のアドレスは存在しない。`<a href="/cdn-cgi/l/email-protection#...">` + `data-cfemail="<hex>"` に置き換わる

正しい検証は、hex を復号することです（先頭 1 バイトが鍵で、残りを XOR する）。

```sh
curl -sL "https://example.com/support/" | python3 -c "
import sys, re
h = sys.stdin.read()
for x in re.findall(r'data-cfemail=\"([a-f0-9]+)\"', h):
    k = int(x[:2], 16)
    print(''.join(chr(int(x[i:i+2],16) ^ k) for i in range(2, len(x), 2)))
"
```

ビルド成果物には素のアドレスが入っています（難読化はエッジで起きる）。ローカルは grep で足りるが、本番だけ復号が必要——この非対称が誤読の原因でした。

## 要望フォームを置くと攻撃面が増える

フィードバックを受ける口を用意し、投稿を GitHub の Issue として自動作成する構成にしました。便利ですが、外部から叩ける口を作るということです。

入れた防御:

- **CAPTCHA（Turnstile）** — トークンは単回使用
- **同一オリジン限定** + 本文サイズと文字数の上限
- 本文を 5 連バッククォートのフェンスで囲んで Markdown を無害化（`@メンション`と画像を解釈させない。**5 連以上のバッククォートは除去**しておく）
- **自由記述の `|` をエスケープ**（Issue 本文の表が崩れる）
- 投稿を公開する API は**フォーム経由以外はタイトルのみ返す**（ラベルの誤操作時に漏れる範囲をタイトルに限定）

一番危なかったのがこれです。

キャッシュキーを `origin + pathname` 固定にしていないと、`?x=1` を付けるだけでキャッシュを回避され、GitHub API のレート制限（5,000/時）を外部から枯らせます。

私は自分で `?cb=` を付けて確認しているときにこれに気づきました。検証は「GitHub API の消費量」で測るべきで、レスポンスの `age` ヘッダはエッジ由来なので当てになりません。

**IP 単位のレート制限は未実装のままです**（API トークンに必要な権限が無く、WAF 側でやる話になった）。正直に書いておきます。

フォームで識別子（ユーザー ID やアプリのバージョン）を受け取るなら、プライバシーポリシーにその節を足す必要があります。記載がないと申告が不正確になります。

## シークレットをどこに置くか

どこに置くと実際にビルドへ埋め込まれるのかを間違えると、動かないか漏れます。

| もの | 置き場所 |
|---|---|
| API トークン・シークレット | ホスティングの Secret（production と preview の両方に入れる） |
| 公開してよいサイトキー | CI の Variables |
| リポジトリ操作用の PAT | fine-grained で必要な権限だけ（実際に他が 403 になることを確認） |

**サイトキーを CI 側に置く理由**: ビルドが CI で走ってホスティングには成果物だけ上げる構成だと、ホスティング側の環境変数はビルド時に読まれません。「Secret はホスティング、ビルド時に埋め込む値は CI」という切り分けです。

さらに権限と場所の罠。

- API トークンに CAPTCHA / KV の権限が無く、ダッシュボードでしか作れないものがあった
- CAPTCHA の設定はゾーン（ドメイン）ではなくアカウント直下にあり、ドメインを選択中のサイドバーには出てこない（直 URL で行く必要がある）
- ホスト名を本番だけ登録すると、プレビュー環境では `Error: 110200`（ドメイン不一致）でフォームの検証ができません。→ **実投稿の検証は本番でしかできない**と割り切りました

運用として、シークレットの値は画面に出さず API で投入しました（値を目にしない形にしておくと、誤ってログや Issue に貼る事故が構造的に起きません）。

## Firebase / OAuth の初期構築で踏んだもの

### ① `CONFIGURATION_NOT_FOUND` = Authentication 自体が未初期化

着手前はこのエラーでした。プロジェクトを作っただけでは Authentication は有効になっていません。しかも iOS = Apple サインイン / Android = Google サインインがそれぞれ唯一の認証手段だったので、**ここが全体のブロッカー**でした。

### ② Apple は API で有効化できるが、Google は Console でやる

- **Apple**: プロバイダの有効化 API に `{"enabled": true}` を送るだけ。iOS ネイティブのみなら Services ID / Key ID / 秘密鍵は不要
- **Google**: API で `enabled: true` だけ送ると、OAuth 同意画面のブランド設定（公開名・サポートメール）と iOS / Android の OAuth クライアントが伴わず、`REVERSED_CLIENT_ID` が生成されない半端な状態になり得ます

「API でできる」ことと「API でやってよい」ことは違う、という例でした。

### ③ 実 plist を置いた瞬間、ユニットテストが本番へ実通信し始めた

これは肝を冷やしました。本番プロジェクトを作って実際の設定ファイルをリポジトリに置いた瞬間、`make test` が本番プロジェクトへネットワーク通信するようになりました。

原因は、初期化のガードが「設定ファイルが無ければ初期化しない」だけで、テストホストがアプリ本体なのでテスト時にも初期化されることでした。

「未初期化」を前提にするテストが 5 ファイルあり、それまで通っていたのは「設定ファイルが gitignore されていて偶然不在だったから」でした。CI は設定ファイル不在で通るので、**ローカルと CI で挙動が違う**状態です。

→ テスト実行中を判定する明示的なガードを足しました。判定は「本番への通信痕跡の件数」で行いました（ログ行の有無では判定できなかった。修正前もログは出ていなかったため）。

### ④ Debug の entitlements が「無料アカウント前提」のまま残っていた

有料の Developer Program に加入した時点で前提が変わっているのに、Debug ビルドの entitlements が最小構成のままでした。実害はこれです。

- `associated-domains` が無い → Universal Link / QR を実機の Debug ビルドでテストできない
- App Groups が無い → ウィジェットの共有コンテナが実機で解決されない（**シミュレータは緩いので通っていただけ**）
- Apple サインインの entitlement が無い → 実機で本物のサインインを検証できない

App ID と capability が Portal に存在しないとプロファイルが発行されないので、これは App ID 登録の後にやる作業です。

### ⑤ 設定ファイルの一部が「後から生成される」

Firebase の設定ファイルを配置したものの、Google サインイン用のキー（`REVERSED_CLIENT_ID` / `CLIENT_ID`）が入っていませんでした。

これは Auth の Google プロバイダを有効化したときに初めて生成されるもので、有効化した後に設定ファイルを再取得する必要があります。ビルドスクリプト側で「このキーが無ければ警告を出す」ようにして、取り忘れを検知できる形にしました。

### ⑥ サービスアカウントのプロジェクト権限が 0 件だった

ストアの API を叩くサービスアカウントを作って Console 側に招待したのに、クラウドプロジェクト側の IAM ロールが 1 つも付いていませんでした。

ストア Console への招待と、クラウドプロジェクトの権限はまったく無関係です。DB アクセスやシークレット読み取りのロールを別途付与し、未有効だったシークレット管理の API も有効化する必要がありました。

### ⑦ GitHub OAuth App が未登録で、看板機能が動いていなかった

外部連携用の OAuth App を登録しておらず、**client_id がコード側で空文字**でした。要するにその連携機能は一度も動いたことがありませんでした。

Debug ビルドはモックに差し替わる構成だったので、開発中はまったく気づけませんでした。「Debug で動いている」は「本番で動く」の証拠にならない、という典型です。

## OAuth 同意画面の本番公開と機密スコープ検証

外部連携（カレンダー / スプレッドシート）を持つなら、**ここが D-U-N-S と並ぶ外部待ち**になります。**私の場合は申請から 1 日で承認**されましたが（公称 10 日前後・数週間の事例もある）、**その前に踏んだものが多い**ので順に書きます。

### そもそも API が有効化されていなかった

一番大きかったのがこれです。有効な API を実際に確認したら、Calendar API と Sheets API がどちらも無効でした。

この状態ではこうなります。

- すべての API 呼び出しが `403 SERVICE_DISABLED` を返す
- スコープを正しく揃えても連携はまったく動かない

これは Debug ビルドでは絶対に検知できませんでした。外部連携をモックに差し替えていたので、ユニットテストでもシミュレータでも一切露見せず、実機の Release ビルドで初めて分かりました。

さらに悪いことに、アプリ側が 403 を一律「Google 連携の権限が不足しています」と表示していたため、**原因の切り分けを誤らせました**（権限の問題だと思い込んで、スコープばかり疑った）。

> **教訓** 2 つ
> 1. 「使う API を有効化する」は独立したタスクとしてリストに載せる（私のリストにはこの項目自体が無かった）
> 2. エラーを一律の文言に丸めると、自分の切り分けを妨害する。`SERVICE_DISABLED` のような区別できる情報は落とさない

逆に、使わない API は有効化しません。私の場合 `drive.file` は**スコープ**であって Drive API そのものは呼ばないので、Drive API は有効化しませんでした（最小権限を維持）。

### スコープの選定 — 機密を減らす方向で組む

要求したのは 4 つで、そのうち「機密（sensitive）」に判定されたのは 2 つだけでした。

| スコープ | 判定 |
|---|---|
| `calendar.events` | 機密（検証対象） |
| `calendar.calendars` | 機密（検証対象） |
| `calendar.calendarlist.readonly` | 非機密 |
| `drive.file` | 非機密 |

ここで 2 つ学びがありました。

- 当初はスコープが足りず、連携が機能していませんでした。カレンダー一覧の取得と専用カレンダーの作成に必要なスコープを要求していなかったためです。**認可は通るのに機能しない**という状態になります
- 機密の `spreadsheets` を、非機密の `drive.file` に置き換えました。アプリは**自分で新規作成したファイルにしか書かない**ので、per-file 権限で足ります。機密スコープを 1 つ減らすと審査の範囲が狭くなるので、要求前に「本当にその広さが必要か」を確認する価値があります

「テスト中」のままだと refresh token が 7 日で失効します（ユーザー数の上限もある）。本番公開は避けられません。

### 最初に止まったのは「アプリ名の不一致」だった

検証センターの「確認の進行状況」に、解決すべき問題が並びます。最初に赤で止まったのはブランドの取り扱いガイドラインでした。

![Google Auth Platform の検証センター。ブランドの取り扱いガイドラインの指摘として「OAuth 同意画面に表示されるアプリ名とホームページに掲載されているアプリ名が一致していません」と表示されている](./assets/oauth-verification-branding.png)

内容はロゴやボタンの意匠ではなく、**同意画面のアプリ名とサイトのアプリ名が一致していない**というものでした。原因は同意画面側の表示名がカタカナ表記になっていたことです。サイトはラテン文字表記だったので、機械的に別名として扱われました。

直し方は「サイトを直す」ではなく「同意画面の表示名をサイトと同じ表記に揃える」です。ブランド名を翻訳も音写もしない、という方針がここでも効きました。

直した後の再検証は、この「ブランディングの確認に関する問題」ダイアログから依頼します。**「問題は修正した」か「検出された問題は正しくないと思う」のどちらかを選ばないと続行できません**。放っておいても勝手には再検証されません。

![Google Auth Platform の「ブランディングの確認に関する問題」ダイアログ。前回の確認で検出された問題として「ホームページでアプリの目的が説明されていません」「OAuth 同意画面で構成されているアプリ名が、ホームページに掲載されているアプリ名と一致していません」が並び、対応方法として「問題は修正した」「検出された問題は正しくないと思う」のラジオボタンがある](./assets/oauth-branding-issue-dialog.png)

もう 1 つ「ホームページでアプリの目的が説明されていません」も同時に出ていました。**ランディングページに「このアプリは何をするものか」を文章で書く**必要があります。スクリーンショットやダウンロードボタンだけでは足りません。

直す場所は Google Auth Platform の「ブランディング」→「アプリ情報」→ アプリ名です。**同意画面に出るのはこの 1 か所の値**で、サイト側の表記と 1 文字単位で一致させます。

![Google Auth Platform のブランディング画面。「アプリ情報」の下に「アプリ名」の入力欄があり、Bucket List Commit と入っている](./assets/oauth-branding-app-name.png)

### 差し戻しの指摘は「プライバシーポリシー」だった

ブランド名を揃えた後、メールで 1 度差し戻されました。ロゴやボタンの意匠を指摘されると思っていましたが、そちらは最後まで問題になりませんでした。実際の指摘は 2 点で、どちらもプライバシーポリシーの記載でした。

> (1) does not state with whom you share, transfer, or disclose Google user data
> (2) does not specify any data protection mechanisms for sensitive data

既存の「第三者提供」の節に提供先を列挙してあっても足りません。Google が求めるのは「Google ユーザーデータに限定した明示」でした。

→ 専用の 2 節（Google ユーザーデータの共有・転送・開示 / **Google ユーザーデータの保護措置**）を日英に新設しました。**記載はすべて実装を確認して書きました**（端末と Google の直接通信 / 連携先アカウント情報は端末内のみ / iOS は Keychain・Android は永続化せず認可情報から都度取得 / TLS / 最小権限のスコープ / DB のアクセス制御は本人のみ）。AI / ML の学習に使わないことも明記（検証の要件に含まれる）。

手続き上の罠。

指摘メールに「返信」しないと審査が進みません。修正して Console から再提出するだけでは足りず、**メールへの返信が必要**でした。

審査中は「公開ステータス」「ユーザータイプ」「スコープ構成」を触らないでください。検証プロセスがやり直しになります。

### 承認後にも制約が残る

承認メールに書かれていた運用上の注意が重要でした。

- 新しいスコープを追加する / 同意画面の設定を変更すると、再度検証申請が必要になります。今後スコープを触るときは審査待ちが再発する前提で計画する必要があります
- 検証は継承されません。未承認の機密 / 制限付きスコープは、追加検証なしには使えません
- Cloud Console の Project Owner / Editor を最新に保つ（今後の連絡が届かなくなる）
- 審査に使ったデモ動画は削除せず「非公開」にする。上記のとおり再審査で再提出を求められるので、消すと作り直しです（審査中に非公開にすると担当者が見られず差し戻されるので、切り替えは承認後）

### 承認が効いていることの最終確認

承認メールが来たことは「効いている」証拠になりません。実機で「このアプリは Google で確認されていません」の警告画面が出なくなったことを目視して、初めてクローズしました。

承認されたスコープの件数が要求より少なくても、欠けているとは限りません。私の場合「承認 2 件」でしたが、**機密が 2 件しかなかったから**です（非機密は検証対象外）。件数だけ見て慌てる必要はありません。

### ドメイン所有権は「推測」で済ませない

機密スコープ検証の前提として、ホームページとプライバシーポリシーが所有権確認済みドメイン上にある必要があります。

登録は Search Console で行いますが、最初の選択が効きます。「ドメイン」を選ぶと**サブドメインを全部カバー**でき、確認方法は DNS だけになります。「URL プレフィックス」は入力した URL しかカバーしません。

![Search Console のプロパティ タイプの選択ダイアログ。左に「ドメイン」（すべてのサブドメインの URL / DNS の確認が必要）、右に「URL プレフィックス」（入力されたアドレスの URL のみ / 複数の確認方法に対応）が並んでいる](./assets/search-console-property-type.png)

私は当初「検証を提出できたから所有権確認は済んでいるはず」と考えましたが、それは根拠になりません。DNS の TXT レコードを直接引いて確定させました。

```sh
dig +short TXT example.com | grep google-site-verification
```

ドメインプロパティで登録してあればサブドメインもカバーされます（サブドメイン側に meta タグや HTML ファイルが無いのは正常）。

### GitHub 連携（OAuth App）の設定

もう 1 つの外部連携です。こちらは審査がないので簡単でしたが、配線に穴がありました。

登録画面はこれです。Application name / Homepage URL / Application logo を入れて、Client ID が発行されます。

![GitHub の OAuth App の設定画面。Client ID と Client secrets、Application logo のアップロード欄、Application name（Bucket List Commit）と Homepage URL の入力欄が並んでいる](./assets/github-oauth-app.png)

- Device Flow を有効にして OAuth App を登録（クライアントシークレットを持たない方式）
- client_id は配布バイナリから抽出できる非秘匿値なので、そのままコミットする方針にしました（Device Flow にクライアントシークレットは存在しない）
- 空値を Release ビルドで fail-fast させました。Debug はモックに落ちるので、配線を忘れても気づけません。「動いていないことに気づけない」経路は、**構造的に止める**しかありません

この検証中に、連携先のボードを「アカウント全体のタイトル一致」で探していて、他人の同名ボードを掴みうる実装だったことも見つかりました（リポジトリスコープに修正）。外部サービスの検索 API は、スコープを明示しないと想定外のリソースを掴みます。

## Rules / Functions のデプロイドリフト

これはリリース直前に本番だけで起きるバグの温床でした。

- マージしても本番に反映されない。Security Rules も Cloud Functions も、リポジトリにマージした内容が自動でデプロイされる構成ではありませんでした。本番はマージの数日前のリビジョンで動いていました
- **静的サイトも同型**（push トリガが無く、手動でワークフローを叩く構成だった）

検知方法は「本番の実体を API で取得して、リポジトリの内容と突合する」です。

実際にこれで、Storage Rules の本番専用バグを見つけました。条件式で使う変数の誤用により、Android のバックアップ復元が本番で一度も成功しておらず、退会 / 全消去の削除も全部拒否されていたというものです。エミュレータのテストでは通っていました。

危なかったのは、「消えたつもり」で合格判定しかけたことです。削除が 403 で失敗しているのに、UI 上は「削除しました」と出ていました。→ サーバー側の実データを直接見て 0 件になったことを確認する手順に変えました。

### ドリフトの実例と、確立した手順

最初のデプロイの後、リポジトリ側で 3 回変更していたのに本番は初回のままでした。気づいたのは本番の設定を API で取得してリポジトリと差分を取ったときです。

このときの差分は「本番のほうが厳しい」方向でした（削除したはずの条件が本番だけに残っていた）。セキュリティ穴ではありませんが、その条件のせいで書き込みのたびに余分な読み取りが 1 件発生していた = 課金対象の無駄でした。ドリフトは「危険な方向」だけに出るとは限りません。

そこで手順を固定しました。

1. **デプロイ前**に本番の設定を取得して差分を取る —— 差分が「今回の変更ちょうど」であることを確認する（他の PR の未反映が混ざっていないか）
2. テストを通す（私の場合は Rules のテスト 278 件）
3. デプロイする
4. デプロイ後にもう一度取得して、リポジトリと完全一致（コメント込み）することを実際に確かめる —— コマンドの終了コードは反映の証拠になりません
5. インデックスも件数と状態を突合する（追加直後は `CREATING` なので、`READY` になるまで API で追跡する）

未デプロイのままだと「穴が開いたまま」になる変更がありました。例えば「認証済みユーザーが 1 回の書き込みで有料機能を自己付与できる」穴を閉じる変更は、デプロイして初めて効きます。マージした時点で安心すると、**本番は無防備なまま**です。

### ローカルのエミュレータと本番で、ルールの評価が違った

これは「テストが全部緑なのに本番だけ全部拒否される」という最悪の形で出ました。

ローカルのエミュレータは、読み取りや削除のときにも「書き込もうとしているデータ」の参照を解決してしまいます。本番はそこが未定義なので、同じ条件式が エミュレータでは通り、本番だけ拒否されました。

結果として、372 件のルールテストは全部緑のまま、本番ではバックアップの復元と削除が一度も成功していませんでした。

→ 対策は 2 段構えにしました。

1. CI の静的ガードで、そのパターン自体を書けなくする（読み取り・削除の条件でその参照を使ったら落とす）
2. **本番の評価器に対して手動で検証する**（本番のルールセットを取得して、そこにテストケースを投げる API がある）

テストの穴も見つかりました。そもそも **削除のテストが 1 件も無かった**のです。「テストが緑」は「テストが存在する」を意味しません。

### 「テストが失敗するのは環境要因」と決めつけて、実バグを本番にデプロイした

これは一番危なかった話です。

ストレージのアクセス制御のテストが 7 件失敗していて、私は「エミュレータの環境要因」だと判断しました。実際は**実バグ**でした。

さらに最悪なことに、その日の午前に、修正前の壊れたルールを本番へデプロイしていました。（幸いユーザーが存在しない時期だったので実害はなく、修正後の再デプロイで解消しました）

さらにこのバグは、それまでの監査を 18 ラウンド通り抜けていました。テストが「落ちている」のに原因を環境に帰属させたことで、**検査が実質的に無効化されていた**わけです。

> **教訓**: テストの失敗を「環境要因」と結論するには、環境要因であることの証明が必要。
> 「たぶん環境」で片付けると、落ちているテストが本番のバグを指しているケースを取りこぼします。環境要因だと言いたいなら、**同じ環境で別のテストが通っていること**などを根拠として示すべきでした。

このとき使えた手がかりを記録しておきます。失敗した 7 件が**すべて「できる」側のアサーション**（読める / アップロードできる）で、「できない」側のテストは全部通っていました。

> 全部拒否されているなら、「拒否されること」のテストは自明に通ります。

「肯定側だけが落ちている」という偏りが、全 deny のシグナルでした。失敗の内訳に偏りがあるときは、それ自体が原因を指しています。

### 反映の順序を間違えると「窓」が開く

サーバー関数とアクセス制御を同時に変えるときは、**順序が重要**でした。

**必ず「関数 → ルール」の順**にします。逆順だと、**クライアントがデータを書けない**のに**代わりに処理する関数もまだ無い**という窓が開き、その間の操作が失われます。

しかも**関数の側にも注意点**がありました。

- 認証ユーザーの削除トリガは旧世代の API にしか存在しませんでした（新しい書き方に移行できない）
- 旧世代のモジュールが **default export を持たない**ため、名前付き import に直す必要がありました（実際に踏んだ）
- 関数のコードを変更する PR をマージしても、手動でデプロイしないと反映されません（CI はテストだけ）

## App Check の強制化 — 順序を間違えると戻せない

クライアント認証（App Check）を「計測のみ」から「強制」に切り替える工程です。

強制にすると、条件を満たさないクライアントは全部締め出されます。順序が重要でした。

1. 両 OS の実機でトークンが `VALID` になることを試してから強制にする
2. サービスは**1 つずつ**切り替える（**認証系のサービスは同時に触らない**——サインインごと止まる可能性がある）
3. 毎回再取得して、意図した値になっていることを確認する
4. **切り戻し手順を先に用意しておく**（同じ API で戻せば即座に解除できる）

「計測のみ」モードは「強制しないが計測する」ので、強制にする前に判定できます。一方、完全な OFF は**計測もしません**。最初これを混同して、「トークンが付いていない」と誤診しました（**実際は計測していなかっただけ**）。

強制化のタイミングは「エミュレータが必要な検証を全部終えた後」にしました。強制にするとPlay 配信版を載せたエミュレータが締め出されるからです（デバッグ用のトークンは debug ビルド専用）。

## コスト防御で踏んだ GCP の落とし穴

コスト防御の[予算キルスイッチ](/engineering/app/personal-app-cross-store-release-full-journey/)（従量課金の請求が跳ねたら請求先アカウントのリンクを自動で解除する仕組み）を作るときに踏んだものです。

### そもそも「日次の上限を設定して超過分をエラーにする」ができなかった

私の設計書は破産防止を 3 段構えにして、その 2 段目に「Firestore / Cloud Storage の Quota 上限で 1 日の上限を強制し、超過分はエラー化（課金されない）」と書いていました。試して確認したら、これは実現できませんでした。

| 対象 | 実際に確認結果 |
|---|---|
| Firestore の日次 読取 / 書込 / 削除の上限 | 上書き不可（API が「固定値」フラグで拒否する）。表示されている値は無料枠の境界を示すだけで、従量課金では超過分は課金されエラーにはならない |
| Cloud Storage の egress | 上書きは可能だが、単位が「ビット毎秒」のレート制限で、日次総量の上限にはならない（時間 × レートでコストは積み上がる） |

レート制限は採らない判断にしました。理由が 5 つあります。

1. プロジェクト全体の共有プールなので、**同時利用者が増えるほど全員が遅くなる**
2. 公式ドキュメントに「requests can be **throttled** or can be rejected with a retryable 429」とあり、**画像が読めずエラーになりうる**
3. バックアップの復元が 429 になると、機種変更のデータ移行が失敗する
4. そもそも総量の上限にならない
5. 公開コンテンツが伸びたとき = コストリスクが顕在化する場面 = 一番 UX を守りたい場面で効いてしまう

→ 設計書の 2 段目を訂正し、3 段目（予算キルスイッチ）を「任意」から「必須」に格上げしました。

### クライアント認証（App Check）は転送量を守らない

これも重要な発見でした。

公開画像は **ダウンロードトークン付きの URL** で配信していて、この URL は アクセス制御ルールもクライアント認証もバイパスします。

→ コストの主要ドライバである転送量に対して、App Check は防御になりません。「App Check を入れたからコストは守られている」は誤りです。

### 予算アラートは「課金停止」ではない

当たり前ですが最初に誤解しました。予算を設定してもアラートが飛ぶだけで、課金は止まりません。止めるには**請求先アカウントのリンクを解除する**しかなく、それを自動化するのがキルスイッチです。

- 課金アカウントの通貨が JPY なので、USD 指定の予算作成は `INVALID_ARGUMENT`（REST では追加のヘッダも必要）
- 依存パッケージを明示的に足さないとデプロイが失敗することがある（フレームワークの依存ツリーに実在しないパッケージを内部で要求していた）
- 通知を publish するサービスアカウント名は決まっている（推測した名前は存在しなかった）
- コンテナレジストリのクリーンアップポリシーを設定する ——コスト制御の仕組みそのものがコストを垂れ流していたら本末転倒なので、ビルド成果物は 1 日で削除するようにしました
- 判定ロジックの依存をゼロにして、CI であえて依存をインストールせずにテストした（「判定部分は依存ゼロ」自体をガードにできる）

## サイトのデザインは試した結果直した

最後に、サイトの見た目の話です。「簡素すぎる」という指摘の原因を、感覚ではなく計測で特定しました。

| 症状 | 実際の値 | 対応 |
|---|---|---|
| 見出しの階層が成立していない | h2 が 17px / 本文 16px = 1.06 倍 | 1.38 倍に |
| モバイルでタップしづらい | タップ領域 26px（iOS 推奨の 44px 未満が 9 件） | 0 件に |
| ナビが折り返して被る | 6 項目で 2 行 | 横スクロールの 1 行バーに |
| 3 列表が画面からはみ出す | — | 表だけコンテナ内スクロール（ページ全体は横スクロールさせない） |
| ノッチ付き端末で端が詰まる | — | `env(safe-area-inset-*)` を追加 |

`hidden` 属性は author 側の `display` 指定に負けます。`[hidden] { display: none !important }` を書くまで、`href="#"` の死んだボタンが実際に描画されていました（実ブラウザで開いて初めて気づいた）。

**測り方の注意**: iframe 経由でレイアウトを測ると嘘をつきます（スクロール位置のクランプが別扱いになり、「17px 切れている」と誤検出しました。直接開くと正常）。計測は必ず実ページを直接開いて行います。

## バックエンドと OAuth で届くメール

| 件名 | 送信元 | 届くタイミング |
|---|---|---|
| Welcome to Firebase | `firebase-no-reply@google.com` | プロジェクトを作った時 |
| Google Cloud の無料トライアルへようこそ | `googlecloud@google.com` | 請求先アカウントを作った時 |
| [Firebase] プロジェクト「〈アプリ名〉」が従量課金制の Blaze のお支払いプランにアップグレードされました | `firebase-noreply@google.com` | 従量課金プランに上げた時 |
| **[Action Needed] OAuth Verification Request Acknowledgement** | `api-oauth-dev-verification-reply+〈ID〉@google.com` | 検証申請の受付時と、**指摘が出るたび同じ件名で** |
| Google アカウントの一部のデータを GitHub と共有しました | `noreply-accounts@google.com` | GitHub OAuth の連携を通した時 |

OAuth の検証メールで注意した点です。

- **受付通知と指摘が同じ件名で届きます。** 私のところには同じ日に 2 通来ていて、2 通目が指摘でした。件名で区別できないので、本文まで開かないと進捗が読めません
- **送信元アドレスに申請ごとの ID が入っています**（`+〈ID〉` の部分）。返信はこのアドレス宛のスレッドで行います。Console から再提出するだけでは審査が進まないので、このメールを消さないでください

## まとめ — 周辺インフラのチェックリスト

```
【最初に決める（後から変えられない）】
□ /terms /privacy のパス（アプリが直接開く + ストアにも登録する）
□ 事業者サイト（apex）とアプリ用サブドメインを分ける
□ 事業者サイトは申請より先に公開する（審査の参照先になる）
□ 日英の URL 設計（接頭辞なし固定 / 自動リダイレクトなし）
□ メールアドレスを役割で分ける（事業体レベル / アプリ固有 / レポート受け）

【DNS】
□ apex のカスタムドメインは DNS が自動で作られない
□ apex に CNAME を置く前に MX / SPF / DMARC が引けることを権威 DNS で実測する
□ 法務ページの本文は仕様書ではなく実装から書く
□ 公開の判定は「実 URL で 200 + 本文長 + 未完成マーカー 0 件」

【着地ファイル】
□ AASA は _headers で application/json を明示（200 でも Content-Type が違うと機能しない）
□ assetlinks に入れるのは「アプリ署名鍵」の SHA-256（ストア登録が前提）
□ 検証はオンデバイスで（pm get-app-links）
□ 対象パスの一覧をアプリ側のルーティング定義と突合する
□ 各パスの着地ページも用意する（無いとリンクを踏んで 404）

【ホスティング】
□ リダイレクトの宛先に末尾スラッシュを付ける（308 でクエリが消える）
□ プレビュー用ドメインの重複対策がリポジトリ外にないか確認する
□ デプロイ直後の 1 回目は旧版が HTTP 200 で返る（期待値が来るまでリトライ）
□ curl は -L を付ける

【メール】
□ 転送サービスは受信専用。返信手段（SMTP リレー + SPF / DKIM / DMARC）まで用意する
□ OAuth 同意画面のサポートメールの制約を確認（Google グループが必要になる場合がある）
□ Google グループは「メッセージの管理 = 管理しない」にする
□ 重要な通知が来るアドレスのフィルタを、申請より先に作る
□ 本番 HTML のメールアドレスが難読化されていないか（grep が空振りする）

【外部から叩ける口を置くなら】
□ CAPTCHA / 同一オリジン限定 / サイズ上限
□ 投稿本文を Markdown として解釈させない
□ キャッシュキーを固定する（外部 API のレート制限を枯らされる）
□ 識別子を受け取るならプライバシーポリシーに節を足す

【シークレット】
□ 「Secret はホスティング / ビルド時に埋め込む値は CI」の切り分け
□ CAPTCHA のホスト名をプレビュー環境ぶんも登録する

【外部連携 / OAuth】
□ 使う API を有効化する（未有効だと全呼び出しが 403・モックでは検知できない）
□ 使わない API は有効化しない（最小権限）
□ 機密スコープを減らす方向で組む（per-file 権限で足りないか）
□ 「テスト中」のままだと refresh token が 7 日で失効する
□ 差し戻しはプライバシーポリシー（Google ユーザーデータの共有先 / 保護手段）で来る
□ 指摘メールに返信しないと審査が進まない
□ 審査中は公開ステータス / ユーザータイプ / スコープを触らない
□ 承認後もスコープ追加・同意画面の変更で再審査になる
□ 審査用のデモ動画は消さず非公開にする（承認後に切り替える）
□ 承認が効いたことは実機で警告画面が出ないことで確認する
□ ドメイン所有権は推測ではなく DNS を直接引いて確定する

【バックエンド】
□ Authentication は明示的に初期化が要る
□ プロバイダごとに「API でよいか Console が必要か」が違う
□ 設定ファイルに後から生成されるキーがある（有効化後に再取得）
□ サービスアカウントのプロジェクト IAM は Console の招待と無関係
□ 実設定ファイルを置いたらテストが本番へ通信しないか確認する
□ Debug の entitlements が古い前提のまま残っていないか
□ 外部連携の client_id が実際に配線されているか（モックだと気づけない・Release で fail-fast させる）
□ Rules / Functions は「マージしても本番に反映されない」前提で突合する
□ 反映は「関数 → ルール」の順（逆順だと窓が開く）
□ デプロイ後に本番を再取得してリポジトリと完全一致を実測する
□ インデックスは READY になるまで追跡する
□ App Check の強制化は最後（切り戻し手順を先に用意する）

【コスト防御】
□ 日次上限で超過分をエラー化する方法は存在しない（上書き不可）
□ 予算アラートは課金停止ではない
□ クライアント認証は転送量を守らない（トークン付き URL はバイパスする）
□ 止める手段は請求先アカウントのリンク解除だけ
```

この領域の教訓は 1 つに集約できます。「200 が返っている」「画面に出ている」「マージした」は、どれも動いている証拠になりません。判定は必ず、その工程の実体（Content-Type / 本番の ruleset / 実データ / 実ブラウザ）で行うことです。

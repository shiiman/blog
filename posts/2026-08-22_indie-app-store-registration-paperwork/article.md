## はじめに

個人開発の iOS / Android アプリ **Bucket List Commit** を App Store と Google Play へ同時提出しました。この記事はその一番最初にやった「アプリ開発とまったく関係ない事務手続き」の記録です。

コードは 1 行も書かないのに、全工程で一番リードタイムが長いのがここでした。しかも依存が一本道で、並行できません。

私はここで、「並行できると思っていたものが直列だった」「無料ルートの存在に気づかず有料コースを勧めた」「黒塗りが透けていた」という 3 種類の失敗をしました。同じ道を通る個人事業主が同じ穴に落ちないように残します。

> シリーズ「ストアに出すまで」全 5 本の 1 本目です。アプリの中身と実装は[別シリーズ](/engineering/app/indie-bucket-list-app-overview/)にまとめました。
>
> この記事は「ストアに登録する前」だけを扱います。ストア側の手順は [App Store Connect 編](/engineering/app/app-store-connect-review-submission-notes/) / [Google Play Console 編](/engineering/app/google-play-console-review-submission-notes/) に、全体像は[全工程まとめ](/engineering/app/personal-app-cross-store-release-full-journey/)にあります。

### この記事の表記について

固有の識別子は伏せています（屋号は `Example Works`、住所は架空のものに置き換え）。アプリ名 `Bucket List Commit` は実名です。

### 前提

- **個人事業主**（法人ではない）。開業届は既に提出済みだが**屋号欄が空白**だった
- 名義は Apple = Individual（個人）/ Google Play = 組織アカウント
- 課金あり・配信地域は日本 + 米国
- 費用は Apple Developer Program ¥12,980/年 + Play $25 のみ（D-U-N-S は 0 円で取れた）

## 順番を間違えると数週間戻る

```
屋号を決める
  └→ 屋号入りの開業届を取り直す（税務署）
        ↑ D-U-N-S の必要書類がすべて「屋号の記載のあるもの」だから、これが前提
     └→ D-U-N-S 番号を取得
           ↑ Play の組織アカウントの必須条件
        └→ D&B のデータベースに反映されるのを待つ（数日〜2週間）
              ↑ 反映前に Play へ入力すると弾かれる
           └→ Play で組織アカウントを作成
              └→ 本人確認（組織の登録書類）
                 └→ 15% 手数料の登録 / 電話番号の確認 / デベロッパー名の変更
                       ↑ 本人確認が完了するまで、この 3 つは解禁されない
```

私は当初「開業届の取り直しと D-U-N-S 申請は並行できる」と説明していました。誤りです。D-U-N-S の必要書類が屋号入りの書類なので、開業届が先に手元にないと申請自体ができません。

一方で、この待ち時間の裏では別の作業を並行できます。D-U-N-S 待ちの間に Firebase の本番構築・法務ページの公開・署名周り・Apple Developer Program の加入（D-U-N-S 不要）を進めました。外部待ちを直列にしないことが、この工程で唯一効く高速化です。

## 1. 屋号を決める

屋号は Play のデベロッパー表示名になりうる名前で、しかも後続の全書類の正典になります。

アプリ名を屋号にしませんでした。理由は、将来ほかのアプリを出したときも**同じ開発者名で並ぶ**からです。アプリ 1 本の名前を屋号にすると、2 本目以降が不自然になります。

正規表記を先に決めて固定します。

- 半角スペースは 1 つ
- 各単語の頭のみ大文字
- 末尾のピリオドなし
- 法人格サフィックス（Inc. / LLC など）を付けない

これを**4 か所で完全一致**させます。

1. 開業届の屋号欄
2. D-U-N-S の事業体名
3. Apple の Legal Entity Name
4. Play の組織名

揺れると D&B の照合や Apple の実体確認で弾かれます。自宅住所のローマ字表記も同じで、D-U-N-S と Apple はどちらも英語表記を要求するので、こちらも 1 か所に固定しておきます。

```
法人名   Example Works
番地     1-2-3 Examplecho Example Building 101
市区町村 Chiyoda-ku, Tokyo-to
都道府県 Tokyo
郵便番号 100-0001
```

建物名・部屋番号を番地欄に含めるのを忘れないでください。Play は完全な住所を公開し、D-U-N-S との一致が要求されるので省略できません。最初、建物名を落とした案を書いてしまいました。

商標のスクリーニングは屋号とアプリ名の両方でやります（調べ方は [App Store Connect 編](/engineering/app/app-store-connect-review-submission-notes/)に書きました）。

私が屋号を選んだ基準は 2 つでした。

1. **既存資産との一貫性** —— 既に持っているドメインや別プロダクトと同じ系列の名前にする
2. **アプリ名と開発者名が同一になるのを避ける** —— 屋号はストアで**アプリ名のすぐ下に出る開発者名**になります。1 本目のアプリ名を屋号にすると、2 本目以降で「別アプリなのに開発者名が 1 本目のアプリ名」という不自然な並びになります

## 2. 屋号入りの開業届を取り直す（税務署に行く話）

**なぜ必要か**: D-U-N-S の必要書類が**すべて屋号の記載があるもの**だからです。

> 開業届の控え / 確定申告書 / 営業許可証 / 公共料金請求書 / 屋号名義の通帳 のいずれか

私の開業届は**屋号欄が空白**でした。この状態では 1 つも要件を満たしません。

代替書類はどれも「既に屋号で事業をしている証拠」なので、屋号を新しく決めた場合は**どれも持っていません**。だから開業届の出し直しが最短になります。

| 代替になる書類 | 屋号を新規に決めた場合 |
|---|---|
| 確定申告書のコピー | 次の申告まで手に入らない |
| 営業許可証 | 業種によっては存在しない |
| 公共料金の請求書・領収書（屋号名義） | 屋号名義の契約が無い |
| 屋号名義の銀行口座の通帳（表紙） | 屋号口座を作るほうが時間がかかる |

**屋号専用の変更届は存在しない**

「屋号を追加する届」というものはありません。「個人事業の開業・廃業等届出書」を屋号記載で再提出します。

- 「その他参考事項」欄に**屋号を追加する旨**を書く
- **開業日は当初の日付をそのまま書く**（今日の日付にしない）。当初の「提出日」と「開業日」を混同しないこと
- **費用はゼロ**
- 提出期限（開業日の翌月から 2 か月）は**初回提出の話**で、屋号追加の再提出は対象外

確定申告書の屋号欄に書く方法もありますが、**次の申告まで書類が手に入らない**ので、急ぐなら不適です。

### 2025年1月から収受日付印（受付印）が全国一律で廃止された

これは知らないと詰みます。紙で提出しても控えに受付印は押されません。提出した事実を証明する手段は次の 3 つです。

| 手段 | 入手 | 前提 |
|---|---|---|
| e-Tax の「受信通知」/「電子申請等証明書」 | 即時 | 電子申請した場合 |
| 「申告書等情報取得サービス」で e-Tax から PDF 取得 | 数日 | マイナンバーカードが必須 |
| 窓口で交付されるリーフレット『申告書等の提出について』 | 即時 | 窓口で希望する（郵送提出でも返信用封筒を同封すれば返送される） |

3 番目のリーフレットが、後の Play の本人確認で実際に通った書類です。「（本日）、書面で提出された申告書等を受け付けました。」と大きく書かれており、**日付と税務署名の記載欄がある**（窓口で記入して交付される）ので、実質「受付印付きの控え」と同等に機能します。詳しい経緯は [Google Play Console 編の「本人確認」](/engineering/app/google-play-console-review-submission-notes/)に書きました。

> **教訓**: 制度が廃止されたときは「代替措置が何か」まで調べる。
> 私は「収受日付印が廃止された」ことは把握していたのに代替措置を知らず、そのせいで「納税証明書を取ってきてください」という**不要な遠回り**を案内してしまいました。

### Mac から e-Tax を直接叩く経路が無い

「e-Tax で出せばいい」という案内も誤りでした。3 段構えで詰みます。

1. 国税庁の案内は、開業届の e-Tax 提出を「**e-Taxソフト**で作成後」と記載している
2. e-Taxソフト（WEB版）の作成可能手続一覧に開業届が無い（所得税は青色申告承認申請と消費税関連のみ）
3. e-Taxソフト（ダウンロード版）は Windows のみ

→ **オンラインで出すなら民間の会計ソフト経由**です（クラウド確定申告サービスの「開業届の電子申告」機能。**スマホアプリ限定**で、電子証明書入りのマイナンバーカード + 読取対応スマホ + 利用者識別番号 16 桁が必要）。

私は結局**紙で窓口に提出**しました。TSR 側の要求が「控え（屋号の記載のあるもの）」で受付印を求めていなかったこともあり、自分保管の控えのコピーで足りると判断しています。

開業届にはマイナンバー欄があります。第三者に渡すならマスクが必要で、そこにもう 1 つ罠があります。

## 3. 黒塗りは「注釈レイヤー」だと透ける

これは実際に書類が却下された話です。

iOS / macOS プレビューの「マークアップ」で塗った黒塗りは、元画像に焼き込まれません。PDF の注釈（`/Type /Annot`）として**上に乗っているだけ**で、下の内容はそのまま PDF 内に残ります。

開業届のマイナンバー欄を iPhone のマークアップで黒塗りしてアップロードしたところ、こう却下されました。

![Google の本人確認画面。「確認情報に問題が見つかりました」「アップロードする書類が有効であることをご確認ください」と表示されている](./assets/play-verification-rejected.png)

PDF の中身を実測するとこうでした。

| 項目 | 値 |
|---|---|
| `/Producer` | `iOS Version …` |
| `/Annots` | 2 個（うち 1 つがマイナンバー欄の矩形） |
| 画像 XObject | 3 個（本画像 + 6×8 の overlay 2 個） |
| ファイルサイズ | 3,145,721 バイト（3 MiB の 7 バイト下 = 上限ギリギリ） |

元画像のマイナンバー欄のピクセル統計は、こうなっていました。

```
輝度 平均 231.7 / 標準偏差 51.4   ← 白い紙に文字が残っている
```

= 黒塗りは効いておらず、マイナンバーは実質そのまま送信されていました。

**正しい手順**

1. 画像そのものを塗りつぶして再エンコードする（注釈を乗せるのではなく、ピクセルを潰す）
2. **焼き込めたことをピクセル統計で検証する** ——該当矩形の**最大輝度が 0 / 標準偏差 0.0** であること。**目視では注釈と区別できません**
3. PDF ではなく JPEG / PNG で提出する（注釈レイヤーを持てない形式にする）

この方法なら、数値そのものを画面に出さずに「マスクできているか」を判定できます。機密欄の検証は必ずこの統計方式でやるべきです。

> **教訓**: 「マスクしてください」と伝えるときは、マスクの"方法"まで指定する。
> 指定しないと、マスクできない方法で実行されます。

さらに皮肉なことに、Play の本人確認では、黒塗りそのものが却下要因になり得ます。Play Console のホームに「書類を編集したり操作したりしないでください」と常時表示されており、却下メールにも「書類の一部が隠れたりしている場合…受け付けられません」と書かれています。最終的に**マイナンバーを隠さない原本**で通しました。

> 渡す先によって「マスクすべき」と「マスクしてはいけない」が逆になります。提出要件を先に読んでおきましょう。

## 4. D-U-N-S 番号を取る

D-U-N-S = D&B（Dun & Bradstreet）が事業体に割り当てる 9 桁の識別番号で、**Play の組織アカウント**と Apple の Organization 加入の必須条件です。

最重要の性質: 事業体に 1 つで、用途に紐づきません。どの経路で取っても両ストアで使えます。

### 3 つのルートの比較

| ルート | 期間 | 費用 | 必要書類 |
|---|---|---|---|
| A. 日本の窓口（TSR）無料コース | 30営業日（約1.5か月） | 0 円 | 屋号入り書類 + 在籍が確認できる書類 |
| B. 同 有料コース | 7営業日 | 15,000円（税別・実質 16,500円） | 屋号入り書類のみ |
| C. Apple の専用ページ | 数日（実測 5 日） | 0 円 | 書類提出なし |

C が正解でした。最初 A を選び、料金表を精読して B に変更し、最後に C の存在に気づきました。窓口側のユーザガイドの**冒頭**にこう書かれています。

> Apple Developer との取引の方は Apple Developer 専用ページから無償（且つ状況によっては短納期）で取得できる

「Apple は Individual で加入するから、Apple のルートは使えない」と判断したのが誤りでした。D-U-N-S は事業体の識別番号なので、Apple 経由で取っても Play の組織アカウント登録に使えます。これで 16,500 円を節約しました。

> **教訓**: 有料サービスを検討する前に「専用ページ・無料ルートの有無」を確認する。

A と B の差は費用だけではありません。無料コースは**必要書類に「在籍が確認できる書類」が追加**されます（個人事業主でも**名刺で可**。ガイドの例に最初に挙がっています）。有料コースはこれが不要です。当初は無料を選んでいましたが、料金表を精読して「無料は合計約 2 か月かかり、組織化の期間面のメリットが消える」と分かって再判断しました。

### Apple ルートと日本の窓口は「排他」ではなかった

これは実際に申請して初めて分かったことです。

Apple の専用ページから申請すると、D&B の日本側の実務は結局その窓口（TSR）が代行します。申請後に窓口の担当者から確認メールが届き、**事業内容の照会（数項目）に答える**流れになりました。

つまり「Apple ルート」と「窓口ルート」は**同じ実務の入口が違うだけ**で、Apple 経由なら手数料と書類提出が省けるという関係でした。

- 実際にかかったのは **申請から 5 日**。Apple の公式記載も「requesting 後 up to 5 business days」で一致します
- 私が事前に書いていた「無料コース = 30 営業日程度」は**この案件には当てはまりませんでした**

### Apple 経由の申請で気をつけたこと

- 申請 URL: `https://developer.apple.com/enroll/duns-lookup/`（Apple ID でのサインインが必要）
- まず既存の事業体を検索し、見つからなければ「検索で組織が見つからない場合は、D&Bに情報を送信して、**無料で**D-U-N-S番号の取得を申請することができます」に進む
- 入力は半角英数字のみ。日本語も中黒（`・`）も通りません（カンマは通りました）
- **建物名・部屋番号を番地欄に含める**（Play は完全な住所を公開し、D-U-N-S との一致が要求されるので省略できません）
- 送信した表記が、以降すべての正典になります（法人名 / 番地 / 市区町村 / 都道府県 / 郵便番号 / 電話番号 / 氏名 / 仕事用メール）
- 英文商号に事業所名（支店名など）は含められません（窓口のガイドに明記）
- 電話番号はハイフンなしの形式でハマる報告が複数あります。指示された形式に厳密に従うこと（Play の登録でも同じで、`+81 80-xxxx-xxxx` は弾かれ `+81xxxxxxxxxxx` で通りました）
- 住所のローマ字表記は「番地 → 市区町村 → 都道府県 → 郵便番号 → Japan」の順で 1 回決めて固定する
- 連絡先メールは**独自ドメイン**にしておくと後の工程で使い回せます。ただし転送メールは迷惑メール判定されることがあるので、確認メールを見落とさないようフィルタを先に作っておくこと（私は 1 つ作り忘れていました）

### 発行された名前が全大文字に正規化された

これは知らないと後で困ります。

```
申請時に送った名前:  Example Works
D&B が発行した名前:  EXAMPLE WORKS   ← 全大文字に正規化された
```

しかもこれがそのまま Play の組織名・デベロッパー名として入ります。言い換えるとストアでユーザーに表示される名前が全大文字になります。

デベロッパー名だけは後から正規表記に直せます（画面に「組織の正式名とは異なる名前を指定できます」と明記されており、変更しても D&B 照合は壊れません）。ただし**審査中は触らない**ほうが安全です。

### D-U-N-S 取得中に届くメール

外部待ちの工程なので、進捗はメールでしか分かりません。実際に届いた順番と間隔です。

| 件名 | 送信元 | 意味 |
|---|---|---|
| DO NOT REPLY: Inquiry #〈番号〉Received - Update for〈屋号〉 | `donotreply@iresearch.dnb.com` | 申請を受け付けた |
| ＜DUNSナンバー：ご確認＞〈屋号〉様 | `duns_mini@tsr-net.co.jp` | 日本の窓口から事業内容の照会。**これに返信しないと止まる** |
| Re: ＜DUNSナンバー：ご確認＞〈屋号〉様 | `duns_mini@tsr-net.co.jp` | 返信後のやり取り |
| DO NOT REPLY: Resolved Inquiry #〈番号〉(Case #〈番号〉) - Update for〈屋号〉 | `donotreply@iresearch.dnb.com` | 発行された |
| Apple Duns Update | `noreply-appledev@email.apple.com` | Apple 側に反映された |

私の場合の間隔はこうでした。

- 申請の受付 → 窓口の照会まで **約 10 時間**（同日）
- 受付 → `Resolved`（発行）まで **5 日**
- 発行 → Apple 側への反映まで **1 日**

Apple は「D-U-N-S 受領後、Apple が D&B から情報を受け取るまで最大 2 営業日」「2 週間を超えたら D&B に問い合わせよ」と案内しています。**警告よりずっと早く終わることがある**ので、待ちの想定は幅を持たせておくのがいいと思います。

### 「Organization で登録しろ」というメールに乗らない

D&B のデータが反映されると、Apple からこういうメールが来ます。

> If you have the legal authority to bind your company... you can use this number to enroll for your company. Before enrolling, please ensure that EXAMPLE WORKS is a legal entity.

屋号は trade name であって legal entity ではありません。Apple は DBA / trade name を受け付けません。Apple = Individual のままにして、D-U-N-S は Play の組織アカウントのためだけに使いました。

「番号を取ったから Organization にできる」ではないという点に注意してください。

### 発行されてもすぐ Play に入力できない

D&B のグローバルデータベースに反映されるまで待ちが入ります。窓口からも明示的に警告されました。

> グローバルのデータの更新につきましては、今回のデータ更新から**数週間程度お時間がかかることがある**ようでございます

**実際は 1 日**でした（発行の翌日に反映を確認）。**警告よりずっと早いこともある**ので、待ちの想定は幅を持たせておくのが正解です。

反映されたかの確認方法を 3 つ試して、使える順序が分かりました。

| # | 手段 | 評価 |
|---|---|---|
| 1 | Apple の D-U-N-S Lookup で、申請時と同じ検索をやってヒットするか | ○これが本命。申請時は「見つからない」状態だったので、ヒットに変わることが反映の判定になる。Apple 公式も「D-U-N-S 受領後、Apple が D&B から情報を受け取るまで最大 2 営業日」「2 週間を超えたら D&B に問い合わせよ」と記載 |
| 2 | 窓口の担当者に聞く | ○申請時にメールのスレッドが開いているので、そこに返信するのが最短かつ無料。日本側の運営元そのものなので回答は権威がある |
| 3 | Play Console に実際に入れてみる | 最終ゲート。不一致・未反映だとメール + Console に「組織の名前または住所の確認が行われていません」バナーが出る。再試行はできるので、1 がヒットしてから試すのが安全 |

D&B 公式の無料 Lookup（`dunsnumberlookup.dnb.com`）は日本企業に使えません。国リストを列挙して実際に確認したところ、選択肢は 35 か国のみで Japan がありません（欧州 28 + カナダ + 南部アフリカ 4 + オーストラリア / ニュージーランド。**米国すら無い**）。`Jap` と入力しても `No items found` になります。日本企業のデータ窓口は D&B ではなく国内の提携企業なので、あのツールの管轄外です。

### Play に入れる前に「D&B 側」を確定させる

一番大事な注意点です。

照合は「法人名・住所が D-U-N-S レコードと完全一致するか」で行われます。そして、住所・名称は Play Console 側では直せません。D&B 側を直してから、また反映を待つことになります。

→ Play に登録する前に、D&B 側の表記を確定させてください。

## 5. 契約・税務・銀行は「両ストアで 2 つある」

**私が構造的に漏らした項目**なので、独立させて書きます。

私のタスクリストは「契約 / 税務情報 / 銀行情報」を **Play の配下**に置いていました。そのため、Apple 側にも独立した「有料アプリ契約 / 税務情報 / 銀行情報」があることが、リストから抜けていました。

実害が出ました。

Apple の有料アプリ契約が「有効」にならないと、iOS のアプリ内課金商品は 1 つも作れず、Sandbox の課金テストもできません。API で商品が 0 件・グループが 0 件なのを見て「API の使い方が悪いのか」と疑って時間を使いました。原因はこれでした。

「課金の検証はストア登録と並行できる」という前提も成立していませんでした。

### 流用できるものと、できないもの

一方で、片方で確定させた入力値はもう片方に流用できます。

| 項目 | 流用 |
|---|---|
| 米国の税務フォームの入力値（氏名 / 居住国 / 外国 TIN / 租税条約の条項と税率） | ○そのまま使える |
| 受取口座 | ○同じ個人口座で両方いける（Apple は Individual = 本名登録なので名義が一致する） |
| 口座種目の既定値 | ×ストアごとに違う（一方は「普通」が既定、もう一方は「貯蓄」が既定） |

有料アプリ契約は一度同意すると取り消せません（公式に明記）。規約に出てくる「税務上の帰結は自身の法務・税務アドバイザーに相談する責任がある」は定型文です。

クレジットカードの明細に出る名前は「屋号」で、アプリ名ではありません（販売者単位の設定なので、将来の全アプリの明細に出ます）。同じく販売者プロファイルのサポートメールは事業体レベルの窓口で、アプリ固有の連絡先とは別に用意しました。

## 6. API でできること・できないことの境界

事務手続きをどこまで自動化できるかは、先に把握しておくと計画が立てやすいです。境界は両ストアでほぼ同じでした。

|  | API |
|---|---|
| アカウント登録 / 本人確認 / 契約同意 / 税務 / 銀行 | ×両ストアとも非対応（手作業） |
| アプリレコードの作成（= 名前の確保） | ×両ストアとも非対応 |
| コンテンツレーティングの質問票 | ×非対応（画面のみ） |
| 内部テスターの個別指定 | ×非対応 |
| ビルドのアップロード | ○両方可 |
| 課金商品の登録 | ○両方可 |
| ストア掲載情報（テキスト / 画像） | ○両方可 |

「アカウントを作る系」は全部手作業で、「作った後にモノを入れる系」は全部 API 可——と覚えておくとだいたい合っています。

## 7. アカウント種別の判断は 3 回ひっくり返った

この判断は 1 日のうちに 2 回改訂しました。恥ずかしい記録ですが、**どこで判断を誤ったかが再現性のある教訓**なので残します。

| # | 決定 | 覆った理由 |
|---|---|---|
| ① | 両ストアとも個人アカウント | 12人×14日のテスト要件が「個人アカウント限定」だと判明 |
| ② | 両ストアとも組織アカウント | Apple の Organization は屋号（trade name）を使えないと判明 |
| ③ | Apple = Individual / Play = 組織（最終） | — |

### ①→② で見落としていたのは「依存関係」だった

12人×14日の要件は、公式ヘルプのタイトル自体が限定していました。

> **新しい個人用デベロッパー アカウント向け**のアプリテスト要件

本文も「〜以降に**個人アカウント**を作成したデベロッパーは…」と書いていて、組織アカウントへの言及がありません。

「アカウント種別の選択が、クリティカルパスそのものを消せる」という構造でした。最初の比較で「期間」「費用」「公開範囲」を並べたのに、「種別によって要件自体が消える」という依存を見落としていました。

> **教訓**: 選択肢を比較するときは「その選択で消える要件はないか」を軸に入れる。
> コストや期間の比較表を作ると、その表に無い次元（要件の有無）を見落とします。

### ②→③ で覆ったのは原文を読んでいなかったから

Apple の Organization の要件には、はっきりこう書かれています。

> Your organization must be a legal entity that can enter into contracts with Apple. We do not accept DBAs, fictitious business names, trade names, or branches.
> If you're an individual or sole proprietor/single person business, you'll need an Apple Account…

**屋号は trade name そのもの**で、個人事業主は Individual に案内されています。

日本語のブログには「個人事業主が Organization に変換できた」という事例もありますが、**古い時期か例外と判断しました**（原文がここまで明示しているので）。

> **教訓**: 「できた事例がある」を根拠にする前に、公式の原文を読む。

### 公開項目の解釈が曖昧なところは、実画面で確認する

Play のヘルプは組織アカウントの公開項目を「デベロッパーの**氏名**・正式な住所・メール・電話番号」と書いていますが、この「氏名」が組織名を指すのか担当者の本名を指すのかが曖昧でした。

本名が公開されるなら「屋号表示で本名を出さない」という副産物は失われます（12人免除という主目的は変わらないので決定自体は覆りませんが）。→ **登録時に実画面で確認する**タスクとして持ち越しました。

ヘルプの文言が両方に読める場合、「たぶんこっち」で進めてはいけません。登録は不可逆な操作を含みます。

## 8. アカウント名義の可逆性 — どの向きの変更が不可能か

先に調べておくと、迷う時間が減ります。

|  | 可能 | 不可能 |
|---|---|---|
| Apple の種別 | Individual → Organization（D-U-N-S + 電話確認） | — |
| Play の種別 | 個人 → 組織 | 組織 → 個人 |
| Apple の氏名 | — | 加入フローで「続ける」を押した後は変更不可（政府発行の身分証と一致必須） |
| Apple のデベロッパー表示名 | — | Individual は本名固定 |
| Play のデベロッパー名 | いつでも変更可（審査あり・保存 ≠ 反映） | — |

私は「Apple は後から組織化できる / Play は組織から個人に戻せない」を確認したうえで、Apple = Individual・Play = 組織という非対称な構成を選びました。

公開範囲も先に確認してください。

|  | 公開されるもの |
|---|---|
| Play の組織アカウント | 住所 + 電話番号（組織の公開項目） |
| Apple の Individual | 本名。住所は EU 配信時のみ（DSA のトレーダー申告） |

バーチャルオフィスを使わないなら、**自宅住所が公開されることを受け入れる判断**が要ります（私はそうしました）。逆に言うと、追加費用ゼロで済ませるならここが唯一のトレードオフです。

### ほかに「取り消せない」もの

| もの | 注意 |
|---|---|
| 有料アプリ契約への同意 | 一度同意すると取り消せない（公式に明記） |
| D&B に登録した名称・住所 | ストア Console 側では直せない。D&B 側を直して反映を待つ |
| Apple の加入フローで確定した氏名 | 「続ける」の後は変更不可・政府発行の身分証と一致必須 |
| 課金商品の ID | 削除しても再利用できない・両 OS で一致必須 |
| ストア掲載の「無料 / 有料」区分 | 公開後は変更不可（公開前なら変えられる） |

### 引っ越したときの手順

公開する住所は「最新であること」がポリシー要件です。放置するとポリシー違反でアカウント停止のリスクがあります。

順序は「身分証の住所変更 → お支払いプロファイルの更新」です。逆順にすると、確認のために出す身分証と登録住所が食い違います。

## 9. 2FA と復旧手段 — ここを失うと全部失う

アカウントを失うと、アプリも売上も引き継げません。リリース直前の項目として最後に固めました。

本当は「最後」ではなく「最初」にやるべきでした。Apple の Account Holder の Apple ID は**後から変更するのが極めて困難**です。要するに、こういうことです。

> 加入する前に、その Apple ID の 2 ファクタ認証と信頼できるデバイスの登録を済ませておく

のが正しい順序でした。加入を先に済ませてしまったので、「復旧手段が電話番号 1 つだけ」の状態で加入したことになります。

**Google 側**

- 2 段階認証 ON + **バックアップコードを保管**
- 復旧用の電話 / メールの生存確認

### Apple 側 — バックアップコードという概念が存在しない

これが一番の発見でした。Apple の復旧手段は次の 3 つで、Google の「バックアップコード」に相当するものがありません。

| 手段 | 私の判断 |
|---|---|
| 信頼できる電話番号 | 2 つ目は追加しない（本人が使える番号が 1 つしかないため） |
| 復旧用連絡先 | 設定できなかった |
| 復旧キー | 設定しない |

- 復旧キーは設定しないことにしました。失うとアカウントに永久にアクセスできなくなり、Apple サポート経由の救済も閉ざされるためです。「復旧手段だから増やせば安全」とは限りません
- 復旧用連絡先は実際に試して設定できませんでした。設定変更は Web からできずデバイスが必須（iOS 15 / iPadOS 15 / macOS 12 以降）で、相手の Apple ID にも条件があります（13 歳以上 / iOS 15 以降 / 2FA 有効 / パスコード設定済み）。同一人物の別 Apple ID を指名する案も、成立を確認できませんでした

代わりに効いたのは「開発機の Mac を信頼できるデバイスにする」ことでした。開発者 Apple ID で Mac にサインインすると、2 ファクタ認証の確認コードの受け取り先が「電話番号 1 つだけ」の状態から改善します（iCloud の同期項目は OFF にして開発機を汚さない運用）。

ただし「デバイス」一覧に Mac が載っていても、確認コードを受け取れる「信頼できるデバイス」とは限りません。動かしてみると、iCloud には未サインインの状態でも、Xcode や Developer サイトのサインインだけでデバイス一覧には載ります。一覧に出ていることは根拠になりません。

残ったリスクは「電話番号 1 つ + メール 1 つ + Mac 1 台」です。予備メールの追加は電話番号不要で Web だけで完結するので、ここが一番安い改善なのに私は未実施でした（ただし転送先が同じメールだと連鎖は切れません）。

## 10. 外部待ちの間にどう前進するか

この工程は**待ち時間の塊**です。「どれが誰にも依存していないか」を毎回洗い直して、そこだけを進めるようにしました。

### 「相手に一切依存せず今すぐできる唯一の前進経路」を探す

一番効いた判断がこれです。片方のストアの本人確認で止まっているとき、「もう片方のストアの契約・税務・銀行」は完全に独立していて、しかも課金の検証をブロックしていました。止まっている側を待つ間に、律速をもう 1 つ潰せる状態でした。

優先順位は毎回この形で書き直しました。

| 順 | やること | なぜこの順か | 外部待ち |
|---|---|---|---|
| 1 | 止まっていない側の契約・税務・銀行 | 相手に一切依存しない唯一の前進経路。しかも課金の検証をブロックしている | 数日（口座確認） |
| 2 | 止まっている側の再提出 | 書類を揃え直す | なし |
| 3 | 課金商品の登録 | 1 の完了が前提。商品 ID は両 OS 一致必須かつ変更不可 | なし |
| 並行 | ストア素材（スクショ / 説明文） | 両ストアで必要。待ちの裏で作れる | なし |
| 並行 | 実機検証のうち課金以外 | 課金だけが 1 に依存するので、それ以外は今すぐできる | なし |

### 待ちの裏で進めたもの

外部待ちが 2 つ（D-U-N-S と機密スコープ検証）走っている間に、次を並行させました。

- **バックエンドの本番構築**（名義に依存しない）
- **公式サイトと法務ページの公開** —— **これは先にやる価値がありました**。事業者サイトは D-U-N-S 申請と各種審査で「事業体の実在性」を示す参照先になるので、申請より前に公開しておくほうが順序として正しい
- **署名まわり**（Apple の配布証明書は D-U-N-S 不要 / Android のアップロード鍵はストア登録前でも作れる）
- Apple Developer Program の加入（D-U-N-S 不要なので Play と完全に並行できる）

逆に「待ちの裏でやれる」と思っていて実はできなかったものが課金の検証でした（前述のとおり有料アプリ契約が前提だった）。「並行できる」という想定は、着手前に依存を 1 回確かめるのが安全です。

```
【書類を渡すとき】
□ 黒塗りは注釈レイヤーだと透ける（ピクセル統計で焼き込みを検証）
□ 渡す先によって「マスクすべき」と「マスクしてはいけない」が逆になる

【名義を決める前に確認する】
□ どの向きの変更が不可能か（Play の組織 → 個人は不可 / Apple の氏名は確定後変更不可）
□ 何が公開されるか（Play の組織は住所 + 電話 / Apple の Individual は本名）

【最後に固める】
□ 2FA と復旧手段（Apple にバックアップコードは存在しない）
□ 重要な通知が来るメールのフィルタを、申請より先に作る
```

この工程で一番の学びは、「無料ルートや代替措置の存在を確認してから動く」ことでした。D-U-N-S も、収受日付印の代替も、どちらも「調べれば分かるのに、調べる前に動いて遠回りした」ものです。

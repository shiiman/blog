## 何を出したか

| 項目 | 内容 |
|---|---|
| アプリ | やりたいことリスト（バケットリスト）を管理するアプリ |
| iOS | Swift / SwiftUI / SwiftData / WidgetKit・最小 iOS 17 |
| Android | Kotlin / Jetpack Compose / Room / Glance・minSdk 26 |
| バックエンド | Firebase（Firestore / Storage / Auth / App Check / Cloud Functions） |
| 認証 | iOS = Apple サインイン / Android = Google サインイン |
| 課金 | サブスク 2 種 + 買い切り 6 種（両 OS で同一 ID・同一価格） |
| 配信地域 | 日本 + 米国（英語ローカライズあり） |
| 名義 | Apple = Individual（個人）/ Play = 組織アカウント |

iOS と Android を同日に提出する方針でした。理由は、両 OS 間でアカウント移行の機能を持っており、片方だけ先に公開するとデータ移行のテストが実データで走ってしまうからです。

## コードでは閉じない領域が、本番の大半だった

このプロジェクトでは、リリース関連のタスクを 1 つの Issue にまとめて追跡していました。最終的な数は**全 165 項目**です。

内訳の性質はこうでした。

| 系統 | 中身 |
|---|---|
| 実機・回帰検証 | iOS / Android / クロス OS の通し確認（最大の塊） |
| 課金・エンタイトルメント | 商品登録 / Sandbox / ライセンステスト / サーバー通知 |
| ストア掲載物 | スクショ / 説明文 ja+en / レビューノート / メタデータ |
| Console の手作業 | 内部テスター登録 / コンテンツレーティング（どちらも API 非対応） |
| バックエンド | Rules / Indexes のデプロイ / App Check の強制化 / コスト防御 |
| 法務・法令 | 規約 / プライバシーポリシー / 米国法対応 |
| 事務 | 名義 / D-U-N-S / 契約 / 税務 / 銀行 / 2FA |

165 項目のうち、コードを書く作業は 1 割程度でした。残りは「Console を触る」「実機で 1 回ずつ確認する」「書類を出す」です。

### タスク管理そのもので事故った話

参考として、追跡の失敗も残しておきます。

#### ① Issue 本文が 256KB の上限に達した

進捗ログを本文に足し続けた結果、GitHub の上限に到達しました。完了済み 112 件の記録に埋もれて、残タスクが見えなくなっていました。未完了だけを別 Issue に切り出して解決しました。

#### ② コメントのチェックリストが一度も倒されていなかった

本文に 127 個、コメントに 36 個のチェックボックスがありました。コメント側は「済 0 / 未 36」で、一度も更新されていませんでした。`gh issue view --json body` だけを見ていると 36 件を丸ごと見落とします。

→ **チェックはすべて本文に一元化**し、コメントにチェックリストを作らないルールにしました。

**③ 件数をハードコードしていて陳腐化した**

「この節の 144 件 / 済 66 / 残 78」と書いてあったのに、**実際は 184 / 99 / 85** でした。

→ 数字はハードコードせず、毎回チェックボックス行を数えて出すルールにしました。

#### ④ 「まとめて 1 件」にすると中の未完が埋もれる

`K-1` のようなグループ項目を 1 件として数えていたため、その下にある未完了 2 件が本文に埋もれて見えなくなっていました。枝番（`K-1-1`〜`K-1-7`）に分解して、それぞれ 1 件として数えるようにしました。

#### ⑤ 完了メモの中に書かれた「未了」を、現在の状態と読んでしまった

ある項目を「スクリーンショットが未了」と報告しましたが**誤り**でした。出典は別項目の完了メモ（数日前の日付）の中の一文で、**その後に実際は完了していました**（どれもチェック済みになっていた）。

→ 状態はチェックボックス（`- [x]` / `- [ ]`）で判断する。完了メモの本文は「**書かれた当時のスナップショット**」で、現在の状態ではありません。

> **教訓**: 「進捗が見える」状態を維持することそのものが工程の一部。
> 100 件を超えると、管理の失敗が実作業の失敗と同じだけコストになります。

## 審査のために追加で実装することになった機能

ここがこの記事の本題です。「アプリは完成している」つもりだったのに、ストアのポリシーと審査要件のために**新しく実装が必要になったもの**を全部並べます。

### 1. 報告 / ブロック / 規約同意の 3 点セット（最大のもの）

Play のコンテンツレーティング質問票に答えている途中で、ポリシー違反が発覚しました。

Play の**ユーザー生成コンテンツ（UGC）ポリシー**は、投稿が他ユーザーに見えるアプリに次を**必須**としています。

| 要件 | 当時の状態 |
|---|---|
| 「利用規約に同意しない限り UGC を作成 / アップロードできないようにします」 | ×同意導線なし（設定画面のリンクだけ） |
| 「不適切なコンテンツを定義し、利用規約で禁止します」 | ○充足していた |
| 「不適切な UGC やユーザーを報告してブロックするためのアプリ内システム」 | ×両方なし |

これはレーティングの問題ではなく、ポリシー違反の問題です。違反時の措置は「Google Play から削除」。さらに **iOS も同じ要件**（App Store Review Guidelines 1.2 = フィルタ / 報告 / ブロック / 公開連絡先）。

さらに悪いことに、ブロック機能は過去のバージョンで意図的に廃止していました。仕様書に「ブロック機能は持たない —— フレンド解除で十分とする」と明記し、コレクションと Security Rules も削除済みでした。

回避策がありませんでした。

- 公開範囲を狭めても駄目（**特定グループ限定でも報告は必須**）
- 片 OS だけの対応も駄目（両ストアが同じ要件）
- 申告を曲げるのも駄目（UGC は実在するし、質問票で「共有: はい」と保存済み）

結果として実装したのがこれです。

| 機能 | 実装 |
|---|---|
| ブロック | 専用コレクション（owner-only + キー allowlist）。実行時にフレンド解除 / 保留申請の整理 / 共有リストの解消まで行い、以後は Security Rules の遮断ゲート 3 点（通知の作成 / フレンド申請の作成 = 再申請の遮断 / 逆方向のエッジ = 招待リンク経由の穴）で遮断。公開リスト / ユーザー検索 / 通知からも除外。ブロックされた側からは一切分からない（owner-only read + 一般エラー） |
| 報告 | ドキュメント ID を `{報告者UID}_{対象UID}` の決定的な形にして、二重報告を Rules 層で防止。create のみ許可・クライアントからは読めない（運営が管理コンソールで確認する）。導線は公開リストの投稿者 + フレンド / 受信申請 / 送信申請の各行 |
| 規約同意ゲート | オンボーディングの必須ページ + 既存ユーザーには離脱不可の再同意モーダル + 同期層の防壁（サーバーへの公開 / 共有リストの作成・更新 / 画像アップロードを、現行バージョンの規約に同意していない端末からはブロック） |

**「同期層の防壁」が重要**でした。UI に同意ゲートを置いただけでは、UI を通らない書き込み経路が残ります。ポリシーの要求は「同意しない限りアップロードできない」なので、**データが外に出る層で止める**必要があります。

しかも完了後に、Play のコンテンツレーティング質問票を再回答する必要がありました（ブロック / 報告が「いいえ」→「はい」に変わるため）。**再回答は全問やり直し**です。

なお、iOS 側は**年齢レーティングの申告は変更不要**でした。`ageRatingDeclaration` の全 29 項目にブロック / 報告 / モデレーションの設問が存在しません。Apple のブロック・報告要件は Guideline 1.2（審査の合否）であって、レーティングの入力ではないからです。

> 一番の教訓: 「実装しない」と決めた機能の判断根拠が陳腐化する。
> 「報告は作らずブロックで代替する」という方針を立てていたのに、その代替手段のブロック自体を後で削除していたため、気づいたときには「制限も報告もブロックも無い」状態でした。方針ドキュメントは、前提が消えたときに一緒に見直さないと嘘になります。

### 2. アカウント削除・全データ削除・課金の開示・OSS ライセンス

ストアの必須要件として実装したものです。ここは「よく知られた要件」なので短めに。

| 要件 | 根拠 | 実装 |
|---|---|---|
| アカウント削除 | App Store 5.1.1(v) / Play のデータ削除要件 | アプリ内で退会（再認証 → 認証情報の削除 → サーバー上の自分のドキュメント削除）。公開 URL でも削除方法を案内する必要がある |
| 全データ削除 | 上記と別物 | ローカル DB の全モデルを削除 + 二重確認 UI |
| 課金の開示 | Guideline 3.1.2 | Paywall に自動更新の説明 + 名称・期間・価格 + 規約 / ポリシーへのリンク。価格はストアから取得した実値を出す（ハードコードしない） |
| OSS ライセンス | 各ライブラリのライセンス条項 | ビルド時に自動生成して同梱 |

**OSS ライセンスで踏んだ罠**は書く価値があります。

iOS は「同梱できていなかった」、Android は「同梱はできていて中身が足りなかった」という非対称でした。

Android 側は手書きで 7 群だけ列挙していました。旧コメントには「Google Play services / Play Billing などはプロプライエタリなので OSS 帰属一覧に含めない」と書かれており、「OSS ではない」という判断自体は正しいのですが、それらは別途 Legal Notices としての帰属表示を要求します。

根拠は Google 自身が公式プラグイン（`oss-licenses-plugin`）を提供し、その収録対象に該当ライブラリを含めていることでした。→ **公式プラグインの収録範囲をそのまま採る**方針に切り替え、手書き 7 群 → **自動生成 343 件**になりました。

「どのライブラリが帰属表示を要求するか」は法務判断なので、独断で足したり引いたりしてはいけません。これが一番の学びでした。

検証の罠。

- debug ビルドでは実データが生成されない（「Licenses are only provided in build variants (e.g. release)」という 126 バイトのプレースホルダが入る）。掴んでしまうと一覧が 1 件になり、しかもビルドは通るので気づけない
- 一覧が表示されること自体では検証にならない。実際に配布物（debug APK / release APK / AAB）を `unzip` して、**全 343 件の本文が空でないこと**まで確認しました
- 旧テストは「一覧が空でない / アセットが実在する」しか見ておらず、依存を追加しても落ちなかった

> 「あるべきものの件数」より「あってはならないものが 0 件」の方が壊れにくい。
> 差し替えの検証で「本文が Apache License で始まる件数」を数えようとしたら、**元から全文を持つ依存も該当してしまい**、assert の前提が誤っていました。「出力に汎用 URL が 1 件も残っていないこと」という直接の証明に書き換えました。

### 3. アプリ内ブラウザの撤去（年齢レーティング 17+ → 4+）

仕様書には 2 か所で「4+」と書いてあったのに、申告は 17+ になっていました。Play 側は 3+ で、両ストアで食い違っていました。

真因は iOS だけがアプリ内ブラウザ（`SFSafariViewController`）で任意 URL を開いていたことです。Apple はこれを Unrestricted Web Access と見なします。Android は OS のブラウザに渡していたので 3+ で通っていました。

**片 OS だけの非対称**で、しかも**同じアプリの中でも不整合**でした（メモ内のリンクは iOS でも既に外部ブラウザで開いていた）。3 箇所を外部ブラウザに統一して 4+ に戻しました。

再発防止として、「アプリ内ブラウザを持ち込んだら CI が落ちる」ガードを入れました。Android 側は `androidx.browser` が Gradle 依存に入っただけで落とすようにしています（実装される前に止める）。

### 4. プライバシー申告を実装から起こし直す

iOS のプライバシーマニフェストは 2 種類しか宣言していませんでした。実際は、アカウントに紐づくデータをバックエンドに送っていました。実測して **9 種**に是正しました。

| 分類 | 種別 |
|---|---|
| 関連付けあり（7種） | 名前 / メールアドレス / 写真またはビデオ / その他のユーザコンテンツ / ユーザ ID / デバイス ID / 購入 |
| 関連付けなし（2種） | 製品の操作（アナリティクス）/ クラッシュデータ |
| トラッキング | 全 9 種で「なし」 |

判断の根拠を**自分で見て作った**のがポイントです。

- **「関連付けなし」の根拠**: アナリティクスとクラッシュログにユーザー ID を設定する API 呼び出しが**両 OS で 1 箇所も無い**ことを試して確認
- **支払い情報は申告しない**（決済フレームワークが処理し、アプリは保持しない）

 Play のデータセーフティも同じ内容に揃える必要があります。「iOS だけ直して Play を忘れる」は起こりやすい事故です。

### 5. 米国法（App Store Accountability 法）への対応

米国の複数の州法（App Store Accountability 法）が 2026 年に相次いで発効しました。1 つは施行日が延期 → 差止 → 差止解除という経緯を辿っていて、「いつから効くか」自体が動きます。

**まず責任分界を確認したのが良かった**です。ストアがやることと開発者がやることは、はっきり分かれていました。

| 誰が | 何を |
|---|---|
| ストア（Apple / Google） | アカウント作成時の年齢確認 / 18歳未満への保護者同意の取得 / 同意が無ければダウンロードと課金をブロック → 開発者側のコードは不要 |
| 開発者 | (a) 年齢レーティングの付与（アプリ本体 + 各アプリ内課金にも個別に）/ (b) 重要変更の事前ストア通知 / (c) 年齢・同意データの取扱い制約（年齢制限・法令遵守・安全機能のみに使用。広告 / プロファイリング / 分析への流用禁止・長期保存禁止）/ (d) 年齢に応じた体験（努力義務・任意） |

アプリ内に自前の年齢確認ポップアップを作る必要はありません（年齢確認はストアが肩代わりする）。最初これを実装が必要な要件かと疑いましたが、条文と両社のドキュメントを読んで「不要」と確定させました。

 (d) の年齢シグナル API については、**両社とも採用を義務化していません**（一方は "can use"、もう一方は "doesn't mandate" と明記）。**実務上の前提も厳しい**:

- iOS の年齢区分 API は最新 OS 専用 → 最低 OS が古いとほぼ全ユーザーでシグナルが返らない
- **Android 側はベータ**で、しかも対象州の施行日以降に作成されたアカウントにだけ返る

→ **現状ほぼ全ユーザーでシグナル不在**なので、v1 では実装しない判断にしました。「法令対応」と聞くと全部やらなければと思いますが、条文上の義務と実装可能性は分けて見る必要があります。

さて (b) の「重要変更の事前ストア通知」で詰まりました。利用規約 / プライバシーポリシーに重要な変更を加える前に、各アプリストアへ通知する義務です。

ここで詰まったのは「ストアに『通知する』API も画面も存在しない」ことでした。

通知は該当申告（プライバシー申告 / レーティング / 課金機能の申告）の更新で果たすことになりますが、その更新はストア側の外部状態で、CI からは観測できません。

→ 観測できない「申告したか」を追うのをやめ、変更の側を凍結する方式にしました。

具体的には、**6 つの宣言面**（プライバシーマニフェスト / 課金商品 / 公開範囲の種別 / DB のコレクション構成 / ストレージのパス構成 / Android の権限）を**正規化してハッシュで凍結**し、変化したら CI が落ちて「**更新すべき申告を名前で提示する**」ようにしました。

正規化するので、コメントや整形の変更では発火しません（プライバシーマニフェストは plist として読み直す、など）。

さらに最大の穴。

規約とプライバシーポリシーの本文は別リポジトリ（静的サイト）にあり、アプリのリリースと完全に独立してデプロイできました。= ストアに何も通知せず規約を変更して公開できたわけです。アプリ側の CI では原理的に検知できません。

→ サイト側にも対称のガードを置きました。そのサイトには PR / push の CI が無かったので、**デプロイワークフローの公開直前**に配線しました（義務が「公開する前の通知」なので、位置としても適切）。

さらに最初のガードは片方の経路にしか無かったという失敗もしました。静的ホスティングはローカルから直接デプロイできるので、CI 内だけにガードを書いたらローカル経路が完全に素通りでした。「隣に同型の未配線がある」——このプロジェクトで何度も繰り返したパターンです。

なお、**課金商品ごとの年齢レーティング**も同法の要求です。ここで両ストアの非対称を手を動かして確かめました。

|  | 商品単位の年齢レーティング |
|---|---|
| Play | 専用フィールドが実在する。「現在 US のみサポート」（= この法律が米国法であることと一致） |
| App Store Connect | IAP に rating 系の属性も relationship も無い（アプリ単位のみ）→ iOS 側は該当作業なし |

「両 OS でやるべき作業」だと思い込むと、存在しない設定を探して時間を使います。API の discovery を自分で動かして「無い」ことを確定させるのが速いです。

### 6. 課金の権利判定をサーバー権威にする + 審査アカウントへの恒久付与

これは**審査要件から逆算して必要になった**ものです。

Play の「ログインの詳細」には、こういうチェックボックスがあります。

> このログイン情報を使用すると、アプリ内のすべての機能とコンテンツ（プレミアム コンテンツや有料コンテンツを含む）を制限なくご利用いただけます。

- 有料プランを持たないアカウントで ON にすると虚偽申告
- OFF にすると「有料コンテンツを審査できない」申告（画面に「審査できないとアプリが削除される可能性」と警告が出る）

→ 審査アカウントで実際にテスト購入してから ON にするしかありません。

ところが、**テスト購読は寿命が短い**（Play のテスト定期購入は 5 分周期・最大 6 回で自動キャンセル ≈ 30 分）。実際に 約 2.5 時間で失効して、申告が偽に戻りました。

→ 最終的に、サーバー側で「審査用 UID には権利を付与する」実装を追加しました。環境変数で UID を指定すると、権利検証の応答が常に Pro + 全アイテム所有になります。

**これは公開後に必ず解除する項目**なので、「公開後タスク」の Issue に分けて管理しています（先に解除すると申告が偽に戻るので、**公開が確定するまで着手しない**）。

しかも課金の検証時には、逆にこの付与を一時的に外す必要がありました。審査 UID が無条件 Pro だと、「テーマを買っても Pro が消えないこと」の検証が自明に真になって何も測れません。

### 7. 予算キルスイッチ（コスト防御）

これは審査要件ではありませんが、個人開発で従量課金のバックエンドを本番稼働させる以上、必須と判断して追加実装しました。

仕様書には「クォータ上限で守る」と書いてあったのですが、**実現不可能**でした（Firestore / Storage に「これ以上使わせない」上限は設定できない）。課金を実際に止められる唯一の手段は、請求先アカウントのリンク解除です。

```
Cloud Billing の予算 → Pub/Sub 通知 → Cloud Function → 請求先アカウントのリンクを解除
```

設計で決めたのは次の点です。

- 予算 ¥5,000/月・アラート 50/90/100/200%・停止は 200%（= ¥10,000）
- **「100% で即停止」は却下**しました。無効化するとバックエンドが全部止まってアプリの全機能が停止するので、**原因を調べる猶予として差額を残す**
- 判定は 「実費 ≧ 予算額 × 倍率」の金額比較 1 点に絞る。通知に含まれる閾値超過フラグは閾値を超えたときにしか入らないので、50% 通知で誤発火する。見ない
- 予算 0 / 金額欠落 / デコード失敗はすべて安全側（無効化しない）。壊れた通知で例外を投げると Pub/Sub が再試行ループになるので、null に倒す

本番プロジェクトで実際に停止テストまでやりました（合成通知を publish → 請求が無効化される → 手動で復旧）。**ダウンタイム約 1 分・データは無傷**でした。**未リリースだからこそできるテスト**です。

**境界値も実際に確認**しました（199.98% で `disable: false` = オフバイワンなし）。

### 8. 最大 Dynamic Type で詰む画面の修正（提出ブロッカー）

提出前日に見つかった、一番危なかったものです。

```sh
xcrun simctl ui <device> content_size accessibility-extra-extra-extra-large
```

これで実際に確認すると、**離脱経路のない全画面**が最大文字サイズで詰んでいました。

| 画面 | 症状 |
|---|---|
| 規約同意シート | 素の `VStack` + `Spacer()` で CTA が画面外。閉じる操作を封じているのでアプリが完全に詰む |
| 端末ロック画面 | 同型（root ごと差し替えなので逃げ道なし） |
| オンボーディングの規約ページ | 下部確保が固定 pt で、本文が CTA の下に潜る |
| Paywall | すでにスクロール可能で無傷 |

「離脱できない画面」で文字が入り切らないと、アクセシビリティの問題ではなく『アプリが起動できない』バグになります。アクセシビリティ関連は審査で見られる項目でもあります。

修正は 3 画面とも同じ形です。

```swift
GeometryReader { proxy in
    ScrollView {
        content
            .frame(minHeight: proxy.size.height, alignment: .center)
    }
    .scrollBounceBehavior(.basedOnSize)
}
```

通常サイズでの中央寄せを維持したまま、大きい文字ではスクロールできるようになります。

> 逃げ道のない画面だけは、最大 Dynamic Type で必ず手を動かして確認する。逃げ道がある画面は多少崩れても致命的になりません。優先順位はここです。

### 9. 審査導線を成立させるための「見せ用の公開データ」

これは「実装」ではなく「本番データの常設」ですが、審査のために必要になったものなので入れます。

レビューノートに「公開リストのタブから報告 / ブロックを確認できる」と書きました。ところが本番の公開リストは、実際に見たら 0 件でした。

理由は 2 つの重なりです。

- 公開リストは**端末言語と一致する投稿だけ**を表示する仕様（言語フォールバックは意図的に持たない設計）
- **自分の投稿は自己除外される**

つまり「**他人名義の公開投稿**」が本番に 1 件もないと、こうなります。

```
タップできる行が存在しない
  → 「…」メニューが一度も描画されない
  → 報告 / ブロック導線に到達できない
  → Guideline 1.2 の定型リジェクト
```

になります。

→ 審査用に「他人名義の公開投稿」を ja / en 各 1 件、本番に常設しました。

同時に進めていた「テストデータの掃除」と正面衝突しました。掃除対象に入っていた公開投稿を消すと導線が消えるので、**常設する分を掃除対象から明示的に除外**し、レビューノートにその投稿名を明記しました。

**表示名を必ず設定すること**も忘れないでください。未設定だと既定の表示名（「あなた」など）が出てしまい、レビュアーに「**『あなた』さんをブロックしますか?**」と表示されます。

提出直前に審査アカウントでサインインして、公開リストが実際に何件返るかを目視する——これ自体を受け入れ条件にしました。**0 件ならリジェクト確定**なので、確認しない選択肢がありません。

> **教訓**: レビューノートに書いた導線が「実データに依存」していないか確認する。
> コードは正しく動くのに、**本番にデータが無いから導線が成立しない**——これは実装のテストでは絶対に見つかりません。

### 10. その他

短くまとめます。

- **アナウンス経路**: Push 通知の受信検証をしていて、アプリアイコンのバッジを消す手段が存在しないことが判明しました（バッジを設定する API 呼び出しがコードベースに 0 件で、バックグラウンド実行を宣言していないので `badge: 0` を送っても消えない）。緊急のお知らせにバッジを付けると、全ユーザーのアイコンに `1` が永久に残るところでした。→ 「お知らせを DB のドキュメントで正典化し、アプリ内の通知一覧に取り込む + バッジを未読数と連動させる」実装を追加
- **同梱アセットの出所台帳**: 提出前必須の「コンテンツ権利」申告のために、画像 81 件の出所を 1 ファイルに台帳化しました。仕様書に「イラストは無料素材」と書いてあったのに、実態は全点を画像生成 API で自前生成していた（設計書に生成プロンプトまで残っていた）という記述の陳腐化もここで見つかりました
- **ブランドロゴのガイドライン適合確認**: 「当時どこから落としたか」の記録が残っていないので、「今の同梱物が公式配布物と一致するか」で担保する方針にしました。X / LINE は公式配布物と sha256 完全一致、GitHub のロゴは公式 octicons と SVG path がバイト完全一致、Google 系は色構成が完全一致（着色改変なしの証明）まで確認しています。LINE は PNG を直接配布せず ZIP のみなので、そこまで辿らないと「公式サイトからダウンロード」要求を満たす証拠になりません

## 検証環境の作り分け

この工程で一番効いたのが、環境の性質を正しく把握することでした。

| 環境 | できること | できないこと |
|---|---|---|
| シミュレータ / エミュレータ（debug） | UI / ロジック / 内部状態の直読み | 課金 / クライアント認証 / 一部のクラウド機能 |
| エミュレータ + Play 内部テスト配信 | Play 配信と同じ経路の release 検証・課金テスト | 内部状態が読めない（root 不可・`run-as` 不可）/ Play Integrity が成立しない |
| iOS 実機（TestFlight / 直接インストール） | Apple サインイン / 課金 / クラウド同期 / クライアント認証 | 本番のクラウド環境は TestFlight 配布でしか検証できない（署名で環境が決まる） |
| Firebase Test Lab（物理端末） | Play Integrity の成立確認 | 対話的な操作は限定的 |

### 物理 Android 端末は Test Lab で代替できた

Android のクライアント認証（Play Integrity）の成立確認だけは、どうしても物理端末が必要でした。エミュレータでは、Play ストア経由でインストールしても拒否されます。

「端末を買うしかない」と結論していたのですが、Firebase Test Lab の物理デバイスで代替できました（約 $0.25）。

```
① Play が生成した「署名済みユニバーサル APK」を API で取得
   ローカルビルドの AAB / APK では無意味
      （署名がアップロード鍵になり、Play の配信証明書と一致しない）
② gcloud firebase test android run --type=robo --app=<universal.apk> \
     --device="model=<物理端末>,version=36"
   split APK は投入できない（ユニバーサル APK 1 本で投げる）
③ 判定はクラウド監視のメトリクス（検証回数を result / security / app_id のラベルで見る）
```

**結果**: `ALLOW / VALID` が実行時間帯とぴったり一致して立ちました（それまで 30 日間 0 件）。

**判定の罠**: 無効なトークンは**アプリを特定できない**ので、「拒否」の件数だけ見てもどのプラットフォームが弾かれているか分かりません。一度「iOS が弾かれた」と誤読しかけました。エミュレータのアプリを強制終了して拒否件数が減衰することで、出どころを確定させました。

### 「その環境で検証した」という前提が崩れる

これは複数回踏みました。

- エミュレータに入っていたのがサイドロード版だった（`installerPackageName=null`）。Play 配信版は Play のアプリ署名鍵で署名されるので、ローカル鍵で入った APK への上書き更新は**構造的に不可能**。言い換えると 「Play 配信で検証している」という前提自体が満たされていませんでした
- エミュレータのスナップショットが巻き戻ると、以後の記録が全部前提から崩れる
- ローカルビルドは `CFBundleVersion` が既定値のままで、版数では区別できない。**バンドルコンテナの UUID の変化**で「置き換わったこと」を確認しました

> 「どの環境で測ったか」を毎回機械的に確認する。
> `installerPackageName` / 署名 / ビルド番号 / コンテナ UUID ——環境の同一性を示す指標を 1 つ決めて、検証のたびに見るのが結局一番速いです。

### シミュレータで別の Apple ID を使えた

「iOS では端末の Apple ID しか使えないので、別アカウントでの検証は不可能」と結論していました。これは誤りでした。

シミュレータの iCloud に別の Apple ID でサインインすれば、同一インストール上で身元を切り替えられます。

詰まっていた「ユーザ名またはパスワードが違っています」というエラーは、その Apple ID でブラウザから iCloud.com にサインインして利用規約に同意すると解消しました（既知の対処法として複数報告がある）。

「実際に確認不能」と結論する前に、環境の別の入口を 1 つ試す——これで消化できた項目が複数ありました。

### 同じシミュレータに 2 つのテストを投げると、両方失敗する

「フルスイートだけ間欠的に落ちる flaky」を追ったら、テストの問題ではありませんでした。

真因は、シミュレータが 1 台で、複数の作業ツリーが同じ 1 台を共有していたことです。バンドル ID が同じなので、後から来た実行のインストールが、走行中のテストホストを強制終了します。

**なぜ「flaky なテスト」に見えるか**（全部自分で確かめました）:

| 観察 | 実際 |
|---|---|
| 落ちるテストが毎回違う | 殺された瞬間に走っていたテストが犠牲になるだけ |
| 単体で回すと通る | 衝突しないから |
| クラッシュレポート（`.ips`）が無い | SIGKILL はレポートを残さない（コード起因のクラッシュなら必ず出る） |
| `Executed N tests, with 0 failures` と出る | リトライで 2 回目に通るため |
| なのに ` TEST FAILED ` | 初回の kill が run 全体を落とす |

決定的な切り分けは「自分のツリーに存在しないテストクラスが失敗一覧に出ていないか」でした。別の作業ツリーにしか無いクラス名が出て一発で分かりました。`xcresult` の `failureText` が `Test crashed with signal kill.` ならこれです。

対策は**シミュレータをプール化してロックを取る**ことにしました。**全部埋まっているときは失敗させず待つ**（失敗させると並行作業側のビルドを壊すため）。

### Android エミュレータで踏んだもの

- AVD ホームが `~/.config/.android/avd/` に移っていた（`~/.android/` は空）。これで「AVD は 0 個」と誤報しました（実際は 8 個あった）
- プロセスを再起動すると古いスナップショットまで巻き戻る。検証用アカウントのローカルデータが **54 件 → 6 件**になりました。巻き戻り先がサイドロード時代なら、以後の「Play 配信で検証した」記録は全部前提が崩れています
- AVD をクローンしても「3 台目」にならない。端末識別子のハッシュを端末 ID から作る設計だったので、クローンでは同値になります → `-wipe-data` で作り直す必要がありました
- Play ストア入りイメージはサイドロードを「Get this app from Play」で遮る（アプリが起動しない）。→ `adb install-multiple -i com.android.vending` で installer を明示すれば起動できます（Play ストアを無効化するのは GMS が壊れるので不可）
- ネットワークが死んだら Private DNS の設定を疑う

### iPhone に Release ビルドを入れるまでの前提 3 つ

CLI だけで完結しますが、前提が 3 つあり、どれも自動化できません。

1. 端末の Developer Mode を ON（無効だと destination が見つからず `Timed out waiting for all destinations`）
2. Xcode に有料チームのアカウントを追加（無いと `No Account for Team`）
3. **Portal で端末の UDID を登録** ——`-allowProvisioningUpdates` は証明書 / App ID / プロファイルを自動生成しますが、**端末登録は代行しません**。**年 100 台の枠を 1 つ消費します**

そのうえで踏んだ罠:

- `devicectl --device` に渡す ID と `xcodebuild -destination id=` に渡す UDID は別物（取り違えるとどちらも通らない）
- `xcodebuild` は exit 0 でも `** BUILD FAILED **` を返す → 終了コードではなく文字列で判定する
- 端末ロック中は install は通るが launch が失敗する → 検証を繰り返すなら自動ロックを切ってもらう
- 実機ログの回収が `Device not configured (6)` で失敗したときの原因は USB ケーブルだった。UDID の形式・出力先・接続方式を全部試して外したあと、**抜き差しで直りました**。**最初に抜き差しを試すべきでした**

### クロス OS の検証は「どの ID が使えるか」で制約される

2 台をまたぐ検証をやると、アカウントの構造がそのまま制約になります。

- iOS の Apple サインインはネイティブなので、端末に設定されている Apple ID しか使えません。一方 Android は web OAuth なので任意の Apple ID が使えます。この非対称のせいで「どの UID で検証するか」が構造的に決まりました
- プロバイダの unlink は不可逆です。iOS からは Apple でしかサインインできないので、Apple 連携を外すとその UID へ戻れません
- 逆に **「戻れなくすること」が目的になる場面**もありました。審査アカウントに開発者個人の Apple ID が紐づいていると、**審査担当者が個人データを見られる**ので、提出前に意図的に切り離しました

### 「404 になること」を受け入れ条件にすると永久に失敗する

検証の判定基準そのものを間違えた例です。

「公開を取り消したら旧 URL が **404** になること」を受け入れ条件に書いていました。しかし Cloud Storage は未認証の呼び出し元に存在の有無を明かさないので、実体が無くても 403 を返し、404 は原理的に返りません。

→ 正しい判定は「**200 以外**（実際に返るのは `403 Permission denied.`）＋ オブジェクトが実際に削除されていること」でした。「404」で書いていた受け入れ条件は、通ることが原理的にありえなかったわけです。

## 提出直前の本番データの掃除

検証を重ねると、本番に自分のテストデータが溜まります。レビュアーが最初に見る画面がそれになるので、提出前に掃除しました。ここも順序を間違えると巻き戻ります。

### ローカルが正なので、サーバだけ消しても戻ってくる

このアプリはローカル DB を正（source of truth）にしてサーバへ同期する設計です。サーバのデータだけ消しても、端末が次の同期で再び publish します。

→ 端末を持っているアカウントは、端末側の操作（退会 / データ削除）から始める必要がありました。

### バックアップの blob を消さないと掃除が巻き戻る

もっと厄介だったのがこれです。掃除したのに、アプリを入れ直したらテストデータが復活しました。

原因は、新規インストールが「復元を発火させる条件」を全部満たしていたことです。1 回だけ復元するためのラッチが端末の設定領域（UserDefaults）に置かれていたので、アンインストールで消えます。**入れ直すたびに「初回」になる**わけです。

→ クラウド上のバックアップ blob を消すまで、掃除は完了しません。

その blob には、プライバシー修正を入れる前のビルドが書いた古い内容が入っていました。掃除は「今のデータ」だけでなく「過去のビルドが残したもの」まで見る必要があります。

### 削除の順序 — tombstone とクライアント認証

- 退会の記録（tombstone）が入ると、同じ UID でユーザードキュメントを再作成できません。→ データの掃除を、認証ユーザーの削除より先にやります
- クライアント認証を強制モードにした後は、エミュレータ経由の操作ができません。→ 掃除の手段が「実機」と「管理 API」だけになるので、強制化のタイミングと掃除の順序を合わせて計画する必要があります
- 消してはいけないものもあります。私の場合、統計用のカウンタ（個人に紐づかない実採用値）は残しました。消すとランキング画面が空になるためです

### 審査用サンプルは「増やす」より「最小 + 審査後に消す」

審査導線を成立させるためのサンプルデータについては、**件数を増やすほど悪い**という裁定にしました。

捏造した他人の投稿を、実ユーザーに本物として見せることになるからです。審査に必要なのは「**タップできる行が 1 つ**」だけ（それが無いとメニューが描画されず定型リジェクトになる）。空状態の表示は実装済みなので、審査後に消しても壊れません。

そのうえで、サンプルの作り方に罠がありました。

- ランキングの既定期間が「先月」を読む実装だった → 当月分の集計しかないと**開いた瞬間 0 件**になる
- ステータスの raw 値が `completed` ではなく `done` だった → `completed` で引くと 0 件になり「データが無い」と誤診する
- 集計のコレクション名に**言語サフィックス**があり、英語ぶんを作り忘れると英語端末で空になる
- 1 件を「達成済み」にすれば 2 つのセクションを同時に満たせる（最小サンプルの作り方）
- ユーザードキュメントを先に消すと、報告機能の書き込みが「対象ユーザーの存在チェック」で壊れます（掃除の順序がここにも効く）

最終的に、**各セクションちょうど 1 件**に揃えました（試して確認したら 2 セクションが空で、逆に 1 セクションは 7 件と過剰でした）。

意図的に埋めなかった空白が 1 つあります。ランキングの既定表示が「先月」を読む実装なので、**その月に審査されると既定表示は 0 件**になります。前月分のデータを作れば埋まりますが、これはやめました。

> それは「先月そんな採用があった」という捏造なので作らない

と判断したからです。**リジェクト経路ではない**（レビューノートが指しているのは別のセクションで、そこには 1 件ある）し、翌月には自然に解消します。「埋められるから埋める」ではなく、埋めることが嘘になるかで判断すべきでした。

### 「消してよいか」も実際に確認してから決める

掃除の対象を「恒久データだから残す」と説明しかけて、**それが誤りだった**という例があります。

私は退会記録（tombstone）や課金の紐付けレコードを「**恒久的に残す設計**」だと説明しました。正しくは「恒久なのは仕組みで、入っていた行は全部この 1 か月の検証残骸」でした。ユーザーの「データはリセットされてるんじゃないの？」という指摘のほうが正しかったわけです。

試して分かった各データの実際の寿命はこうでした。

| データ | 実際に守っているもの |
|---|---|
| 退会記録（tombstone） | 退会直後のまだ有効な ID トークン（最大 1 時間）だけ。対応する認証ユーザーが既に無く、最新でも数時間前ならもう何も守っていない |
| 課金レシートの保管 | 次回の検証で端末から再構築されるので消せる |
| 統計カウンタ | 個人に紐づかない実採用値 = 消すと画面が空になるので残す |

消す前に「そのデータは今も何かを守っているか」を実際に試しました。さらに tombstone の削除には「1 時間以内のものがあれば中止する」ガードを入れて実行しました。「設計上の役割」と「今この行が持っている意味」は別物です。

## 提出前のレビューをどう組んだか

実装が終わってから提出までに、レビューを 4 段階やりました。個別のバグは記事の対象外なので、やり方と、そこで分かった「レビューの組み方の失敗」だけ書きます。

| 段 | 目的 | 結果 |
|---|---|---|
| ① 両 OS のパリティ監査 | iOS / Android の機能差を潰す | 複数ラウンド |
| ② リリースブロッカー掃討 round1 | 「実害が出る / 合同公開を止める」ものだけに絞る | crit 1 / high 5 |
| ③ 同 round2 | round1 の修正の回帰狩り | crit 1 / high 3 |
| ④ 全体監査（13 観点の並列） | 網羅性を取る | critical 1 / high 4 / medium 12 / low 25 |
| ⑤ 最終総合レビュー（2 ラウンド） | 提出可否の判定 | 「このままの提出は不可」と判定 |

### 観点を分けて並列に見る

④ では観点を 13 に分けて、それぞれ独立に全文を読ませました。

```
直近マージ分の回帰（3分割）/ 同期とストア整合 / アクセス制御・認証・削除 /
課金と有料機能の制限 / 両OSのパリティ / 多言語と文言 / リリース構成とビルド設定 /
既知クラッシュと品質 / ウィジェット・通知・拡張の境界 / エクスポートと外部連携 /
プライバシーと個人情報
```

効いたのは「複数の観点が独立に同じ結論へ収束したもの」を高確度として扱ったことでした。3 つの観点が同じ欠陥を指したものは、実際に全部本物でした。

⑤ では「**ストア審査のシミュレーション**」を観点として入れました。**レビュアーの目線で通しで触る**という観点は、機能の観点とは別に立てる価値があります（実際、ここから提出ブロッカーが出ました）。

### 敵対的検証を入れたら、半分以上が誤検出だった

これが一番大きな学びです。⑤ では検出した指摘に対して、「それを否定する側」の検証を別に走らせました。

| ラウンド | 検出 | 敵対的検証を生き残った |
|---|---|---|
| 第1 | 45 件 | 23 件 |
| 第2 | 24 件 | 10 件 |

要するに半分以上が誤検出でした。「見つけた」をそのまま修正に回すと、存在しない問題のために本物のコードを壊します。

> **教訓**: 検出したら「本当か」を別の手続きで潰す。「再現手順が書けるか」「反証できないか」を通してから修正に入れる運用にしました。

### round1 の修正が round2 で回帰を生んだ

②→③ で見つかった crit / high は、4 件すべてが round1 の修正による回帰でした。しかも共通の構造がありました。

> round1 の対称化（片方の OS に合わせる修正）が、もう片方の OS のアーキテクチャと組み合わさって初めて顕在化した

「片方に合わせて直す」修正は、もう片方の別経路を拾い切れません。私の場合は「表示名の上書き方式」「復元専用のバックアップ」「セッションの生読み」「画面回転での再駆動」といった Android 固有の構造が、iOS 前提の修正と噛み合って新しい欠陥を作りました。

> **教訓**: パリティ修正の後は、必ず「反対側での回帰狩り」を 1 ラウンド回す。

### 「ガードがあること」が「対応済み」の誤認を招いた

⑤ で見つかった中に、こういうものがありました。

> 対策済みだと思っていた項目に、実は片側だけ実装が無かった。しかし「両側に実装があることを検査するガード」が存在していたので、対応済みだと思い込んでいた

原因は、**そのガードの判定が「和集合」になっていた**ことです（どちらか一方にあれば通る）。ガードの存在自体が安心材料になってしまい、中身を疑いませんでした。

> **教訓**: ガードを信じる前に、ガードの負のテストを 1 回やる。「片側を消したら落ちるか」を確かめていれば、その場で分かりました。

### 運用として決めたこと

- medium 以下は個別に起票せず、統括の issue に記録だけ残す（起票すると全部やる圧力が生まれて、crit / high の消化が遅れる）
- 統括 issue は「crit 0 かつ high 0」になるまでクローズしない
- 「残り 1 件」になった時点で最終レビューをやる。そこで **26 件**出ました。残タスクが減ったことは「品質が上がった」ことを意味しません

## 繰り返し踏んだ 9 つのメタな罠

工程が違っても、同じ形の罠を何度も踏みました。これが一番共有する価値があると思います。

### ① 成功応答が嘘をつく

| 場面 | 症状 |
|---|---|
| `altool` | `UPLOAD SUCCEEDED` は受理ではない（後で却下メールが来る） |
| App Store Connect | `processingState=VALID` は配信ではない（グループへの割当が別工程） |
| Play の商品 API | `state: "ACTIVE"` を送って HTTP 200 が返るのに DRAFT のまま（専用メソッドが必要） |
| Play の本人確認 | 画面が「本人確認中」に変わるのは「アップロードされた」だけ |
| FCM 送信 | HTTP 200 は端末到達の保証ではない（配信側の失敗は非同期） |
| `firebase deploy` | exit code 0 でも意図した内容が本番に載っているとは限らない |

> 判定は「その工程の実データ」で行う。応答コードは「リクエストが受理された」以上のことを保証しません。

### ② 「一覧に無い」は「無い」の証拠にならない

| 場面 | 症状 |
|---|---|
| ビルド一覧 | `limit` を小さくした一覧は順不同で、最新が入らない。「存在しない」と誤報告した |
| 未作成のリレーション | GET が `data: null` を返す（404 ではない）→「API 非対応」と誤読 |
| 未設定のリソース | 逆に 404 を返すものもある（設定後は読める）→ これも「API 非対応」と誤読 |
| Play の書類リスト | 画面の選択肢に「開業届」が載っていないが、それでも通る |
| アクティビティログ | 全操作を記録していないので「行が無い = やっていない」の証明にならない |
| 配布証明書 | `security find-identity` にも API にも現れないのが正常（Cloud Managed） |
| 本番データの棚卸し | コレクション名を当てで書いて「0 件」と誤報した（実体は別名だった） |
| 同上 | クエリがエラー（400）で落ちているのを握り潰して「0 件」と読んだ |
| ローカルの AVD 一覧 | 探す場所が移動していて「0 個」と誤報（さらに `head` で切れていた） |

> 「無い」を主張するには、網羅的に見たことの証明が必要。部分的な一覧は反証に使えません。

本番データの棚卸しで確立した手順は 3 つです。

1. **ルートのコレクションを列挙してから回る**（推測でパスを叩かない。サブコレクションも同じく列挙する）
2. クエリは「アプリが実際に投げる形」で投げる（複合インデックスがある形。単一フィールドだけで投げると 400 になることがある）
3. **エラーと 0 件を明示的に区別する**（エラーを表す値を返して呼び出し側で分岐する）

**逆に使える性質もあります**: Firestore は**空のコレクションを保持しない**ので、ルート列挙に出てこないこと自体が「1 件も無い」証明になります。

### ③ 画面表示で判定しない

| 場面 | 正しい判定手段 |
|---|---|
| Play の本人確認 | Google からのメール |
| デベロッパー名の変更 | 後日、実際に表示が切り替わったか |
| データセーフティ | Console のプレビュー（API に GET が無い） |
| サブスクの完成 | UI が正・API の `state` は当てにならない（この 1 件だけ逆） |
| 削除が成功したか | サーバー側の実データが 0 件になったか（UI は「削除しました」と出る） |
| サインイン状態 | 認証が要る書き込みが通るか（設定画面はセッションが壊れていても「サインイン済み」に描画される） |

> 画面と実体のどちらを信じるかは、工程ごとに変わります。「常に API を信じる」も間違いです。

### ④ 検出機構が動いていないと false green になる

これが一番怖い罠です。

| 場面 | 症状 |
|---|---|
| メール検索での却下検出 | 認証トークンが失効していても「メール無し = 問題なし」と返す実装だった。却下されていても見逃す |
| ポーリングの終了条件 | API が一瞬空配列を返した回でも「完了」と判定して報告しかけた |
| CDN のキャッシュ | デプロイ直後の 1 回目は旧版が HTTP 200 で返る。1 回で「未反映」と判断すると誤報 |
| パイプによる終了コードの上書き | `make verify 2>&1 \| tail -80` で失敗が exit 0 になった |
| 構造ガード自身の穴 | エラーメッセージ内の文字列や説明コメントに grep が当たり、本体を消しても通る |

しかも「テストが走っていない」類の false green が、想像以上に多く出ました。

| 何が起きたか | どう気づいたか |
|---|---|
| 共有ライブラリのテスト 16 件が 1 件も実行されていなかった（プラットフォーム指定の都合で空実行） | 消えていた中身が重かった（画像の位置情報除去の唯一のテスト・回帰の唯一のテスト・本番から 5 箇所呼ばれる関数の唯一のテスト） |
| アクセス制御ルールのテスト 279 件が CI で一度も走っていなかった | 「本番の全 deny を長期間見逃した」真因がこれだった |
| 実行環境（JDK）のバージョン差でテストランタイムが初期化に失敗し、該当ブロックが自動 skip される | green のまま検証しない（skip されたことに気づけない） |
| ビルドが up-to-date でスキップされ、`BUILD SUCCESSFUL in 912ms` と出ながらテストが 1 件も走らない | 実行時間の異常な短さ |
| 増分ビルドだとコンパイル行がログに出ず、静的解析が「0 files」で何も検出しない | クリーンビルドで比較した |
| ファイルを追加してもプロジェクト生成を呼ばないターゲットがあり、参照の無いファイルが検査から漏れる | archive が落ちて初めて分かった |
| ローカルの lint に厳格モードが無く、CI と一致していなかった | 試してみると main への push 直近 200 回のうち 137 回が失敗していた。約 2 か月気づかなかった |
| コンパイラ警告をエラー扱いにする設定が無く、「警告 0」を守るものが実質何も無かった | テストターゲットに警告が 15 件溜まっていた |

> 教訓は 2 つです。
> 1. 「全部通った」と「全部走った」を別々に担保する。CI に 「skip が 0 件であること」を検証するステップを足しました
> 2. ローカルのゲートを CI と同一コマンドにする。乖離があると「ローカルが緑」を根拠に出し続けて、CI の赤に気づけません

### ガードは「検知力」を実際に確認しないと 0 円

これは特に効いた教訓です。CI に構造ガードを 30 本以上置いていたのですが、「合格」が出ても壊れを検知できないなら、そのガードの価値はゼロです。試して確認したらこうでした。

- 実バグを再発させても「合格」を出していたガードが 3 本あった
- 11 パターンの負テストのうち 3 本が「説明コメント」のせいで検知できなかった —— ガードがコメントを剥がさずに検索していたため、コードを消してもコメントに当たって通ってしまう
- ガード自身の判定バグも 2 件（**丸めた後の値で基準を割る** / コメント内の記述を次の要素の開始と誤認して取りこぼす）

> ガードを書いたら必ず「壊して落ちること」を自分で試す。コメントや文字列リテラルを剥がしてから検索する。負のテストを入れて初めて、自分のガードが素通りしていたことに気づきました。

### 検証スクリプトのバグを「アプリの不具合」と誤読する

判定に使った正規表現が期待どおりにマッチせず、6 回連続で空文字を返していました。その TIMEOUT の山を見て「アプリ側の不具合だ」と誤読しかけました（実際は `text="0 / 24"` の末尾のクォートに阻まれていただけ）。

検証が失敗し続けるときは、まず検証側を疑う。

### ⑤ 片 OS だけ静かに死んでいる

両 OS で同じ機能を持っていると、片方だけ動かなくなっていることに気づけません。

| 場面 | 症状 |
|---|---|
| iOS の Push 通知 | 一度も成立していなかった（トークンの保存先がサインイン後のパスなので、iOS でサインインした痕跡が皆無だった） |
| Android の Apple 連携 | 本番で一度も動いていなかった（web OAuth に必要な設定が空。iOS のネイティブサインインは別経路なのでAndroid でしか露見しない） |
| Storage の Rules | Android の復元と削除が全部拒否されていた（エミュレータのテストでは通る） |
| 年齢レーティング | iOS だけアプリ内ブラウザを使っていて 17+ になっていた |
| クライアント認証 | iOS の必要な entitlement が欠落していて一度も成立していなかった |

共通しているのは「機能が無いのではなく、観測できていなかった」ことです。「エラーログが 0 件」は正常の証拠になりません。**成功の痕跡を数える**（トークンが N 件ある / 検証が N 件 VALID になっている）方が確実です。

### ⑥ 公式ヘルプに載っていない中間ステップがある

| 場面 | 隠れていたもの |
|---|---|
| Play の 15% 手数料 | 「アカウントグループを管理」モーダルの 2 問を回答しないとバナーが出ない（ヘルプ記事に記載なし） |
| 同上 | 本人確認が完了していないと登録できない（公式に記載なし） |
| Play の依存関係 | ログインの詳細 → ターゲットユーザー → データセーフティ の一本道 |
| Play のナビ | 署名鍵の画面が 2 段階で移設されていた |
| Apple の「ビジネス」 | 旧称「契約/税金/口座情報」から改名されていて見つけにくい |

> 「画面に出ていない = 自分の操作が悪い」とは限らない。ヘルプに載っていない前提がある可能性を先に疑うと、消耗が減ります。

### ⑦ 「無音の失敗」は UI を見ていると永久に気づけない

リリース前の検証で繰り返し出たのがこの形です。

| 症状 | なぜ気づけないか |
|---|---|
| 画像がクラウドに上がっていない | 自分の端末にはローカルのファイルで表示されるので、他人に見えていないことが分からない |
| バックアップが良い世代を上書きした | 設定画面の「最終バックアップ」は成功として更新される |
| 削除がサーバー側で失敗した | UI は「削除しました」と出る |
| 復元が失敗して古い状態のまま進んだ | 無言で失敗するので、件数が増えないことに気づいて初めて分かった |
| 編集者の記録が別の人に書き換わった | 内容は保たれるので表示では気づけない |

> リリース前の検証では「UI が成功と言っているか」ではなく「サーバー側の実体」を見る。
> 私はこれを手順に落として、削除系は必ず**サーバーの実データが 0 件になったこと**を確認するようにしました。

### ⑧ 仕様や設計書の「残骸」が誤読を生む

これも複数回踏みました。

- 設計書の「当初案」が仕様に残っていて、実態と食い違った —— 私は「画像 42 枚が未着手」と読んで作業を積みかけましたが、実際は別の方法で全部用意されていました。同じ形で「素材の出所」の記述も実態と違っていました
- 削除跡のコメントが裁定の逆を書いたまま残っていた —— 「同梱する」と書いてあるのに実装は「同梱しない」。将来「実装漏れ」と誤読されて再追加されるリスクがあります
- Debug のサンプルデータが本番と違う件数だと「本番でもそう見える」と誤読させる（私は 3 枚 → 1 枚に揃えました）

> 「未着手」と書かれている項目も、コードを見て確認する。方針を変えたら、その方針を説明していた文章も同時に直す（残すと次の自分が信じます）。

逆に「仕様に実装しないと明記してある」ものは、見落としではなく判断です。それを覆すときは「バグ修正」ではなく「判断の変更」として扱うべきでした（私は課金の検証方式でこれを混同しかけました）。

### ⑨ チェックリストの文言が実現不能なことがある

自分で書いたタスクリストにも「実現できないこと」が混ざっていました。

- 「Grace Period を 7 日に設定」——Apple の選択肢に 7 日は存在しなかった（3 / 16 / 28 日のみ）。「7 日」の出所は Play 側の既存設定だった
- 「クォータ上限でコストを守る」——実現不可能だった（設定できる上限が存在しない）
- 「実機が必要」と書いていた項目の多くは、エミュレータや Test Lab で消化できた
- 「未実装」と書いてある項目が実は実装済みで、チェックが倒れていないだけだった（複数件）

> 着手前に API / 実装で選択肢を確認する。チェックリストは過去の自分の想定にすぎません。**Issue の記載より実際に確認を信じる**——これは何度も効きました。

□ Apple: Individual / Organization を決める

□ Play: 組織 / 個人を決める

□ 屋号入りの開業届を取り直す（D-U-N-S の必要書類が「屋号の記載のあるもの」）

□ D-U-N-S が必要なら Apple の無料ルートを先に確認（書類提出なし・数日・0 円）
□ 書類の黒塗りは注釈レイヤーだと透ける（ピクセル統計で焼き込みを検証）

【フェーズ 0: 期限つきの公式要件を洗い出す】
□ ビルド環境（SDK / ツールチェーン）の最低バージョン要件と期限
□ ターゲット API レベルの年次要件（公開ゲート）
□ 課金ライブラリの最低バージョン（既存バイナリは動き続けるので気づきにくい）
□ 年齢レーティング質問票の新項目（未回答だと提出がブロックされる）
□ プライバシー関連の申告様式（required-reason API を含む）
    → 提出直前ではなく着手時に、自分の値を実測して表にしておく

【フェーズ 2: 外部待ちを先に着火する】

□ Apple Developer Program 加入（数時間）
□ アプリ名を確保する（App Store は先着制）
□ OAuth の機密スコープ検証が必要なら申請（数日〜数週間）

【フェーズ 3: 待っている間にやる（ここが一番作業量が多い）】

    → ドメイン所有権確認が前提 / スコープは機能ごとに増える
□ リダイレクト・キャッシュ・Content-Type を実ブラウザと curl -L で実測する
□ 外部から叩ける口（フォーム等）を置くならレート制限とキャッシュキーを設計する
□ バックエンドの本番プロジェクト作成 + コスト防御
□ 署名（iOS の配布証明書 / Android のアップロード鍵）
□ バージョン番号方式の確定（両 OS 共有にするなら単調増加が必須）

## 公開後にやることを、公開前と分けて持つ

「公開してからでないとできない / してはいけない」タスクがあります。混ぜると事故るので、別の issue に分けました。

| # | タスク | タイミング | 種別 |
|---|---|---|---|
| 1 | 審査用アカウントへの特別扱いを解除する | 両ストアの公開直後 | 更新審査のたびに再発しうる |
| 2 | 課金サーバー API の本番環境の疎通を再確認する | 公開後 | 一度きり |
| 3 | 審査用のサンプルデータを削除する | 審査が完全に終わってから | 一度きり |
| 4 | 公式サイトのストアリンクを有効化する | 公開後 | 一度きり |
| 5 | ターゲット API レベルの年次要件に追従する | 毎年 | 恒久の年次タスク |

### 1 は「公開が確定するまで絶対に外さない」

外した瞬間に、「審査アカウントで有料コンテンツを含む全機能にアクセスできる」という申告が偽になります。

厄介なのが、**更新審査のたびに必要になりうる**ことです。テスト購入の定期購入は短周期で更新され、数十分で自動キャンセルされるので、審査期間中ずっと有料状態を維持する手段が他にありません。「付け直す → 通ったらまた外す」を繰り返すことになります。

### 2 は「本番環境が 401 のまま公開に向かった」

これは提出時点で未解決のまま残した項目です。課金レシートを検証するサーバー API を、同じ鍵で両環境に投げると、応答が分かれます。

| 環境 | 応答 | 意味 |
|---|---|---|
| 本番 | `HTTP 401`（エラー詳細なし） | 認証が成立していない |
| サンドボックス | `HTTP 404`（トランザクションが見つからない） | ○認証は成立している |

未公開なので本番側にアプリの実体が無いためと推定していますが、**公開後に通るようになるかは未検証**です。実装は「本番 → サンドボックス」の順に試して成功した方を使うので壊れていませんが、**公開後の実購入は本番環境**なので、ここが 401 のままだと本番レシートの検証が実質サンドボックス頼みになります。

**切り分けで大事な点**: `400`（トランザクション ID の形式が不正）は認証が成立しています（ID の検査は認証の後）。**認証失敗は `401` だけ**です。これを「鍵が悪い」と誤読しないよう気をつけます。

### 4 は「公開までストアページが 404」

公式サイトのダウンロードボタンは、ストア URL の定数が空の間は「準備中」を表示してリンクを描画しない作りにしました。

**URL 自体は提出時点で確定しています**（アプリレコードを作った時点で決まる）。でも公開までストアページは 404 なので、先に入れると死んだリンクを踏ませることになります。

**審査担当者がサイトを見る可能性もあります**（サポート URL とプライバシーポリシー URL がそこを指しているので）。「準備中」表示のほうが、死んだリンクより安全です。

## まとめ

提出を終えて振り返ると、この工程で一番役に立った方針は 1 つだけでした。

> 「終わった」の判定を、その工程の実データで行う。

`UPLOAD SUCCEEDED` は受理ではなく、`VALID` は配信ではなく、HTTP 200 は反映ではなく、「本人確認中」は承認ではなく、UI の「削除しました」は削除ではありませんでした。逆に、サブスクの `MISSING_METADATA` は不備ではなく、`find-identity` に証明書が出ないのは正常でした。

**どちらを信じるかは工程ごとに違う**ので、覚えるべきは個別のルールではなく「**判定手段を毎回明示的に決める**」という習慣だと思います。

さらにもう 1 つ。

> コードが完成してからリリースまでの工程を、最初から見積もりに入れる。

私はここを「あと少し」だと思っていて、実際には 3 週間かかりました。しかもその 3 週間で新しい機能実装（報告 / ブロック / 規約同意ゲート）が発生しています。ストアのポリシーは、実装内容に対する要件を後から追加してきます。

UGC を扱うなら報告とブロックは避けられません。課金があるなら審査アカウントで有料機能を触れる状態を作らないといけません。従量課金のバックエンドを使うならコスト防御が要ります。これらは「リリース作業」ではなく「機能開発」なので、その分の時間を最初から取っておくべきでした。

審査結果はまだ出ていません。何を言われたか、リジェクトされたなら何が原因だったかは、結果が出てから追記または別記事にします。

これから両ストアに出す方の、消耗ポイントを 1 つでも減らせれば幸いです。

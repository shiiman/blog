## はじめに

個人開発のバケットリストアプリ **Bucket List Commit** をストアに出す準備をしている最中に、**提出をブロックする問題**が 1 つ出てきました。

**ユーザー投稿コンテンツを扱っているのに、報告もブロックも規約同意も無い**という状態でした。

これは両ストアで必須要件です。気づいたのがリリース直前だったので、そこから急いで実装しました。この記事はその記録です。

> シリーズ「アプリの中身と実装」全 12 本の 9 本目です。最初から読むなら [① アプリの概要](/engineering/app/indie-bucket-list-app-overview/) から。ストアに出すまでの手続きは[別シリーズ](/engineering/app/personal-app-cross-store-release-full-journey/)にまとめました。

---

## 何が必須要件だったか

Google Play のユーザー生成コンテンツのポリシーが求めているのは 3 つです。

| 要件 |  |
|---|---|
| 1. 規約への同意 | **同意しないと投稿・アップロードができない**こと |
| 2. 規約の内容 | 不適切なコンテンツを定義して禁止していること |
| 3. アプリ内の機能 | **報告とブロックの両方**があること |

App Store も同じことを求めています（レビューガイドライン 1.2）。

そして自分のアプリの状態がこうでした。

|  | 状態 |
|---|---|
| 利用規約のドキュメント | ある |
| 同意フロー | **無い** |
| 報告 | **無い** |
| ブロック | **無い** |

ポリシー違反はストアからの削除に直結します。**「機能として無い」のは審査で必ず止まる**類のものなので、リリース必須要件として扱いました。

### そもそも自分のアプリは UGC を扱っているのか

ここは一応確認しました。答えは明確に「扱っている」でした。

- リストを公開して他人に見せられる（探すタブ）
- フレンドのリストを見られる
- 表示名とアイコンをユーザーが決められる
- カバー画像をアップロードできる
- 他人のリストに「いいね」を送れる

**他のユーザーが見るテキストと画像がユーザー入力なら、それは UGC です。** コメント機能が無くても関係ありませんでした。

## ブロックの設計

一番考えたのがここです。

### 置き場所

```
blocks/{userId}/blocked/{otherUserId}   ← 本人しか読めない
```

「誰をブロックしたか」は本人だけが読めるようにしました。ブロックされた側からは**一切分かりません**。

これは意図的な設計です。「ブロックされました」と分かると、そこから別アカウントでの回避や、実生活での摩擦につながります。**ブロックは静かに効くべき**という判断でした。

### ブロックしたときに起きること

単にフラグを立てるだけでは足りませんでした。既存の関係を全部片付ける必要があります。

```
1. ブロックのドキュメントを作る   ← ここだけ失敗したら中断する
2. フレンド関係を解除する
3. 保留中のフレンド申請を消す（送信・受信の両方向）
4. 共有バケットから抜ける / 相手を外す
```

**1 だけを「必ず成功しなければならない処理」にしました。** 2 から 4 は個別に失敗を許容します。

理由はこうです。**1 が成功していれば、以降は Security Rules が恒久的に効きます。** つまり後片付けが多少失敗しても、新しい接触は発生しません。逆に 1 で失敗しているのに 2 以降を進めると、「関係は切れたがブロックはされていない」という中途半端な状態になります。

### Security Rules で恒久化する

ここがブロックの本体でした。クライアント側のフィルタだけだと、REST を直接叩けば通ってしまいます。

3 か所に門を置きました。

| 場所 | 効果 |
|---|---|
| 通知の作成 | ブロックした相手からの通知が**作れなくなる** |
| フレンド申請の作成 | 検索・招待リンク・QR の**どの経路でも申請できなくなる** |
| フレンド関係の逆向きの辺 | 相手側から関係を張り直せなくなる |

「検索経由だけ塞ぐ」では不十分でした。**招待リンクと QR も同じ結果になる経路**なので、入口ごとに塞ぐのではなく、**書き込みの手前で塞ぐ**必要があります。

そして探すタブの公開リストとユーザー検索からも消えます。ここはクライアント側の除外ですが、書き込みが塞がれているので実害はありません。

### 表示から消えなかった不具合

実機で試して見つけました。**ブロックしたのに公開リストからその人の行が消えません。**

原因は、除外の判定を**取得した時点で 1 回だけ**やっていたことでした。ブロック操作の直後に再取得が走らないので、画面に残ります。

**描画時にブロック集合を購読する**形に変えました。ブロックした瞬間に行が消えます。

「取得時に除外」と「描画時に除外」は、見た目が同じでも**更新に追従するかどうかが違う**という話でした。

## 報告の設計

報告は思っていたよりシンプルにできました。

```
reports/{reporterUID}_{targetUserUID}
```

ドキュメント ID を、**報告した人と報告された人の組み合わせで決定的にした**のがポイントです。

これで**二重報告が Rules の層で構造的に防げます**。`create` だけを許可して `update` を禁止すれば、同じ組み合わせでは 2 回目の作成が失敗します。カウンタも重複チェックのクエリも要りません。

読み取りは**全部禁止**にしました。管理者も含めてクライアントからは読めません。確認は Firebase コンソールから直接見ます。

そして**バケット単位の報告は作りませんでした**。ユーザー単位だけです。理由は 2 つあります。

1. 対処の単位がユーザーだから。バケットを報告されても、やることは結局そのユーザーの扱いを決めることです
2. **報告先が増えるほど、コンソールで見る場所が増えます。** 個人開発で自動化しないなら、入口は 1 つにしたほうが運用が続きます

自動モデレーションも Cloud Function もメール通知も入れていません。**個人開発で運用が回る形にする**のを優先しました。

## 規約同意の設計

ここが一番配線が多かったところです。

### 3 つの入口

| 対象 | やったこと |
|---|---|
| 新規インストール | オンボーディングに同意ページを追加 |
| 既存インストール | **閉じられない**再同意モーダル |
| 同意していない端末 | **同期層で書き込みを止める** |

既存インストールへの対応が必要なのが盲点でした。すでに使っている人は、オンボーディングを通りません。**同意していない人が投稿できる状態が残ります。**

再同意モーダルは「あとで」で閉じられないようにしました。要件が「同意しないと投稿できない」なので、**先延ばしできる導線を残すと要件を満たしません**。

### 同期層のガードが本体だった

UI で止めるだけでは足りません。**同意していない端末からの書き込みを、同期層で止める**必要があります。

止めた対象がこれです。

| 対象 |  |
|---|---|
| 個人バケットの公開 | 止める |
| 共有バケットの作成・更新 | 止める |
| カバー画像のアップロード | 止める |
| OG 画像のアップロード | 止める |

ここで**同種の経路への配線漏れを、ひと続きの作業で 3 回踏みました**。

## 「隣接する同種の経路」に配線し忘れるパターン

これが今回一番の学びでした。3 回とも同じ形でした。

| # | 塞いだところ | 忘れたところ |
|---|---|---|
| 1 | 投入（キューに入れる側） | **実行（キューから取り出して送る側）** |
| 2 | カバー画像 | **OG 画像** |
| 3 | 個人バケット | **共有バケット** |

どれも「同じ種類の処理が隣にある」ケースです。1 つ直したあとに、**隣を見ていません**。

投入側を塞いでも、すでにキューに入っているものは実行側から出ていきます。カバー画像を塞いでも、OG 画像は別のコードパスです。個人バケットを塞いでも、共有バケットの更新は別の関数です。

### どうすればよかったか

**実装を始める前に、対象のマトリクスを全部並べる**ことでした。

```
投入 / 実行            × 2
カバー画像 / OG 画像    × 2
個人 / 共有            × 2
iOS / Android         × 2
```

並べれば 16 の組み合わせです。ここを最初に紙に書いていれば、3 回とも 1 回で終わっていました。

**「1 か所直した」の直後に「隣に同じ形のものはないか」を聞く**のを習慣にするのが対策でした。個人開発だとレビューする人が自分しかいないので、この問いを自分で出す必要があります。

## 実機で分かった UI の問題

機能ができてから実機で通したら、UI の問題がまとめて出てきました。

### 確認ダイアログはシートの上に重ねる

これが一番効きました。

**やってしまった形**: シートを閉じてから確認ダイアログを出す。

**何が起きるか**: キャンセルすると**シートが閉じたままになります**。ユーザーは「戻った」つもりなのに、元の画面まで戻されています。

**正しい形**: シートを閉じずに、その上に確認ダイアログを重ねます。キャンセルすればシートに戻ります。

「破壊的な操作の前に確認を出す」は当然なんですが、**キャンセルしたときに元の状態に戻るか**は別に確認する必要がありました。

### 同じ種類のボタンは横に並べる

ブロックと報告は「どちらも相手への対処」なので、性質が同じです。それを縦に並べると、片方が主・片方が従に見えます。

横に並べて、それぞれの下に**何をするものかの説明を付けました**。「ブロック」と「報告」の違いは、ラベルだけでは伝わりません。

### 2 段レイアウトは実機で却下された

フレンド申請の詳細シートで、情報を 2 段に分けるレイアウトを作りました。実機で見て、**余白が空いて美しくない**という結論になり、1 段にして行タップで詳細に飛ぶ形にしました。

シミュレータで見ているときは気づきませんでした。**余白の印象は実機の画面サイズでしか判断できない**という話でした。

### メニューの文言が折り返した

長いラベルがメニューの幅を超えて折り返しました。日本語だと文字数が読みにくいので、**実機で開いて見るまで分かりません**。

### 翻訳キーの衝突

これは日英対応の話ですが、ここで踏んだので書いておきます。

ブロック解除のボタンに「解除」と入れたら、**連携解除の「解除」と同じキーになりました**。連携解除の英語は "Disconnect" なので、ブロック解除のボタンに "Disconnect" が出ます。

キーを分けて解決しました。**同じ日本語でも文脈が違えば別のキーにする**必要があります（詳しくは[日英対応の記事](/engineering/app/ios-android-string-catalog-i18n/)に書きました）。

## 規模

参考として、この対応の規模を書いておきます。

| | |
|---|---|
| コミット | 25 |
| 変更したファイル | 139 |
| 対象 | iOS / Android の両方 + Security Rules |

「報告とブロックを付ける」と口で言うと 1 機能ですが、**両 OS ぶんの UI と、Rules と、同期層のガードと、既存ユーザーへの再同意**が全部付いてきます。

## まとめ

ストアのポリシー対応として UGC 機能を後から入れて、残ったことを 5 つ。

1. **UGC を扱っているなら、報告・ブロック・規約同意は必須要件。** コメント機能が無くても、他人が見るテキストと画像がユーザー入力なら該当します
2. **ブロックは Security Rules で恒久化する。** クライアントのフィルタだけだと REST で抜けられます。そして入口ごとではなく書き込みの手前で塞ぎます
3. **決定的なドキュメント ID で二重報告を構造的に防げる。** カウンタも重複チェックも要りません
4. **既存インストールへの再同意を忘れない。** オンボーディングだけだと、既存ユーザーは同意せずに投稿できます
5. **1 か所直したら「隣に同じ形のものはないか」を聞く。** 実装の前にマトリクスを並べれば、3 回踏むところが 1 回で済みます

そして一番効いたのが**実機で通すこと**でした。ダイアログの重ね方、ボタンの配置、余白の印象。どれもシミュレータでは気づけませんでした。

## はじめに

個人開発のバケットリストアプリ **Bucket List Commit** は、iOS と Android の両方があります。そこで「**片方から片方へ、アカウントとデータごと移せる**」ようにしました。しかも往復できます。

やってみて分かったのは、難しいのはデータの運搬ではなく、**いま正しい端末はどれかを決めるところ**だったということでした。

> シリーズ「アプリの中身と実装」全 12 本の 8 本目です。最初から読むなら [① アプリの概要](/engineering/app/indie-bucket-list-app-overview/) から。ストアに出すまでの手続きは[別シリーズ](/engineering/app/personal-app-cross-store-release-full-journey/)にまとめました。

## 前提: 端末間のリアルタイム同期は持たない

まず作らなかったものを書きます。

|  | 持っているか |
|---|---|
| iOS どうしの端末間同期（iCloud） | ある（自動） |
| Android どうしの端末間同期 | 無い |
| iOS ↔ Android のリアルタイム同期 | 無い |

代わりに用意したのが「**移行のみ・単一端末・往復可**」というモデルです。同時に 2 台で使うことは想定しません。

理由は 2 つです。

1. **サーバーを持たない設計**（[技術構成](/engineering/app/indie-app-technical-architecture/)）でリアルタイム同期を組むと、衝突の解決が破綻します
2. **同時に 2 台で使う需要が自分に無かった**。移行できれば十分でした

## 認証は非対称なので、リンクでまとめる

サインインの手段が OS ごとに違います。

|  | サインイン |
|---|---|
| iOS | Apple Sign-In のみ |
| Android | Google Sign-In のみ |

このままだと、移行先でサインインすると**別の UID になってしまいます**。ソーシャルのつながりも課金の権利も引き継げません。

そこで、**移行元の端末で Apple と Google のアカウントをリンクして、同一の Firebase UID に集約します**。

```
移行元（iOS）で Google アカウントをリンク
  → 1 つの UID に Apple と Google の両方が紐づく
    → 移行先（Android）で Google サインイン
      → 同じ UID になる
```

`linkWithCredential` を呼ぶだけで、**サーバー（Cloud Function）は要りません**。個人開発でこれは大きかったです。

リンクが使えない場合のフォールバックとして、移行先で元のプロバイダに直接サインインする経路も用意しました（Android から Apple サインインする Web の OAuth 経路）。ただし**これは iOS が動いていても Android だけ落ちる**ので、別途の設定が必要でした（[Android 版の記事](/engineering/app/android-compose-room-billing-pitfalls/)に書きました）。

### UID が続くと自動で戻るもの

UID が同じなら、こちらは何もしなくても再接続されます。

|  | 移行後 |
|---|---|
| フレンド関係 | 自動で再接続 |
| 課金の権利 | 自動で再接続 |
| 通知 | 自動で再接続 |
| 公開プロフィール | 自動で再接続 |

**運ぶ必要があるのはローカルのデータだけ**という整理になりました。ここが設計として一番すっきりしたところです。

## データの運搬は 2 経路

ローカルが正のアプリなので、バケット本体は運ぶ必要があります。

| 状況 | 運搬方法 |
|---|---|
| GitHub 連携している | 全件プル（もともと双方向同期しているので、そのまま引ける） |
| 連携していない | 暗号化スナップショットを書き出して移行先で取り込む |

スナップショットは、バックアップ機能と**同じ直列化のコードを再利用**しています。移行のために別の形式を作ると、そこだけ壊れても気づけません。

そして移行を始めた時点で**新しいスナップショットを書き出します**。古いものを使うと、移行の直前に追加した項目が消えます。

### 画像は同梱しない

スナップショットに画像のバイト列は入れません。移行先で Cloud Storage か GitHub から取り直します（可能な範囲で）。

**非公開の画像は、GitHub 連携していないと復元できません。** これは仕様として明記して、移行画面に注記を出しています。画像のバイト列を全部同梱すると、スナップショットが数百 MB になって現実的でなくなるためです。

### Room を SwiftData の 1 対 1 ミラーにしておいた

これが効きました。Room のエンティティを SwiftData のモデルと**フィールド名・型・列挙まで一致**させています。

そのおかげで、スナップショットを**無変換で写せます**。ここを揃えていなかったら、移行のたびに変換コードを書いて、両方向でテストする必要がありました。

## 単一端末リース

一番考えたのがここです。同時に 2 台で編集されると、データが分岐します。それを**構造的に防ぐ**仕組みを入れました。

```
users/{uid}/activeDevice/current  ← 「アクティブな端末」を 1 つだけ持つ
```

動きはこうです。

| 状況 | 挙動 |
|---|---|
| ホルダーが空 / 自分の端末 | 初回サインイン時に自動で claim |
| 別の端末がアクティブ | 「この端末に移行」の明示操作のみで奪取できる |
| 奪われた側 | 完全にロック（閲覧もできない）。ただしローカルデータは破壊せず保持 |
| 戻りたいとき | 「この端末で再開」で再 claim。往復できる |

ロックされた側のローカルデータを消さないのがポイントでした。往復できるモデルなので、**消してしまうと戻ったときに空になります**。

iOS の iCloud クラスタは 1 ホルダーとして扱います（iPhone と iPad は同じ 1 台という扱い）。

### 端末の区別はクライアントの責務

**Rules は同一 UID の端末を区別できません。** リクエストに端末の識別子は入っていないので、サーバー側で「これは別の端末だ」と判定する手段がありません。

だから**自動で奪わない**ようにしました。奪取は必ずユーザーの明示操作です。ここをクライアントの責務と割り切ったのが、設計をシンプルにしました。

### TTL とハートビートは入れなかった

「ホルダーが応答しなくなったら自動で失効させる」案を検討して、**却下しました**。

失効を入れると、**猶予期間のあいだ 2 台が同時にアクティブになりえます**。リースの目的は「同時 1 台」の保証そのものなので、保証を弱める変更は採りません。

新規の設計が必要になるうえに保証が下がる、という組み合わせだったので判断は早かったです。

## ホルダー ID が再インストールで消えた

ここで実害のある不具合を踏みました。

**症状**: アンインストールして再インストールしてサインインすると、**1 台しか使っていないのに**「この端末はロック中です。現在『（端末名）』がアクティブな端末です」と出る。

しかも**表示される端末名が自分自身**なので、説明が実態と食い違います。ユーザーから見れば何が起きているか分かりません。

### 原因は OS 間の非対称だった

|  | ホルダー ID の実体 | 再インストール後 | 後追いの救済 |
|---|---|---|---|
| **iOS** | SwiftData + **iCloud ミラー** | **同じ値に収束する** | **自動で解錠される** |
| **Android** | SharedPreferences の UUID | **消える**（自動バックアップも無効なので戻らない） | **無い** |

iOS はミラーがあるので再インストール後も同じ値に落ち着き、さらに後追いで自動解錠する仕組みまで入っていました。**Android だけが弱かった**わけです。

同じ機能を 2 回書くと、こういう非対称がどこかに残ります。

### 何に変えたか

`Settings.Secure.ANDROID_ID` を**固定のソルト付きで SHA-256** にした値にしました。

| 性質 |  |
|---|---|
| スコープ | アプリ署名鍵 × ユーザー × 端末 |
| 再インストール | **同じ値**（Play App Signing なので署名鍵が安定している） |
| 権限 | 不要 |
| 端末初期化 / 機種変更 | 変わる（**これは別端末として扱うのが正しい**） |

ここで気をつけた点が 2 つあります。

**生のハードウェア識別子をサーバーに置かない**ので、ハッシュ化は必須です。

そして**ソルトに UID を混ぜてはいけません**。ホルダー ID は認証状態に依存せず同期的に解決される値なので、UID を混ぜると「呼ばれた時点で UID が確定しているか」で値が変わります。これは購入イベントの取りこぼしと**同じ型のタイミング依存バグ**を作ります。リースのドキュメント自体が `users/{uid}` の配下にあって owner-only の Rules で守られているので、UID を混ぜる必要はありませんでした。

`ANDROID_ID` が空や null になる端末のフォールバックは、UUID を採番して永続化します。永続先は**既存の prefs を共用**しました。新しいストアを足すと、データを消す 3 つの経路すべてに配線する必要が出て、漏れを生みます。

## 移行先で先にアカウントを作ってしまったとき

想定しておく必要があったケースです。ユーザーが移行先の端末で、リンクする前に新しいアカウントを作ってしまうことがあります。

すると `credential-already-in-use` になって、リンクできません。

対処は「**その捨てアカウントを削除してから、本来のアカウントで認証する**」導線を用意することでした。アカウント削除の機能はすでにあるので、それを使い回します。

ここで 1 つ厄介なことがありました。**削除の途中でセッションが切れると、どちらのアカウントにも入れない状態になりえます**。削除の順序を「サーバーのデータ → 端末の資格情報 → 認証ユーザー」にして、**途中で失敗したら認証ユーザーは消さない**設計にしてあります（消してしまうと、残ったサーバーのデータに本人が二度とアクセスできません）。

## 移行画面の UI で決めたこと

実機で試して、3 つルールにしました。

1. **状態はアカウントの実態で決める。** 画面の中で持っているフラグではなく、実際のリンク状況やリースの状態を見て表示します。フラグを持つと、途中で失敗したときに画面と実態がずれます
2. **エラーは発生したセクションの直下に出す。** 画面の上部にまとめると、どの操作で失敗したのか分かりません
3. **ユーザー起点の書き出しは 20 秒で打ち切る。** 待たされ続けるより、失敗として見せて再試行させたほうがましでした

## まとめ

クロスプラットフォームの移行を作って残ったことを 5 つ。

1. **アカウントリンクで UID をまとめると、運ぶものがローカルデータだけになる。** ソーシャルと課金は自動で再接続します
2. **Room を SwiftData の 1 対 1 ミラーにしておくと、スナップショットを無変換で写せる**
3. **リースは自動で奪わない。** Rules は端末を区別できないので、そこはクライアントの責務と割り切ります
4. **TTL を入れて保証を下げない。** 「同時 1 台」がリースの目的そのものです
5. **端末の識別子は再インストールを跨いで同値である必要がある。** ここが片方の OS だけ弱いことに気づけていませんでした

そして一番の学びは、**同じ機能を 2 回書くと非対称がどこかに残る**ということでした。片方で成立している前提が、もう片方では成立していません。それを見つける手段は、実機で同じシナリオを両方で通すことしかありませんでした。

## はじめに

個人開発のバケットリストアプリ **Bucket List Commit** の課金設計です。

技術的な仕組みは[技術構成](/engineering/app/indie-app-technical-architecture/)に書いたので、この記事は**何をいくらにして、なぜそう決めたか**と、**運用でお金が出ていかないようにした話**を書きます。

> シリーズ「アプリの中身と実装」全 12 本の 7 本目です。最初から読むなら [① アプリの概要](/engineering/app/indie-bucket-list-app-overview/) から。ストアに出すまでの手続きは[別シリーズ](/engineering/app/personal-app-cross-store-release-full-journey/)にまとめました。

---

## プランの形

|  | Free | Pro |
|---|---|---|
| バケット | 20 件 | 1,000 件 |
| フレンド | 2 人 | 50 人 |
| 1 件あたりの画像 | 1 枚 | 3 枚 |
| スプレッドシート出力 | — | あり |

Pro は月 ¥280 / 年 ¥2,800（約 17% 引き）です。買い切りプランは作りませんでした。

プレミアムテーマは **1 つ ¥250 の買い切り**で 6 種。**Pro には含めません。**

広告なし、無料トライアルなし、復帰オファーなしです。

## Free に何を残すかを最初に決めた

一番大きな判断がここでした。**USP の核になる機能は全部 Free に残す**と決めました。

| 機能 | Free |
|---|---|
| GitHub への双方向同期 | 使える |
| Google カレンダー連携 | 使える |
| 公開リストとフレンドのリストからの取り込み | 使える |
| Quick Add | 使える |
| 達成の演出 | 使える |
| 統計画面の閲覧（全セクション） | 使える |
| 共有バケット | 使える |
| CSV / Markdown / PDF のエクスポート | 使える |

Pro にしたのは「**使い込んだ人向けのグレードアップ**」だけです。件数の上限と、スプレッドシート出力。

理由は 2 つあります。

1. **USP を有料の壁の向こうに置くと、そもそも価値が伝わりません。** 「GitHub にデータを持てる」がこのアプリの特徴なのに、それを試せないなら誰も評価できません
2. **個人開発で機能ロックを増やすと、分岐が増えて壊れます。** ロックする場所が少ないほど、テストする組み合わせが減ります

## 上限の数字はどう決めたか

### バケット 20 件 / 1,000 件

Free の 20 件は「**Pro 訴求を強めるために、フレンド 2 人・画像 1 枚と桁を揃えた**」結果です。最初はもっと多く（30 件）にしていたのですが、3 つの上限がバラバラだと説明が長くなります。

Pro の 1,000 件は、実質的にヘビーユーザーをカバーする数です。同時に**悪意ある大量登録への防御**も兼ねています。無制限にすると、1 ユーザーが Firestore と Cloud Storage を無限に使えることになります。

### フレンド 2 人 / 50 人

Free の 2 人は意図的にかなり絞りました。「**家族・恋人・親友レベルの本当に親しい人と共有する**」想定です。

Pro の 50 人は「親しい人と共有」というコンセプトを保ちながら、**Free の 25 倍**という差をつけた数です。ここも無制限にはしません。フレンドが増えるほど Firestore の読み取りと通知の負荷が線形に増えるので、**上限がそのままコストの上限**になります。

### 画像 1 枚 / 3 枚

これが一番コストに直結します。Cloud Storage の使用量は `保存できる件数 × 1 件あたりの画像枚数` で決まるので、Pro の理論上の最大値がここで確定します。

**プランの上限を決めた時点で、1 ユーザーあたりのコスト上限も決まる**設計にしました。

## プレミアムテーマを Pro に含めなかった理由

これは何度か考え直して、最終的に「含めない」にしました。

含める場合に起きることを 2 つ考えました。

1. **テーマだけ欲しい人が月額を払うことになる。** テーマは一度買えば永続的に使えるべきもので、毎月払うものではありません
2. **月額を払っている人が「テーマも入っているはず」と誤解する。** そして「入っていない」と分かったときに不満になります

**役割が違うものを 1 つの商品にすると、説明が長くなります。** 「Pro はバケットとフレンドの上限を上げるもの」「テーマは買い切りで見た目を変えるもの」と分けたほうが、どちらも 1 行で説明できました。

Pro 加入者でもテーマは個別購入が必要です。ここは分かりにくいので、ペイウォールとテーマストアの両方に明記しています。

### 24 時間のお試しを付けた

テーマは「見た目」なので、買う前に自分のリストで見たいはずです。そこで**1 テーマにつき 24 時間・1 回だけの無料試用**を入れました。

| 項目 | 仕様 |
|---|---|
| 期間 | 24 時間（秒単位でカウントダウン） |
| 回数 | 1 テーマにつき 1 回のみ。期限切れ後の再試行は不可 |
| 並行 | 複数テーマを同時に試用できる |
| 期限切れ後 | 自動的に未購入に戻り、そのテーマを使っていたら既定テーマに切り替わる |
| 保存先 | 端末ローカルのみ |

保存先を端末ローカルにしたのは、サーバー側で管理する価値がないからです。端末を変えればもう一度試せますが、それを塞ぐためにサーバーのコレクションを 1 つ増やすほうが高コストだと判断しました。

## 解約して Free に戻ったときの設計

ここが一番仕様を書き込んだところです。方針は 1 行で決まりました。

> **データは保持したまま、UI 上は Free の上限までしか表示・操作できない。**

Pro に再加入すれば全部復元されます。**消しません。**

### 何をキャップして、何をキャップしないか

| 対象 | Free に戻ったとき |
|---|---|
| バケット（20 件超） | データは保持。更新の新しい順に 20 件のみ表示・編集・達成・削除できる |
| フレンド（2 人超） | 関係は保持。フレンドになった順の新しい 2 人のみ表示・利用できる |
| 画像（3 枚保有） | データは保持。1 枚目のみ表示 |
| エクスポート（CSV / Markdown / PDF） | キャップする（20 件） |
| SNS シェア | キャップする（20 件） |
| 統計の集計値 | キャップしない（全件） |
| プレミアムテーマ | 影響なし（買い切りなので） |
| GitHub 同期 | キャップしない（全件） |

判断が分かれたのは下 3 つです。

**統計をキャップしなかった理由**: 統計は受動的な履歴の集計です。Free に戻った瞬間に達成数が急に減ると、**履歴が失われたように見えて混乱します**。ここは完全性を優先しました。

**エクスポートとシェアはキャップした理由**: どちらも「自分のリストを能動的に出力する」操作です。Free が全件をファイルに出せると、課金している人との公平感が崩れます。

**GitHub 同期をキャップしなかった理由**: これは**意図的な例外**です。データのポータビリティがこのアプリの USP そのものなので、Free でも全バケットをリポジトリにミラーします。

この 3 つを合わせると、こう成立します。**「表示上は 20 件でも、凍結された分は GitHub から取り出せる」** ので、エクスポートのキャップがデータの人質になりません。ここが説明できないと、キャップは「解約したらデータを返さない」に見えます。

### 上限の表示は常設にした

上限に達したときだけ警告を出す形にすると、**ユーザーは「あと何件か」が分かりません**。そこで常設の行を置きました。

```
リストタブ    「12 / 20 件」  → 上限到達で「20 / 20 件 上限に到達」+ Pro への導線
フレンドタブ  「2 / 2 人」     → 同様
```

そして 1 つルールを決めました。**分子はキャップ後の件数にします。** 25 件持っていても「20 / 20 件」と出します。「25 / 20 件」は分数として壊れているので出しません。

Free に戻っている状態のときだけ、下に「ほか N 件は表示上限のため非表示」を出します。

## 権利の判定はサーバーに寄せた

iOS と Android で同じ Pro を扱う必要が出てきて、オンデバイスの判定だけでは破綻しました。詳しい構成は[技術構成](/engineering/app/indie-app-technical-architecture/)に書きましたが、要点はこれです。

```
クライアント: 購入の「証拠」を送る（iOS は署名付きトランザクション / Android は購入トークン）
                 ↓
Cloud Function: 権利の「結論」を出す
                 ↓
Firestore: Rules は「本人の read と delete」だけ。create / update を持たない
```

**Rules から書き込みを外したのが対策の本体です。** App Check だけでは塞げません（正規アプリから取り出したトークンを添えれば REST は通る）。値域制限やレート制限も代替になりません。**攻撃は 1 回の書き込みで完了する**からです。

## 審査アカウントの Pro が失効する問題

これはストアに出す直前に踏みました。

**ライセンステスターのテスト定期購入は必ず失効します。** 期間に関わらず 5 分ごとに更新され、**最大 6 回で自動キャンセル**されます（月額でも約 30 分）。

つまり「審査の直前に買い直しておく」は成立しません。**審査は数日かかります。**

そして Firestore に直接書くのも不可でした。次の検証が上書きします。

### Play が求めているのは「常時 Pro」ではなかった

ここで公式のヘルプを読み直しました。求められているのは「**レビュアーが paywall の向こうを自由に見られること**」で、手段は指定されていません。テストの権利付与でも、サンドボックスの購入経路でも、デモアクセスでもよい。

そこで**サーバー側の allowlist** にしました。特定の UID にだけ、無期限の Pro と全テーマを付与します。

これで「有料コンテンツを含む全機能に制限なくアクセスできる」という申告を、**チェックを ON にしたまま真にできます**。

実装で気をつけた点が 3 つあります。

- **更新通知の受信側にも配線が必要でした。** テスト購入の失効通知が来ると、そちらが再計算して false に戻してしまいます
- **付与は権利ドキュメントを組み立てるときだけ**にして、レシートの記録には焼き込みません。環境変数から外して再デプロイすれば消えます
- **全テーマの付与は購入元の判定より後にやります。** 先に足すと、Android からの呼び出しでも購入元が Apple と判定されてしまいました

## 予算のキルスイッチを実際にテストした

最後に、個人開発で一番怖い「知らないうちに課金が伸びる」への対策です。

**Firebase の予算を超えたら課金を止める仕組み**を入れました。

```
Cloud Billing の予算 → Pub/Sub → Cloud Function → 請求先アカウントのリンクを解除
```

### 設計の判断

| 項目 | 決めたこと |
|---|---|
| 予算 | 月 ¥5,000 |
| アラート | 50% / 90% / 100% / 200% |
| 停止する閾値 | **200%（¥10,000）** |
| 再有効化 | 手動のみ |

**100% で即停止は却下しました。** 無効化すると Firestore と Storage が止まってアプリの全機能が死にます。**原因を調べる猶予として差額を残す**という判断です。

判定は「**実費 >= 予算額 × 倍率**」の金額比較 1 点だけにしました。通知に含まれる閾値超過のフラグは**閾値を超えたときにしか入らない**ので、50% の通知で誤発火します。ここは見ません。

異常系は全部安全側（無効化しない）に倒しました。予算が 0、金額が欠落、デコード失敗。そして**壊れた通知で例外を投げると Pub/Sub が再試行ループになる**ので、そこは null に倒します。

倍率は環境変数にしましたが、**下限を 1 にしました**。1 未満を許すと予算内で停止してしまいます。

### 本番で実際に止めた

これは**未リリースだからできたテスト**でした。合成した通知を publish して、実際に課金を止めました。

| 測ったこと | 結果 |
|---|---|
| 閾値未満の通知 | 停止しない（判定ログで確認） |
| 200% ちょうどの通知 | **課金が無効化された** |
| 復旧 | コマンド 1 本。ダウンタイム約 1 分 |
| Firestore のデータ | **無傷**（復旧後に REST で直読みして確認） |
| 従量課金プランの再同意 | 不要 |

判定部分は依存ゼロの純粋関数に切り出して、副作用と分けました。これでインストールなしでテストできます。

**「止まること」と「戻ること」の両方を測っておく**のが大事でした。止まる仕組みだけ作って戻し方を確認していないと、いざ発動したときに慌てます。

## まとめ

課金設計で効いた判断を 5 つ。

1. **USP は Free に残す。** 有料の壁の向こうに置くと価値が伝わりません
2. **上限がそのままコストの上限になるように設計する。** 無制限を作らないと、費用の天井が読めます
3. **役割が違うものは別の商品にする。** サブスクと買い切りを混ぜると説明が長くなります
4. **解約してもデータは消さず、表示だけ絞る。** そして「凍結された分も取り出せる」経路を残します
5. **キルスイッチは「止まること」と「戻ること」の両方を測る。** 未リリースのうちにやっておくと安心できます
